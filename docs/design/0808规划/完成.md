# 丽客美页 Beauty Marketing Agent V3
## Agent-native 产品与工程完整升级落地方案

**方案性质**：目标架构 + 产品合同 + 领域模型 + 数据迁移 + 工程拆解 + 发布验收  
**基线**：现有 `meiyeweb-agent`、产品规划、Agentic Workbench V2 方案及前序架构评审  
**核心目标**：从“高可靠 AI 内容生产系统”升级为“拥有长期经营记忆、主动目标规划、安全执行和持续学习能力的美业营销 Agent”。

---

# 1. 执行摘要

本次升级不再把“Agent 化”理解成给现有五阶段 Workflow 增加更多 LLM 节点，而是重新划分整个系统的责任：

```text
Agent 层
负责：
长期关系 / Thread / Goal / Memory / 判断 / 规划 / 主动建议

        ↓ 编译

Execution 层
负责：
确定性门禁 / 费用 / Provider 副作用 / 恢复 / 幂等 / 交付

        ↓

Artifact & Evidence 层
负责：
ContentPackage / Asset / Delivery / Outcome / Audit
```

现有方案真正有长期价值的部分继续保留：

- DBOS durable execution；
- Task / Work 与副作用幂等；
- ContentPackage 成品真相；
- Provider 接受态；
- 用量与供应成本账本；
- 权利、经营事实与一次性发布批准；
- 不可变 revision / snapshot；
- 当前 Workbench 的文档时间线、Activity、Artifact 和对象工作区方向。

V2 架构评审已经确认，现有升级方向中的 Workstream、Living Plan、Artifact、Interrupt、Steering 等产品思想值得保留，但原方案仍偏向把 Thread、Run、Plan 等继续压入现有 Work/Task/Recipe 模型。

V3 正式改变以下四个上层假设：

1. `AgentThread` 不再等于 `Work`；
2. `MarketingGoal` 成为一等对象；
3. Memory 成为正式 Agent 子系统，而不仅是 ContextBundle 的附属能力；
4. 固定五阶段 Harness 从“永恒运行拓扑”降级为兼容执行视图，长期编排改为**受约束的 Typed Plan Grammar**。

这并不意味着引入第二套 durable runtime。DBOS 继续是所有付费、外部、副作用任务的唯一耐久执行底座。

# 2. 产品目标重新定义

## 2.1 目标产品

最终产品不是：

> “给门店一个很好用的 AI 内容生成器。”

而是：

> **“长期理解这家店，并持续帮它完成宣发工作的 Beauty Marketing Agent。”**

产品长期闭环：

```text
经营目标
   ↓
理解门店现状
   ↓
读取长期经验
   ↓
发现机会
   ↓
制定计划
   ↓
制作内容
   ↓
交付 / 发布
   ↓
记录结果
   ↓
学习
   ↓
提出下一步
```

已有产品研究已经识别到了真正护城河：通用 Agent 可以获得更好的通用文案知识，但无法自然获得一家门店持续积累的经营事实、过去半年内容与结果关系以及用户不断纠正过的经验。

因此本轮产品架构投入的优先级必须调整为：

```text
长期经营证据
>
长期 Memory
>
上下文与 Skill
>
Agent Planning
>
复杂 Agent 编排技巧
```

而不是反过来。

# 3. 架构总原则

## 3.1 一个语义，一个 canonical owner

不再使用“全系统只有一个真相源”的过度简化表达。

目标规则是：

> **One canonical owner per semantic fact。**

对应关系：

| 语义 | Canonical owner |
|---|---|
| 门店、项目、价格、活动等真实经营事实 | Business Fact Domain |
| 素材及权利 | Asset / Rights Domain |
| Agent 长期对话 | AgentThread |
| 长期经营目标 | MarketingGoal |
| Agent 经验和偏好 | Agent Memory |
| 一次执行任务 | Work / Task |
| 耐久副作用状态 | DBOS Workflow |
| 用户方案 | MarketingPlanRevision |
| 成品 | ContentPackage |
| Provider 状态与成本 | Route / Provider Attempt / Cost Ledger |
| 用户额度 | Usage Ledger |
| 外发结果 | Delivery Receipt |
| 经营反馈 | Outcome Evidence |

**禁止的是同一语义多个 writer，而不是系统存在多个领域真相。**

---

## 3.2 Agent 可以自主判断，但不能拥有业务授权

Agent 可以：

- 理解用户目标；
- 召回 Memory；
- 自主选择 Skill；
- 自主查询能力；
- 自主决定下一步读什么；
- 编译 Plan；
- 对失败输出进行有限自纠；
- 提议长期经验；
- 提议下一次营销动作。

Agent 不可以：

- 修改真实价格；
- 判断权利已经获得；
- 创建用户额度；
- 绕过产品用量；
- 修改 Provider 接受态；
- 伪造发布成功；
- 替用户完成不可逆批准；
- 将未经确认的推测升级成经营事实。

---

## 3.3 Agent Kernel 与 Durable Runtime 解耦

目标：

```text
AgentKernel
    ↓
PlanCompiler
    ↓
ExecutionSnapshot
    ↓
DBOS
```

而不是：

```text
LangGraph checkpoint
      +
DBOS checkpoint
```

因此：

- AI SDK 是首个 `AgentKernel` 实现；
- 将来如果 OpenAI Agents / Mastra Agent 等在评测上明显更好，可以**替换 AgentKernel**；
- 不允许两套 Agent durable checkpoint 与 DBOS 长期并存。

# 5. 新领域模型

本轮只新增真正具有独立语义寿命的对象。

## 5.1 AgentThread

### 解决的问题

当前一次创作 Work 结束后，新的创作天然重新开始。

长期 Agent 必须表达：

> “我们最近一直在处理什么问题？”

例如：

```text
Thread:
「8 月新客引流」

 ├ Work: 小红书护理案例
 ├ Work: 团购活动海报
 ├ Work: 老板 IP 视频
 └ Work: 周末活动复盘
```

### 建议合同

```ts
interface AgentThread {
  threadId: AgentThreadId;
  resourceId: MerchantResourceId;

  title: string;
  status: 'active' | 'archived';

  activeGoalIds: MarketingGoalId[];

  summaryRevision: number;
  summary?: string;

  lastRunAt?: string;
  createdAt: string;
  updatedAt: string;
}
```

Thread 不保存：

- ContentPackage 正文；
- Provider 状态；
- 账本；
- 权利；
- 完整 Message dump。

```ts
interface AgentRun {

    | 'running'

```

AgentRun **不是**：

- Task；
- DBOS workflow；

- business transaction。

# 7. MarketingGoal

这是 V3 最重要的新业务对象之一。

## 7.1 为什么 Goal 必须独立

用户真正说的往往不是：

> “生成一个图。”

而是：

> “最近新客少。”
>
> “下个月想多推头皮护理。”
>
> “想把老板个人 IP 做起来。”

这些目标会产生多个 Work。

因此：

```ts
interface MarketingGoal {
  goalId: MarketingGoalId;
  resourceId: MerchantResourceId;

  objective:
    | 'exposure'
    | 'inquiry'
    | 'booking'
    | 'group_buy'
    | 'ip_growth'
    | 'retention'
    | 'custom';

  statement: string;

  horizon?: {
    from?: string;
    until?: string;
  };

  priority: 'low' | 'normal' | 'high';

  status:
    | 'active'
    | 'paused'
    | 'completed'
    | 'abandoned';

  evidenceRefs: EvidenceRef[];

  revision: number;
  createdAt: string;
  updatedAt: string;
}
```

Goal 不直接拥有执行拓扑。

它是：

> Agent 持续规划的上位目标。

# 8. Agent Memory Platform

## 8.1 Memory 正式成为一级系统

现有 `ContextBundle` 保留。

但是新的关系变成：

```text
Business Truth
      │
Memory System
      │
      ↓
Context Compiler
      ↓
ContextBundle / ModelContext
      ↓
Agent
```

Memory 不代替经营事实，而是保存：

> Agent 从长期交互与结果中积累出来的“怎么更好服务这家店”的信息。

---

# 9. Memory 五层结构

## A. Working Memory

当前阶段正在做什么。

例如：

```text
当前目标：
8 月提高头皮护理咨询

当前策略：
以案例科普 + 主理人 IP 为主
```

自动维护。

无需用户逐条确认。

---

## B. Preference Memory

例如：

```text
小红书少一点强促销感
真人案例优先
标题少用连续 emoji
```

允许自动学习，但有：

- confidence；
- scope；
- decay；
- evidence；
- correction。

---

## C. Episodic Memory

一次真实经历。

例如：

```text
2026-08-03
护理案例图文
老板删除价格强调
改为专业解释
最终采用
```

自动沉淀。

主要用于未来推理和归纳。

---

## D. Procedural Memory

真正稳定的“这家店怎么做更好”。

例如：

```text
小林 IP × 小红书项目科普：
真人照片开头
→ 场景问题
→ 专业解释
→ 温和私信 CTA
```

这种 Memory 影响范围大。

需要：

```text
propose
→ merchant confirm
→ promoted
```

---

## E. Correction Memory

必须一等建模。

例如：

```text
“小林不是老板娘”
“这个项目不是 199”
“以后不要把护理写成治疗”
```

优先级：

```text
Correction
>
Soft Preference
```

---

# 10. Memory Authority 分层

取消“所有 Memory 都必须确认”的统一规则。

```text
L0 Observation
自动记录
不改变未来默认行为

L1 Soft Preference
自动生效
低权重
可衰减
可纠正

L2 Strong Preference
明确表达 / 高置信重复
长期生效
可撤销

L3 Procedural Memory
可改变未来流程
必须 promote / confirm

L4 Business Fact
不属于 Memory 权威
必须由事实域处理

L5 Irreversible Authority
Memory 永远没有资格产生
```

# 12. Progressive Living Plan

Living Plan 保留，但取消“所有任务必经完整 Plan”。

## Level 0：确定性轻修改

例如：

> 删除最后一句。

```text
request
→ deterministic derived revision
```

无需 Plan。

---

## Level 1：简单生成

例如：

> 写一条朋友圈护理介绍。

内部可以产生 concise intent/brief。

前台无需强制展示完整 Living Plan。

---

## Level 2：复杂创作

例如：

> 做一套小红书 5 页护理案例。

产生：

```text
Living Plan
↓
用户可改
↓
Make
```

---

## Level 3：Campaign / Goal Plan

例如：

> 8 月帮我持续推头皮护理。

Plan 可以包含：

```text
第 1 周：科普
第 2 周：案例
第 3 周：主理人 IP
第 4 周：团购转化
```

一个 Plan 可以派生多个 Work。

# 14. 能力模型重新设计

取消：

```text
Recipe > Skill
```

也取消：

```text
Skill > Recipe
```

正式采用四分模型。

## Capability

回答：

> 用户能完成什么？

例如：

```text
小红书案例营销
活动宣传套图
主理人 IP 内容
```

## Recipe

回答：

> 一个成熟任务默认怎么组织？

## Skill

回答：

> 如何把某个专业环节做好？

## Tool

回答：

> 真正执行哪个动作？

关系：

```text
Capability
  ├ Recipe
  ├ Skill[]
  ├ Tool[]
  ├ OutputContract
  ├ UsagePolicy
  └ SafetyPolicy
```

# 17. 原语权限

## read_context

允许 Agent：

- 查事实；
- 查素材；
- 查历史；
- 查 Memory；
- 查可用 Capability；
- 查模型能力；
- 查平台规则。

---

## generate

必须编译为产品级 GenerationIntent。

LLM 不传：

- tenant；
- billing identity；
- Provider credential。

---

## revise

只能对明确 `target_ref` 操作。

必须：

- OCC；
- stable id；
- derived revision。

---

## record

Agent 只允许：

```text
record observation
record proposal
```

禁止直接：

```text
confirm_fact
confirm_preference
grant_right
```

---

## check

确定性。

用于：

- fact fidelity；
- exactText；
- rights；
- platform hard rules；
- structural contract；
- capability compatibility。

---

## ask_merchant

不是普通 Chat。

必须支持：

- 一次性问全；
- 每项“暂不确定”；
- 整组跳过；
- 默认值；
- timeout / resume。

# 20. Typed Plan Grammar

推荐：

```ts
type AgentPlanNode =
  | ReadContextNode
  | GenerateNode
  | ReviseNode
  | CheckNode
  | AskMerchantNode
  | RecordProposalNode
  | ParallelNode
  | ConditionalNode;
```

只允许有限结构：

```text
sequence
parallel
if / else
bounded retry
wait
```

禁止：

```text
arbitrary code
unbounded loop
dynamic executable JS
model-defined SQL
model-defined HTTP endpoint
```

# 67. 最终目标

本次升级真正完成的标准不是：

```text
“Agent 会调更多 Tool”
```

也不是：

```text
“后台看起来像 Mastra”
```

而是五件事情同时成立：

### 1

商家第二个月再来时：

> Agent 真的比第一个月更懂这家店。

### 2

商家只说一个经营目标：

> Agent 可以自己拆成多次宣发任务。

### 3

一次任务复杂时：

> Agent 会规划、检查、修正，并在真正需要时询问用户。

### 4

执行过程中：

> Provider、费用、权利和发布永远可恢复、可审计、不重复。

### 5

内容发布之后：

> 结果会进入下一次判断，而不是消失在系统外。

最终产品闭环应该变成：

```text
                    ┌──────────────────────┐
                    │                      │
                    ↓                      │
Goal → Understand → Plan → Execute → Deliver
 ↑                                      │
 │                                      ↓
 └──── Learn ← Memory ← Outcome ← Observe
```

**这才是 V3 的核心。**

因此，这次升级最终应该把工程资源从：

> “怎样把五阶段 Harness 做得越来越完整”

转向：

> **“怎样让一个 Agent 长期理解一家门店，同时把所有真实业务副作用可靠地交给确定性执行内核。”**

这就是建议作为下一阶段开发权威的目标形态。
