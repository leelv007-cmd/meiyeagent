## 一、这件事为什么必须先定

三条决策各自成立，但**两两之间留了一道缝**，边界就落在缝里：

| 决策 | 原文要点 | 出处 |
|---|---|---|
| D-160② | 商家沉淀的 Skill **可用、可编辑、可删除、不提供下载**；「可编辑：商家可通过自己的组合，做简单的 Skill 编辑与二次修改，便于后续独自复用」 | `DESIGN:2688-2695` |
| D-159③-2 | 「交互形态只能是**确认式**，不能是**配置式**。商家不会配置任何东西，只会点是或否。」并注明「约束 2 最易被日后『加个高级配置面』悄悄破坏，**明确写死**」 | `DESIGN:2603`、`2606` |
| D-163② | 「D-162⑥ 维护面的职责进一步收窄——**不是编辑器，也不是沉淀管线的前台，而是『确认系统提议的沉淀』**」 | `DESIGN:3032`、`3002` |

D-160② 明写「可编辑」，D-163② 明写「不是编辑器」。**两条都没被推翻**，所以「可编辑」的合法解释只剩一种：可编辑的**面**必须小到不构成编辑器。小到什么程度，就是本页要拍的。

D-160 自己也承认这是未决项：

> ② 的「商家可编辑组合」**边界未定**：能改什么（正文？触发条件？绑定关系？）、改坏了怎么办。**须与 D-159③-2「确认式而非配置式」对齐**——编辑能力过强会直接破坏该约束。 —— `DESIGN:2746`

## 二、三条候选边界

D-160 待验证②自己列了三个候选可改对象：**正文 / 触发条件 / 绑定关系**。按可改面从小到大：

### 方案 A —— 零字段可改（纯确认流）

商家只能做四个动作：**采纳**系统提议的沉淀、**否决**、**启用/停用**已有的、**删除**。一个字段都改不了。

- 合 D-163② 与 D-159③-2 到极致。
- **但它把 D-160② 明写的「可编辑、二次修改」直接读没了**。D-160② 不是描述性的，是决定项。判否。

### 方案 B —— 只可改「一句话说明」（推荐）

在 A 的四个动作之上，**只**允许商家改一个东西：这条沉淀的**一句话说明**（即 `description` 的商家侧投影）。

- 正文（instruction）：**不可改**。理由是硬的——`service.ts:619-628` 的 `validatePrompt` 要求 `prompt.content === instruction` 且 `contentHash === sha256(content)`，正文一动就必须重走 Langfuse 提示词位点与受理门（`skillAcceptanceGateFailure`，`service.ts:630-653` 要求 evalRun 通过 + prompt `source==='langfuse'` + `label==='production'`）。让商家碰这条＝把 Langfuse 发布流搬到商家侧，直接违反 D-159③-2。
- 触发条件：**不可改**。「什么情况下生效（输出类型、品类、阶段）」在 D-162⑥ 里明确划归**运营**（User Story 42）。商家改触发条件＝配置，是 `DESIGN:2606` 点名要防的那种破坏。
- 绑定关系：**不可改**。`bindRevision` 走 `config.publish` 能力（`capability-permission.ts:342-353`），商家角色根本不持有；且绑定槽有 DB 级唯一约束（`p1_skill_bindings_active_slot_uq`）。
- 一句话说明：**可改**。它是 D-161② 明确的「运营/使用者靠它认出这条做什么」的识别字段，改它不改变任何执行语义，且天然是一次自然语言输入而非配置项。

**为什么 B 是唯一同时满足两条决策的解**：它兑现了 D-160②「简单的二次修改，便于后续独自复用」——商家给自己的做法起个自己认得的名字，正是「便于独自复用」的字面含义；同时它改不动任何执行语义，维护面主体仍是确认流，D-163② 不破。

### 方案 C —— 可改说明 + 触发条件

在 B 之上开放「什么时候用它」。

- 触发条件一旦可改，界面就必须呈现输出类型/品类/阶段三个维度的选择器——**那就是配置面**。`DESIGN:2606` 已经预判并写死否掉了这条路。判否。

**推荐：方案 B。**

## 三、「改坏了怎么办」——三层兜底，两层是白嫖的

D-160 待验证②问的后半句。答案不需要新建机制：

**第一层：改动本身不可能改坏正在跑的东西。** 已实现且扎实：
- revision append-only，写入只 INSERT 无 upsert，CAS 校验 `current === expectedRevision && revision === current + 1`（`postgres-repository.ts:136-189`）；
- 冻结后无任何 UPDATE 路径，`acceptRevision` 的 WHERE 带 `content_hash`，内容改了就更新不到行（`postgres-repository.ts:191-213`）；
- run 启动即在单个 durable step 冻结 `{skillRevisionRefs, skillContentHashes, skillReceiptIds}`，replay 时逐项比对不符即抛（`workflow-core.ts:378-437`）。

即 D-162⑥ 那句「运营改 skill ＝ 建新 revision，动不了正在跑的任务」对商家侧同样成立，**零新建代码**。

**第二层：商家侧只暴露「恢复上一版」单键，不暴露版本号、不暴露版本列表。** 底层是 `rollbackBinding`（`service.ts:168-217`，只允许回到同 skill 的 `accepted_frozen`），但商家侧界面上不出现 revision / version / rollback 任何一个词（见第四节对照表）。一次点击，一个确认，回到上一个状态。这是确认式对「撤销」的唯一合法形态。

**第三层：红线不进商家可改面。** 权限边界由 D-162⑥ 划定——红线走合规评审，运营都不可改，商家更不可改。落地形态见下一条 ⚠️。

> ⚠️ **实现缺口（须在实装票里解决，不是本页拍板项）**：仓里现有的「不可改」粒度只有两级——整个 config key 拒写（`admin-config/foundation-module.ts:636-641`）与整个 action 不可达（`capability-permission.ts` 映射为 `null` 即默认拒）。**没有以 zod schema 单字段为粒度的通用钩子。** 所以「红线运营不可改」的可落地形态是：把红线做成**独立的、对 `config_apply` 不可写的 key / 独立表**，而不是在某个 schema 里标一个字段。

## 四、术语对照表（补 D-116 判据缺口）

**为什么需要这张表**：票面验收第 4 条要求「商家侧文案过 D-116 口径（无工程词汇）」，但 **D-116 在决策层没有可判定的判据**——正文只给三类禁止（工程语言 / 内部对象名 / LLM 原始反馈，`DESIGN:1984`），判定口径本身还挂在 D-116 的待验证段里（`DESIGN:1988`）。能引用的黑名单只有 D-124 的开放枚举「角色、Workspace、API Key、Provider、技术账本」（`DESIGN:1742`）加一条 `revision` 判例（`DESIGN:2265`）。

而 Core 已有的 19 条禁词正则（`merchant-delivery-language.ts:12-32`）里**已经包含 `revision` / `snapshot` / `schema` / `intent`**——这恰恰是 Skill 界面最想说的几个词。没有这张表，本票商家侧一写文案就撞现成的 CI 门。

| 工程侧概念 | 商家侧说法 | 理由 |
|---|---|---|
| Skill / 技能 | **这套做法** / **你的做法** | 「技能」在商家语境指手艺人手艺，会误读；「做法」是美业口语 |
| skill catalog | **做法清单** | —— |
| revision / version | **不出现**。需要表达时说「上一版」「现在这版」 | `revision` 是既有 D-116 判例（`DESIGN:2265`），且在 19 条禁词内 |
| manifest | **不出现** | 商家侧无对应概念 |
| binding / 绑定 | **不出现** | 归运营，商家不可见 |
| 触发条件 | **什么时候用它**（只读展示，不可改） | 名词化会读成配置项 |
| draft | **还没开始用** | —— |
| accepted_frozen | **已经在用** | —— |
| rollback | **恢复上一版** | 动作名，不是状态名 |
| delete / 删除 | **不再用了** | 「删除」触发损失焦虑；D-160② 的定位是冗余兜底而非主动作 |
| description | **一句话说明** | D-161② 的商家侧投影，也是方案 B 唯一可改字段 |
| eval / 评测 | **不出现** | 商家侧不跑评测；治理的评测环节在运营侧 |
| export / download / 导出 / 下载 | **不出现**，且**不解释**。若必须回应，口径是「它离开这里就跑不起来」 | D-160② `DESIGN:2700`：正确表述不是「我们不允许导出」而是「该产物不存在可携带形态」——承诺一个技术上无意义的能力本身就不诚实 |
| propose / 提议 | **系统问一句：以后都这样？** | D-159③-2 的确认式原型 |

**这张表本身需要拍板**——它是在决策层留白处填的口径，不是从原文推出来的。

### 可白嫖的现成 CI 门

`promptfooconfig.merchant-language.yaml` 这道门**已经在 CI 里跑**（`.github/workflows/core-quality.yml:31-43`，含正向门 + 变异控制反证门），但它检的是 Core 的 `merchantXxx()` 输出函数（`evals/merchant-language/cases.ts:34-70`，仅 5 条 case），**不检 React 组件里的字符串**。

最省事的接法：#259 新增的商家侧 Skill 文案落成 `merchant-delivery-language.ts` 的导出函数，再往 `cases.ts` 加 case——零改造，直接进现成 CI 门，验收第 4 条从「不可判定」变成「可判红可判绿」。
