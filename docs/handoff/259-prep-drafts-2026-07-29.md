## 一、数据面缺口清单（后端工作量远大于「建一个面」）

再加两个净缺：

- **无删除类动词**：全库 `rg 'skill_delete|skill_retire|skill_archive|skill_disable'` 零命中。票面第 3 项「商家侧删除入口」在 Core 侧没有对应命令。

  **裁定（2026-07-29）：租户维度不进本票。** 本票只新增 `tier` 与 `sourceKind` 两个枚举；`workspaceId` 列另立票，随门店层证据层通电时补。依据：`DESIGN:2744`（门店层依赖证据层通电，归纳门槛刻意留空、不提前设计）＋ `DESIGN:3160`（门店层沉淀早期近乎为空）——本轮目录页实际只承载平台层＋行业层，两者均为全局。`tier` 字段现在就存，否则 D-160⓪ 的占比指标算不出（「指标要能算，字段就得先存」）。

## 二、目录页 schema 草案

### 2.1 三个新字段

```ts
/** 一条 Skill 的来源。D-160⓪ 的「行业层第二来源交叉验证占比」由本字段算出。 */
export const SKILL_SOURCE_KINDS = ['harvested', 'authored', 'induced'] as const;
export type SkillSourceKind = (typeof SKILL_SOURCE_KINDS)[number];
// harvested 收割转译 / authored 手写 / induced 归纳
// 三值与 DESIGN:2664-2666 的三层护城河成色表逐一对应；不得新增第四值，不得可空。

/** 归属层级。DESIGN:2664-2666。 */
export const SKILL_TIERS = ['platform', 'industry', 'store'] as const;
export type SkillTier = (typeof SKILL_TIERS)[number];

// SkillCatalog 增补：
//   description: string   // D-161② 必填必显；长度预算随 #258 的 frontmatter 收口定
//   sourceKind: SkillSourceKind
//   tier: SkillTier
//   sourceRef?: { externalUrl?: string; harvestedAt?: string }  // D-160 影响：转译须标外部来源与来源时间
```

### 2.2 落库形态 —— 必须提升为独立列

现有范式是 payload-jsonb（整个领域对象塞 `payload jsonb`，只把索引/约束需要的提为独立列，`postgres-repository.ts:444-472` 的 `putOnce` `extraColumns` 机制）。

**只展示可以塞 payload；但本票不行**——验收要求「目录『来源』列可直接算出行业层第二来源交叉验证占比」，那是过滤 + 聚合，jsonb 里算不动也建不了索引。

```sql
ALTER TABLE p1_skill_catalogs ADD COLUMN IF NOT EXISTS source_kind text;
ALTER TABLE p1_skill_catalogs ADD COLUMN IF NOT EXISTS tier text;
CREATE INDEX IF NOT EXISTS p1_skill_catalogs_tier_source_idx
  ON p1_skill_catalogs (tier, source_kind);
```

写进 `PostgresSkillRepository.migrate()` 的内联 DDL（`skills/postgres-repository.ts:22-113`）。**仓里没有独立 migration 目录**，加列只能改这段（`find apps packages -type d -name '*migration*'` 无结果），走 `migratePostgresSchema` 的 advisory lock + 单事务（`postgres-schema-migration.ts:11-29`）。

`description` 若只显示不过滤，可留 payload——但它是 #258 的 manifest/sidecar 分层结果，**以 #258 落型为准，本草案不预设**。

### 2.3 指标可算性（验收第 2 条的落点）

```sql
-- 行业层第二来源交叉验证占比
SELECT count(*) FILTER (WHERE source_kind = 'induced')::float / nullif(count(*), 0)
FROM p1_skill_catalogs WHERE tier = 'industry';
```

验收断言即：插入若干已知分布的 fixture → 该查询返回预期比值。**fixture 值必须生产可产出**（假绿三禁）。

## 三、五命令 web 派发点契约草案

### 3.1 新增查询（净新建）

| action | payload | 返回 | 权限建议 |
|---|---|---|---|
| `skill_catalog_list` | `{ tier?, sourceKind?, cursor?, limit }` | `SkillCatalogRow[]`（含 `description`/`sourceKind`/`tier`/`activeRevisionRef`） | `workspace.read`（读）——**不可复用 `config.publish`**，否则运营看一眼目录都要 step-up |
| `skill_revision_history` | `{ skillId, cursor?, limit }` | `SkillRevisionRow[]` | 同上 |

两条都要在 `capability-permission.ts:342-353` 补 `kind==='query'` 分支，否则 `authorizer.ts:46-48` 默认拒。**强制分页上限、禁全量语义**（沿 `SPEC:424` 的「不可导出落在查询 API」口径）。

### 3.2 五命令的界面派发形态

沿 admin-config 的 A 链范式（`admin-runtime-config-control.tsx:327-472`），逐条：

| 命令 | 界面动作 | 关键约束 |
|---|---|---|
| `skill_define` | 「新建做法」表单 → 结构化字段，**不是 JSON** | 复合命令：仅 `instruction`+`manifest`+`prompt` 三者齐备才连带 `draftRevision`，缺一即 fail（`foundation-module.ts:82-100`） |
| `skill_accept` | 「跑评测并发布」 | payload 带 `EvalRun`；受理门要求 prompt `source==='langfuse'` + `!isFallback` + `label==='production'`，且 `prompt.content === instruction`（`service.ts:619-653`） |
| `skill_bind` | 「挂到哪个阶段」 | 带 `expectedRevision` 走 CAS；绑定槽 DB 唯一约束 `p1_skill_bindings_active_slot_uq` |
| `skill_rollback` | 「回滚绑定」 | 只允许回同 skill 的 `accepted_frozen`（`service.ts:185-193`） |
| `skill_deployment` | **本票唯一真·零派发**，须新建 | 首发部署硬门：非 `prompt_materialized` 必须带 `experimentalGate.enabled`+`evidenceRef`（`service.ts:237-255`） |

**表单渲染走 HeroUI `DataGrid` 字段树**（`admin-config-form.tsx:15-23` + `admin-config-field-model.ts:1-12` 的「把 zod 契约读成一棵字段树」），**不保留裸 JSON**——这是 D-048 的硬要求，也是补上第〇节那个漏网的方式。

**目录页表格走 shadcn `Table` + `AdminPanel`**（范式 `admin-runtime-config-control.tsx:513-570`），「来源」列用 `AdminStatusChip`。

### 3.3 两处会咬人的既有机制

1. **step-up 重认证**：五命令全映射 `config.publish`，且**一条都不在** `CONFIG_PUBLISH_ACTIONS_WITHOUT_STEP_UP` 白名单（`auth/recent-authentication.ts:39-57`）→ 每次派发都要求 15 分钟内重新认证。目录页做成「点一下就改」会不断弹重认证。**须裁**：把只读查询排除在外（3.1 已按 `workspace.read` 设计），写操作是否进白名单由主控定。
2. **幂等键**：`commandP1` 第三参必须给（范式 `admin-recipe-studio-control.tsx:117-121` 的 `${action}:${crypto.randomUUID()}`），core 侧 `requiredIdempotencyKey` 会卡（`server.ts:2230-2262`）。

### 3.4 六格链留痕口径（关票证据格式）

### 4.2 来源列可算性（票面验收 2）

### 4.3 无导出端点（票面验收 3，**范围须收窄**）

按字面「商家侧全 API 面无导出端点」现网就红（第〇节 #3）。收窄为两条可断言的：

1. `skills` 模块 command/query 注册表快照中**不含任何 export/download 动词**（形态参照 `packages/contracts/src/capability-inventory.test.ts` 的「期望清单 vs 实际清单 + 显式记账枚举盲区」，78 行，是仓里最接近 #246-E 口径的现成物）。
2. 商家侧 Skill 界面**不渲染任何 `Content-Disposition` / `download` 触发路径**。

**属主须裁**：`SPEC:424` 把 no-export 断言也写进了 #251。两票各写一版就是「并行分包语义冲突」那个坑。建议 #259 建库（它先合），#251 引用。

### 4.4 红线不可改（票面任务 2 的负向断言）

⚠️ **现有机制粒度不够**：仓里只有「整个 config key 拒写」（`admin-config/foundation-module.ts:636-641`，键名前缀匹配）与「整个 action 默认拒」（`capability-permission.ts` 映射为 `null`）两级，**没有 zod schema 单字段粒度的钩子**。

落地形态建议：红线做成**独立的、对 `config_apply` 不可写的 key / 独立表**，负向断言＝以运营 actor 调用写红线 → 拒绝。
