# 美业宣发经营 Agent：UI/UX 与 Dashboard Agent 化调整建议

## 核心判断

基于附件的最新权威决策、仓库当前 `main` 分支实现，以及最近围绕创作旅程的提交，我的结论是：

> **不需要重新推翻信息架构。应保留“单 Dashboard 路由三段式”与五个一级导航，把产品从“装了 Agent 卡片的 Dashboard”升级为“由 Agent 状态驱动的工作台”。**

附件已经明确将仓库状态定义为“已接受产品方向、研究仍开放”，且后续 D-164～D-169 对 Dashboard、记忆、执行确认、HITL 和事件状态进行了进一步收敛。当前代码也已实现“提议—创作—继续工作”的三段式结构，而不是停留在概念阶段。

真正需要调整的是以下三件事：

1. 从“纵向卡片堆叠”转向“Agent 事件流＋对象工作区”。
2. 从“固定创建表面”转向“随任务阶段自适应的工作台”。
3. 从“有记忆页面”转向“用户能明确感知产品越来越懂自己”。

# 一、Dashboard 主入口的推荐形态

## 1. 保留一个工作台入口，不再拆首页与创作页

目前 D-164 的方向是正确的：

```text
一级导航
├─ 工作台
├─ 内容
├─ 素材
├─ 门店
└─ 记忆

工作台单路由
├─ ① 今天的提议
├─ ② Agent 创作区
└─ ③ 继续上次工作
```

“工作台”应该同时承担启动、执行、恢复和结果预览，而不是让用户先进入项目列表，再进入创作页。现有代码也已把这三段放在同一个 `ComposerHome` 中。

但应增加一个关键变化：

> **三段结构保持不变，第二段“Agent 创作区”根据任务状态动态改变布局。**

### 冷态或尚未开始任务

维持居中的单列工作台，宽度约 720～800px：

```text
嗨，XX 店主，今天想发点什么？

[ 今天的建议：周五晚适合发预约内容…… ]

[ 定制创作 | 自由创作 ]

[ 智能判断 | 文案 | 图文 | 视频 ]
[ 项目介绍 ] [活动促销] [案例种草] [个人IP] …

┌────────────────────────────┐
│ 说说今天想做什么……          │
│ 上传图片 / 价目表 / 旧内容   │
└────────────────────────────┘

继续上次工作
```

### 任务开始之后

第二段扩展为一个自适应双栏工作区：

```text
┌─────────────────────────────┬─────────────────────┐
│ Agent 事件流                 │ 本次上下文           │
│                             │                     │
│ 意图理解                     │ 当前内容工作区       │
│ 补问卡                       │ 使用的人设           │
│ 计划卡                       │ 引用的项目/素材      │
│ 执行确认卡                   │ 当前任务与等待状态   │
│ 任务进度                     │                     │
│ 成品预览                     │                     │
│                             │                     │
│ [常驻输入框]                 │                     │
└─────────────────────────────┴─────────────────────┘
```

右栏不是参数面板，也不是 KPI Dashboard，而是**只读上下文栏**。它回答：

- Agent 本次用了什么；
- 当前任务属于哪个内容工作区；
- 使用了哪个人设；
- 哪些事实和素材正在生效；
- 当前是否有待处理问题；
- 当前任务处于什么阶段。

移动端把右栏收进全高 Bottom Sheet，不长期占据屏幕。

这样既遵循“不让商家配置”的产品原则，又能避免所有信息都塞入对话流。产品文档已经明确，秒级连续信息适合对话流，长任务适合任务卡，持久对象适合对象工作区。

# 二、当前实现中最值得优先修正的问题

## 1. 推荐卡预填时硬编码选择了文案

当前 `TodayRecommendationCard` 的预填回调会执行：

```ts
selectLens(current, 'copy')
```

也就是说，不论推荐实际适合图文还是视频，点击后都会先进入文案类型。

这与定制创作中“由 Agent 编译 `outputKind`”的方向不完全一致。定制创作不应该要求用户在生成前承担媒介分类。

建议把推荐从一个纯字符串升级成类型化载荷：

```ts
type RecommendationHandoff = {
  intent: string;
  outputHint?: 'copy' | 'image_text_note' | 'video';
  recipeRevisionRef?: string;
  sourceEvidence: EvidenceRef[];
  distributionTarget?: string;
};
```

定制创作模式下：

- 默认选择“智能判断”；
- `outputHint` 只是 Agent 的建议；
- 用户可以修改为文案、图文或视频；
- 不再默认落到 `copy`。

自由创作模式下，继续要求用户显式选择媒介和模型。

这可以解决 D-164 的“输出类型轴可见”与 D-114 的“定制创作由系统判断输出类型”之间的表面冲突：

```text
定制创作：智能判断（默认）| 文案 | 图文 | 视频
自由创作：文案 | 图片 | 视频（必须显式选择）
```

## 2. 第二段正在形成纵向卡片堆叠

当前创作段已经包含：

- 身份选择；
- 引导补问；
- 执行确认；
- 等待消息；
- 流式内容；
- Lens；
- Recipe pills；
- Quote；
- 额度；
- 工具；
- Brief；
- 执行确认与成本反馈。

这些都处于同一条纵向流里。

功能继续 Agent 化后，这种结构很容易成为“卡片滚动灾难”。

建议明确一套 **Agent Frame 视觉语法**，不要让每个后端对象都对应一个新卡片。

可以将业务上的九类 HITL 和各种执行事件，收敛为六类前端呈现组件：

| 呈现族 | 承载内容 |
|---|---|
| `NarrativeFrame` | 阶段说明、策略摘要、部分失败说明 |
| `DecisionFrame` | 补问、事实确认、执行确认、资源闸门 |
| `PlanFrame` | NotePlan、Storyboard、任务计划 |
| `TaskFrame` | 长任务、离场、恢复、取消、重新连接 |
| `ResultFrame` | 文案、图文、图片、视频成品 |
| `MemoryFrame` | 偏好或工作流沉淀提议 |

每个 Frame 统一具备：

```ts
type AgentFrame = {
  frameId: string;
  runId: string;
  kind: AgentFrameKind;
  status:
    | 'streaming'
    | 'waiting_user'
    | 'running'
    | 'paused'
    | 'partial'
    | 'completed'
    | 'failed';
  title: string;
  summary?: string;
  evidence?: EvidenceRef[];
  primaryAction?: Action;
  secondaryActions?: Action[];
  resumeRef?: ResumeRef;
};
```

完成后的执行过程应折叠成类似：

```text
✓ 已理解你的需求
✓ 已使用 3 项门店资料
✓ 已完成内容计划
  查看过程
```

不要继续保留三张或四张完整卡片。

# 三、执行确认卡应该成为统一执行边界

目前仓库已经实现了独立 `execution-confirm-slot`，确认卡和本次成本反馈也放在同一视觉位置，这是正确方向。

建议将它正式定义为所有“生成型动作”的统一边界：

```text
这次将生成
小红书图文笔记 · 5 页

使用
本店项目：头皮护理 SPA
人物：小林主理人
素材：3 张案例图

成品规格
3:4 竖版 · 适合小红书发布
共生成 5 张图片

本次使用
1 次文案额度 + 5 张图片额度
完成后剩余：文案 18 次、图片 42 张

[暂不生成]                 [确认生成]
```

关键原则：

- 卡片只读；
- 不允许在卡内修改比例、数量、模型；
- “修改设置”应返回输入区；
- 只有“拒绝”和“确认”两个决策动作；
- 确定性编辑不出现该卡；
- 会再次调用模型的改版，继续经过同一确认卡；
- 拒绝后原位显示“本次未消耗额度”，不能仅发 Toast。

# 四、成品卡应从“结果卡”变成“下一步行动中心”

成品卡应该有清楚的三层结构：

```text
第一层：成品本身
图片、图文、视频或流式文案

第二层：主要业务动作
采用这版 / 设为封面 / 使用此成片 / 交付

第三层：继续迭代
[换成深色背景]
[加上开业日期]
[生成横版尺寸]

评价条
复制  👍  👎  ⋯
```

当前代码已经实现：

- 评价事件；
- 后续动作 chip；
- chip 只预填输入框、不自动提交。

这部分不需要重新设计机制，只需要强化视觉层级：

- 成品本身占最大面积；
- 主动作只能有一个；
- 后续动作 chips 最多 2～3 个；
- 评价图标极轻，不与业务动作竞争；
- 成本反馈放在结果消息尾部；
- “采用”“保存到素材库”“交付”“基于此再创作”必须保持不同语义。

复杂编辑继续进入结果对象工作区，不在对话流里铺满编辑控件。对话流是主线，对象工作区是放大镜。

# 五、“记忆”不应设计成设置页

把记忆升为一级导航是正确的，因为“越用越懂我”必须是用户能看见的产品价值。附件将其划分为：

- 门店主体偏好；
- 营销活动；
- 常用工作流；
- 用户纠正。

但当前页面仍比较接近四个普通白瓷区块，其中三个域明确尚无生产者；对象值如果不是字符串，还会直接 `JSON.stringify`。

建议将记忆页改成三层：

## 第一层：待你确认

这是默认入口和最有价值的区域：

```text
Agent 最近发现了 2 条可能值得记住的做法

“你最近三次都把促销语气调弱了”
适用范围：小林主理人 × 小红书项目内容
来源：7 月 22 日、25 日、29 日三次创作

[不是这样] [调整一下] [记住]
```

## 第二层：已经记住的内容

按四域分组，而不是简单平铺：

```text
门店表达
项目与活动
常用做法
我的纠正
```

## 第三层：证据抽屉

每条记忆都可以打开：

- 来自哪些会话；
- 哪几次操作形成了这一判断；
- 适用范围；
- 当前 revision；
- 来源是否已被删除；
- 对哪些创作任务产生影响。

记忆页的核心不是 CRUD，而是：

> **系统提出沉淀建议，商家确认、拒绝或纠正。**

这也符合产品最新战略：商家不负责配置 Skill，系统负责策展，用户只做确认。

冷启动时不要显示四个“暂无数据”的空区块。应该解释：

```text
完成几次创作后，这里会开始出现：
· 你常用的表达方式
· 经常发布的项目
· 你反复纠正过的内容
· 可以继续复用的创作做法
```

但必须明确这是将来会生成的内容，不能伪造已经学会。

# 六、视觉系统调整方向

现有“门店橱窗”视觉方向应继续保留。它已经明确：

- 内容是主角；
- 控件只用玻璃或白瓷；
- 控件保持中性；
- 玫瑰金只用于 AI 时刻且一屏不超过 5%；
- 双主题正式支持。

建议进一步规定材质与对象语义的对应关系：

| 材质 | 对应语义 |
|---|---|
| 玻璃 | 临时建议、今日提议、浮层、上下文摘要 |
| 白瓷 | 可长期保留的成品、任务、记忆、资产 |
| 无卡片文本 | Agent 叙述、阶段说明、策略解释 |
| 状态浅色 Wash | 等待、警告、失败、部分完成 |
| 玫瑰金火花 | Agent 正在生成、Agent 新建议、升级提示 |

最重要的一条是：

> **不是每条 Agent 消息都要成为一张卡。**

普通叙述使用时间线文本；只有需要选择、确认、查看结构或操作的内容才使用卡片。

“今天建议”当前仍是一个完整的标准 Card。建议在热态把它压缩为玻璃提议条；只有冷态示例店才使用较大的媒体卡。

# 七、长任务和多设备恢复

视频、图文笔记、批量解析等任务必须通过任务卡承接，而不是让用户守在加载状态里。

任务卡建议固定包含：

```text
正在生成 5 页图文笔记
已完成文案与页面计划
正在生成第 3/5 张图片

预计还需一会儿
可以离开，完成后会提醒你

[查看当前结果] [取消任务]
```

任务离场后：

- “继续上次工作”指向同一个 `runId/workId`；
- 通知也指向同一个对象；
- 页面刷新后恢复同一个待确认节点；
- `reattach` 与 `replay` 分别验收；
- 不创建新的聊天线程或第二套任务真相。

最新决策已经要求待确认状态可跨重启、跨设备持久化，并要求 `runId + step + resumeData` 作为恢复合同。

# 八、建议采用的开源方案与组件

## 1. AG-UI：采用事件语义，不替换现有运行时

AG-UI 提供事件化的 Agent—UI 协议，包括流式消息、状态同步、工具输出、HITL interrupts、静态或声明式 Generative UI；同时强调展示 trace 或工具事件摘要，而不是原始思维链。

适合借鉴：

- Event envelope；
- interrupt/resume 语义；
- typed attachments；
- state snapshot/delta；
- frontend tool rendering；
- custom event。

不建议：

- 用它替换 DBOS、Task、ContentPackage 或现有账本；
- 让模型自由生成任意组件树；
- 在商家端开放无约束 Generative UI。

建议建立一个轻量映射层：

```text
DBOS / Core Events
        ↓
AgentFrame Adapter
        ↓
React Component Registry
```

参考：

- AG-UI Docs：<https://docs.ag-ui.com/>

---

## 2. AI SDK 7：继续作为流式传输和 UIMessage 底座

仓库已经使用 AI SDK 7，且当前 Web 依赖中包含 `ai@7.0.19` 与 `@ai-sdk/react`。

AI SDK 的 `useChat` 采用 transport-based 架构，可承接流式 UIMessage 和工具调用状态。

建议：

- 用 typed data parts 表达 `AgentFrame`；
- 文本 token 与结构化事件分流；
- 不把聊天消息数组作为业务真相；
- DBOS 和 canonical object 仍是恢复来源。

参考：

- AI SDK UI / useChat：<https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-chat>

---

## 3. assistant-ui/tool-ui：选择性复制组件，不接入完整 Thread Runtime

assistant-ui 的 Tool UI 支持 loading、result、interactive、error 和 human input 状态，并能渲染服务端工具、外部工具和审批请求。

其 `tool-ui` 仓库提供可复制的 React 工具调用组件，并采用 MIT 许可。

适合参考或局部移植：

- Approval card；
- Option list；
- Progress tracker；
- Media gallery；
- Error recovery；
- Human input card。

不建议接入其完整 Thread/Message Runtime，因为这会与现有：

- session；
- Task/Work；
- DBOS workflow；
- ContentPackage revision；
- pending-actions；

形成第二状态源。

参考：

- assistant-ui Tools：<https://www.assistant-ui.com/docs/tools>
- tool-ui：<https://github.com/assistant-ui/tool-ui>

---

## 4. CopilotKit：只参考两类 HITL 的分界

CopilotKit 将 HITL 分为两类：

- LLM 决定发起的人类输入；
- 工作流代码确定性触发的 interrupt。

这与项目当前结构高度相符：

```text
Agent 判断需要补充信息
→ AskMerchantCard

额度、权利、发布等确定性条件
→ Workflow-enforced ConfirmationCard
```

建议借鉴这一分界，不引入 CopilotKit Runtime。其 Headless UI 和 Generative UI 能力可以作为交互参考，但现有前后端真相链不适合再叠一套 Agent 状态。

参考：

- CopilotKit HITL：<https://docs.copilotkit.ai/agent-spec/human-in-the-loop>
- CopilotKit Docs：<https://docs.copilotkit.ai/>

# 九、现有组件的具体使用建议

仓库已经具备足够组件，不需要再引入大型 UI 框架：

| 现有组件 | 推荐用途 |
|---|---|
| HeroUI v3 / HeroUI Pro | 工作台壳、确认卡、菜单、状态、表单基础 |
| React Aria Components | Radiogroup、Dialog、Listbox、焦点与读屏语义 |
| `motion` | 卡片状态转换、流式出现、工作台单列到双栏变形 |
| `vaul` | 移动端上下文与工具 Bottom Sheet |
| `react-resizable-panels` | 结果对象工作区，不用于首页 |
| `@number-flow/react` | 本次额度和剩余额度的数字变化 |
| `streamdown` | 流式 Markdown 文案 |
| Sonner | 后台失败或跨页面反馈，不用于关键成本与确认结果 |
| Recharts | 仅后台运营分析，不进入商家 Dashboard |

其中：

- `react-resizable-panels` 只用于结果中心或 Pro Studio；
- 首页不应变成可拖拽三栏 IDE；
- Sonner 不应承载“扣了多少额度”“是否发布成功”等必须长期可见的信息；
- Recharts 不应把商家工作台改成经营数据大屏。

# 十、实施优先级

## P0：先统一体验模型

1. 推荐 handoff 从字符串升级为类型化对象，移除默认 `copy`。
2. 定制创作增加“智能判断”状态，自由创作保持显式媒介选择。
3. 建立统一 `AgentFrame` 契约与组件 Registry。
4. 完成事件折叠规则，避免纵向卡片持续增长。
5. 规范执行确认卡与本次额度反馈。

## P1：提升 Agent 感知

1. 创作中状态扩展为桌面双栏、移动端单栏＋上下文 Sheet。
2. 结果卡建立统一主动作、评价条和后续 chips。
3. 记忆页改为“待确认 Inbox＋已确认记忆＋证据抽屉”。
4. 任务卡完成离场、恢复、重连和精确深链。

## P2：完善对象工作区

1. 图文、图片、视频各自建立媒介专属工作面。
2. 统一采用、调整、交付、版本、再创作语义。
3. 将技术详情、trace、供应商和成本证据留在后台或折叠运行详情。

---

# 十一、建议写入 UI 验收合同的指标

建议不要只检查截图，而是增加以下行为验收：

- 推荐和动作 chip 永不自动提交、永不自动扣额度；
- 定制创作可以不选择输出类型直接开始；
- 自由创作必须明确选择媒介和模型；
- 同一时刻只出现一个主动作；
- 一个需要用户决策的语义只出现一张卡；
- 所有待确认节点刷新和换设备后都能恢复；
- 生成被拒后原位显示本次实际额度变化；
- 所有记忆候选都能看到来源证据；
- 前台不出现内部 ID、原始 JSON、Provider、Channel、Deployment；
- 完成的 Agent 步骤可以折叠，但不能失去审计入口；
- 320px 宽度和 200% 缩放下仍能完成确认、恢复和交付；
- 屏幕阅读器能够区分“正在生成”“等待你处理”“部分完成”“已完成”。

# 结论

最终目标不是让产品“更像聊天机器人”，而是让用户清楚感知：

> **它知道我现在要做什么，知道应该用我的哪些资料，遇到不确定时只问必要的问题，长任务可以自己继续，结果出来后告诉我下一步，而且每次使用都会沉淀成下一次更懂我的依据。**

这才是这套产品 Agent 化之后，Dashboard 主入口应承担的核心体验。
