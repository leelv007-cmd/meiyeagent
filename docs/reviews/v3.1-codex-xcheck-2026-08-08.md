# V3.1 权威规划独立交叉复核（Codex，反驳立场）

**日期**：2026-08-08  
**复核对象**：`docs/design/0808规划/meiye-agent-v3.1-authoritative-plan-2026-08-08.md`  
**复核口径**：默认正文有错；以正文内部合同、两份评审裁决、当前代码和既有 accepted 决策四路互证。本文只报告仍会影响开票或实施的残余问题，不重复两轮评审已正确修掉的内容。

## 1. 总判断

V3.1 已把 R1–R16 与框架评审的大部分方向正确并入，且多数仓库事实断言经抽查成立；但它目前**还不能直接作为无歧义的开票权威**：共发现 **9 项 BLOCK、13 项 MAJOR、3 项 MINOR**。高风险集中在原地合并产生的合同缝：纯 copy 免确认后没有合法的冻结交接物；确认卡、reservation、超时退款的时序与 D-153/现代码相反； Interrupt 缺 revision/run/step 却声称可校验 stale resume；HarnessRelease 同时被写成 immutable、内嵌可变 rollout、又允许未留痕的 per-run override；Prompt Pack 漏掉两个仍在生产路径使用的 key；重试默认值撞 D-167；L2/L3 后置裁决又被 PR/发布门重新拉回批次 5。上述 BLOCK 修清、待决策项拍板并把四张实施矩阵重新对齐前，不建议按 §36 直接开全量票。

## 2. Findings

### BLOCK

#### BLOCK-01：纯 copy 免确认路径没有可供 Make Harness 消费的冻结快照

- **位置**：§3 Level 1（行 180–192）、§7.4（行 378–386）、§14.2（行 637–658）、§21.1（行 926–935）、批次 2/3（行 1588–1606）。
- **证据**：§7.4 声明两个 Harness 的中间“由 `ApprovedPlanSnapshot` 连接”；§14.2 又把它限定为“用户确认后冻结”。但 Level 1 纯 copy 明确跳过 `plan_ready/awaiting_approval`，直接 `handing_off`。纯 copy 仍会调用 LLM、报价和扣积分，并非 Level 0 的确定性旁路，因此 Make 不能既要求唯一冻结快照，又在该路径拿不到快照。§37 也没有覆盖“免确认但 exact plan/release/quote 仍冻结”的断言。
- **建议修法**：把交接物改成中性名称（如 `ExecutionPlanSnapshot`），增加 `approvalBasis: 'merchant_confirmed' | 'policy_exempt_copy'` 和可选 `confirmationRecordRef`；两种路径都必须冻结 exact plan/quote/release，只有含付费媒体路径要求商家确认记录。补 Level 1 admission、重放和扣费幂等测试。

#### BLOCK-02：确认、reservation 与 hold 到期的时序互相矛盾，D-153 无法按正文实现

- **位置**：§14.1–14.3（行 631–682）、§37.2/§37.4-H（行 1684–1702）、附录 A2/A3（行 1850–1852）。
- **证据**：正文说 `PlanConfirmationRecord` 在“确认”后落库，却在记录里放 `holdExpiresAt`；又说 reservation 在确认后的 Make 启动事务内才执行。D-153（决策日志行 2521–2532）的对象则是**等待商家确认的 hold 卡**，到期时取消已有任务并退回预留额度；当前 `dbos-workflow.ts:490-538` 也在等待期间读取 `usageReservation`，到期落 `core_hold_expired` 并退款。按 V3.1 时序，未确认时既没有 `PlanConfirmationRecord`，也没有 reservation，`holdExpiresAt` 无处生效，“退分”也没有被预留的分可退。
- **建议修法**：实施前二选一并显式 supersede：A. 保留 D-153，确认请求创建前先 reserve，拒绝/过期全额 refund，确认后继续 settle；B. 改成确认前不 reserve，则到期文案必须是“未扣分”而非“已退回”，并显式修订 D-153。无论选哪一边，都应拆出 pending `ExecutionConfirmationRequest` 与 immutable `PlanConfirmationDecision`，不要让“已确认记录”承载等待期 TTL。

#### BLOCK-03：Interrupt 声称校验 revision，却没有携带 revision/run/step；同时把所有 interrupt 强制设为可过期

- **位置**：§27.6（行 1259–1291）、§5.1（行 262–268）、§14.4（行 684–686）。
- **证据**：行 1266 要求校验 `interruptId / revision / schema / expiry`，但 `InterruptPayload` 与 resume 合同（行 1273–1283）没有 `revision`、`runId`、`workflowId` 或 `step`。既有 D-169① 要求 resume 三元组 `runId + step + resumeData`（决策日志行 3420–3423），当前 `QuestionCard` 也带 `workflowRevision`（`packages/contracts/src/harness.ts:314-319`）。此外 `expiresAt` 被定义为必填，撞 §5.1/D-169① 的“不做载体层挂起过期”；只有付费确认 hold 才有 D-153 业务期限。
- **建议修法**：协议至少加入 `{threadId, runId, workflowId, step, interruptId, revision, schemaVersion}`，resume 回传 `{interruptId, revision, decision}`，服务端做 CAS/actor/workspace 校验。`expiresAt` 改为可选并注明只有业务规则本身有期限时出现；普通 `ask_merchant` 不得因载体 TTL 失效。

#### BLOCK-04：HarnessRelease 的 identity 不可重建——同一对象同时 immutable、内嵌可变 rollout、允许 override 越过 pin

- **位置**：§29.4（行 1390–1432）、§33.1（行 1491–1507）、§42（行 1788–1794）、§43.8（行 1807）。
- **证据**：`HarnessRelease` 类型内含可变 `status` 与 `rollout`，行 1430/1507 又规定 release immutable、rollout 单独变更，并另建 `p1_harness_release_rollouts`。更严重的是行 1432 写“per-run overrides > release pin”，而 `AgentRun` 只记录 `harnessReleaseId`（行 459–470）；如果 override 是字段级覆写，同一 releaseId 对应多个有效 manifest，违反 exact release、trace 还原和回滚承诺。
- **建议修法**：拆为不可变 `HarnessReleaseArtifact`（所有 exact bindings + manifestHash）、独立 `HarnessReleaseLifecycle/Approval`、独立 `HarnessReleaseRollout`。试跑只能“选择另一个完整 candidate releaseId”，不得在同一 release 上覆写字段；若确需字段 override，必须生成新的 immutable effective release 或持久化完整 effective manifest/hash 并用其作为运行 identity。

#### BLOCK-05：Prompt Pack 漏掉 22 个注册 key 中两个仍有真实消费者的 key

- **位置**：§29.1–29.3（行 1360–1388）、批次 5（行 1627–1634）。
- **证据**：正文 pack 合集只有 20 个唯一 key，漏了 `briefImage` 与 `xhsNoteGen`。当前 registry 明确是 22 键（`apps/core/src/p1/harness/langfuse-prompts.ts:22-32,36-151,156-189`）；`briefImage` 被 `production-stage-ports.ts:1109`、`unified-media-stage-ports.ts:276` 使用，`xhsNoteGen` 被 `note-plan-structured-port.ts:116,164-166` 与 `unified-media-stage-ports.ts:1040-1041` 使用。按正文实现会让真实 image/note 路径没有被 release pack pin 覆盖，直接破坏 R14/D-166④ 的 strict 供给纪律。
- **建议修法**：补齐依赖归属（例如 `briefImage` 进 media/image pack，`xhsNoteGen` 进 note pack），并加构造性测试：所有可达 prompt consumer 的 key 必须被至少一个 pack 覆盖；每种 carrier 的编译依赖集必须 exact；未覆盖 key 使 release 发布失败，不得回 builtin 假绿。

#### BLOCK-06：`boundedRetry` 的默认策略直接撞 accepted D-167“默认关”

- **位置**：§22.2（行 1032–1061）、附录 A6（行 1854）。
- **证据**：正文把每个 unit 的 `retryOn` 固定为 `transient_only`，边界又称“保守默认：连接类/5xx 自动重试”。D-167③（决策日志行 3359–3361）明确是“默认关；三层重试不得叠乘；未知错误默认不重试”。当前文档也没有说明 429、timeout、provider `accepted/acceptance_unknown`、幂等能力和最大 wall clock 如何进入 predicate；若照正文默认开，会在媒体供应方已受理但响应未知时重复烧钱。
- **建议修法**：默认改为 `disabled`；只有 execution unit 明确证明请求幂等、provider 未受理且错误码在发布过的 retry predicate 中时才开启。把 `retryOn` 改成 versioned predicate ref/闭集错误类，并显式排除 validation、contract、rights、billing、accepted、acceptance_unknown。与 SDK/tool/DBOS 三层做“唯一重试属主”测试。

#### BLOCK-07：`MarketingPlanRevision` 一方面 immutable/append-only，一方面又要求原行生命周期变更

- **位置**：§13（行 585–629）、§33.1 写入纪律（行 1505–1507）、§37.2（行 1684–1686）。
- **证据**：`status` 含 `compiling/compiled/confirmed/cancelled/superseded`，这些都要求状态迁移；同节又写“revision 本身 append-only 不可变”，§33.1 再写 Plan revision append-only。若更新同一行，破坏 immutable；若每次状态变化增加 plan revision，则“确认”这种外部事件会改 plan content identity，并与单独的 ConfirmationRecord 重复拥有确认真相。R6 本来要消除派生态写回，但合并后仍留下第二 writer。
- **建议修法**：PlanRevision 只保存不可变内容和 `created` 事实，不放可变 lifecycle status；编译失败/取消/确认/supersede 由独立 append-only event/confirmation record + projection 计算。若保留状态，必须定义 `(planId, revision, stateRevision)` 事件模型，禁止 UPDATE，并说明确认权威只有哪一个对象。

#### BLOCK-08：D2/D3 的“后置”裁决被 PR 表和发布绝对门重新拉回批次 5

- **位置**：§31.3（行 1472–1477）、批次 5（行 1627–1634）、§36 V31-23（行 1668–1673）、§42（行 1790–1793）、§43.9（行 1808）。
- **证据**：§31.3 与批次 5 文字说 L2/L3 仅在“历史任务数百级”后建设，试点只做 allowlist + 人工回滚；但 V31-23 仍写“Eval L2-L4 通路，批次 5”，§43.9 又把 replay 无副作用设为无条件全量发布门，§42 还写“canary 自动暂停”。实施者无法判断是本批建设、只留 backlog，还是未建设却必须验收；这正是 D2/D3 要消除的过早机器。
- **建议修法**：V31-23 改成 “L0/L0.5/L1 + allowlist L4 + 人工回滚演练”；L2/L3 与自动回滚拆成 trigger-bound backlog，不分配批次/PR 号。§43.9 改为“任何已启用的 replay/shadow 均不得有生产副作用”，§42 试点期改成人工暂停；触发点满足后再新增发布门。

#### BLOCK-09：Level 3 一个 Plan 派生 N 个 Work，但未来付费 Work 的授权与预扣粒度完全未定义

- **位置**：§3 Level 3（行 202–206）、§11（行 477–498）、§14（行 631–686）、§25（行 1136–1161）、批次 6（行 1636–1643）。
- **证据**：正文只说“一个 Plan 派生多个 Work”和“含付费媒体确认一次”，没有说明该确认是只批准计划、批准首个 Work，还是预授权未来几周的所有付费执行；quote/rights/facts 会在各 Work 启动前变化，D-153 hold 也只有 1h–30d 有效。若一次确认授权 N 次未来扣费，会造成未再次知情的付费副作用；若每个 Work 都重确认，当前“确认一次”承诺不成立。
- **建议修法**：升级为用户决策。建议 campaign 确认只批准计划/排期，不预授权未来扣费；每个实际付费 Work 在 exact quote/rights/facts 冻结后单独流内确认。允许纯 copy Work 按 policy exemption 自动执行。合同加入 `campaignPlanRef/workOrdinal/approvalScope`。

### MAJOR

#### MAJOR-01：A1 只落了文字，HarnessRelease 类型和伪代码都没有真正 pin/执行 middleware 顺序

- **位置**：§20.4（行 913–922）、§21.4（行 971–1007）、§29.4（行 1392–1425）。
- **证据**：§20.4 要求 before/after/wrap 顺序 pin 进 release，但 `HarnessRelease` 没有 middleware 列表、kind、order 或可执行控制动作字段。§21.4 仍直接 `streamText({tools: toolRegistry.forPhase(...)})`，turn 末才 `agentPolicy.evaluate`，没有展示 before/after/wrap_tool_call，也没有按 workspace/rights 裁剪 active tools。A1 的核心目的——每次 tool call 前确定性拦截——仍可能被实现成旧的 turn 后置链。
- **建议修法**：加入 `middlewareBindings: Array<{policyId, revision, kind, order, allowedControlActions}>`，resolver 输出 exact composition；伪代码必须通过统一 middleware runner 包裹 model/tool call，并让 `activeTools` 来自 server-owned capability/policy 裁剪，不从输入信任。

#### MAJOR-02：Semantic Event 合同漏掉正文刚新增的 `context_role`，且 `bigint` 没有 wire 表达

- **位置**：§27.1–27.2（行 1201–1227）。
- **证据**：行 1207 明说 semantic event 增加 `context_role: included|excluded|summarized`，紧接着的 `AgentSemanticEvent` 接口却没有此字段。`streamOffset: bigint` 也不能直接 JSON/SSE 序列化，而 envelope 未规定 string/number 转换。B2 的 `transient:true` 只有叙述，没有对应 ephemeral wire schema。
- **建议修法**：在 canonical TS/domain schema与 wire schema 分开定义；wire offset 用 decimal string，明确比较/游标规则；补 `contextRole`。为 ephemeral frame 定义 `transient: true`，并加 round-trip、乱序、重复、跨 thread 隔离测试。

#### MAJOR-03：AgentRun durability 只有一个字段，没有定义 Session→Make 的升级/分裂语义

- **位置**：§10（行 455–475）、§21（行 924–1010）、§27.6（行 1259–1291）、§32（行 1481–1487）。
- **证据**：`exit` 被解释为轮末落一次，含付费执行恒 `sync`；但正文未说明同一个 AgentRun 是否从 `exit` 原地升级为 `sync`，还是创建 child run/DBOS workflow。§21 的运行伪代码没有任何 AgentRun persistence/durability 分支，§27 又让 DBOS 持有 pending interrupt。发生确认、重连和 handoff 时无法确定 run identity、parentRunId 和 exact trace 的边界。
- **建议修法**：明确推荐模型：Session turn 是 `exit` AgentRun；handoff 后创建 `sync` child AgentRun（或只创建 DBOS execution run）并通过 `parentRunId + workflowId + snapshotHash` 关联，durability 创建后不可变。列出各持久化点与 crash 窗口测试。

#### MAJOR-04：§38 第 6 条硬门既未拍板又从 §43 的“绝对门”中消失

- **位置**：§38（行 1706–1735）、§43（行 1796–1817）、附录 B2（行 1870）。
- **证据**：§38 把“交付后 7 日自报覆盖率 ≥40%”列为不达不放行的硬门；附录 B2 又把 evidence 覆盖率阈值列为待用户拍板；§43 的 18 条发布绝对门没有这条。一个阈值不能同时是未决参数、硬门和非绝对门。
- **建议修法**：拍板前标为 provisional observation，不得阻断发布；用户决定后，§38、§43、批次退出门和测试数据窗口四处用同一命名/分母/样本下限。建议首个试点窗只观测，形成基线后再升硬门。

#### MAJOR-05：Memory 方案 (b) 仍待决，却已被正文和“最终清单”当成既定实现

- **位置**：§12.5（行 552–575）、§33.1（行 1491–1505）、Memory 并行 lane（行 1617–1625）、附录 B5（行 1873）。
- **证据**：标题明确“待附录 B-5 拍板确认”，但正文随即用强制语气“不另起新表”，§33.1 称“最终清单”，批次也直接按 preference 扩列开工。更深一层，working memory 是有界全量重写，而 preference 三表是 candidate/promotion/head 语义；把 working/procedure 都塞进同一扩列方案是否成立尚未验证。
- **建议修法**：决策前把 §33/§35 改为 option-dependent。建议采用混合方案：preference/correction 延续现有三表；working 放 Thread summary/checkpoint；procedure 如需持久化再评估独立 confirmed projection。不要为了“少一张表”混掉不同生命周期。

#### MAJOR-06：B1 的 HITL 重发现只落了 thread 端点，丢了 resource/workspace 级恢复入口

- **位置**：§27.6 行 1287；框架评审 B1（评审行 86）。
- **证据**：原裁决要求按 `threadId/resourceId` 列挂起审批，使刷新、换设备和未知 runId 场景可恢复；正文只有 threadId。用户从首页恢复时可能还不知道具体 thread，运营/移动端也需要按当前 workspace/resource 拉全部待处理项。
- **建议修法**：提供 workspace-authenticated `listPendingInterrupts({resourceId, threadId?})`；threadId 是过滤条件，不是唯一入口。返回前做 actor/RBAC/tenant 校验，禁止仅凭可猜 threadId 读取 payload。

#### MAJOR-07：CompiledExecutionPlan 的“零代码扩展”与“代码注册表加一项”自相矛盾，缓存边界也不足以安全开票

- **位置**：§16.1（行 715–729）、§22.2（行 1032–1061）、附录 A8（行 1856）。
- **证据**：行 1057 同一句先说 `ExecutionUnit` 类型要“代码注册表加一项”，再说“新增输出类型零代码改动”；附录又把“零代码改动”列硬门。可成立的应是“执行引擎核心零改动”，不是全系统零代码。`cachePolicies` 只有 TTL，正文虽说 key 含 input hash/releaseId，却没含 workspace/data classification、tool/policy revision、rights/fact freshness，存在跨租户或 stale rights 命中风险。
- **建议修法**：把约束精确改成“新增 carrier/recipe 不改六原语与 executor 核心；新增 execution-unit type 仍需注册、schema、policy 与测试”。CachePolicy 至少声明 scope、read/write mode、key schema revision、workspace isolation、fact/rights revision dependencies；含敏感素材/权利/外部副作用的 unit 默认不可缓存。

#### MAJOR-08：§35/§36/§41 的 flag 与 kill switch 批次仍未对齐

- **位置**：批次 2/3/4/5（行 1588–1634）、§36（行 1645–1674）、§41（行 1761–1786）。
- **证据**：PlanCompiler/CompiledExecutionPlan 在批次 2 产生，但 `compiled_execution_plan_v1` 标批次 3；`force_manual_plan_confirmation` 标批次 2，而确认卡在批次 3；新 Make 消费从批次 3 开始，`force_legacy_five_stage` 却到批次 5+ 才出现；批次 4 的 steering 没有对应 `disable_make_steering`，与 D6 的“steering 随所属批次引入”漏落。§36 也没有把这些开关的创建/删除责任绑定到具体票。
- **建议修法**：建立唯一开关矩阵，列 `owner PR / introduced / first effective / fallback / delete condition`；其余三处只引用矩阵。建议 compiled-plan 生产与消费分两个 flag 或明确现 flag 只控制消费；manual confirmation/legacy Make 在批次 3 生效；steering 在批次 4有 kill switch。

#### MAJOR-10：附录 A 没有完整承接 §0.4 自己列出的硬约束，且 A15 来源指针不可审计

- **位置**：§0.4 行 87；附录 A（行 1843–1863）。
