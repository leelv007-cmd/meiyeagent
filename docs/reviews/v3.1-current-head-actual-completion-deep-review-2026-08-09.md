## 二、必须先处理的阻断问题

### P0-1 跨 workspace 确认操作（安全）

确认 `decide/expire` HTTP 路由只鉴权 URL 中的 workspace，随后仅按全局 `requestId` 调 service；service 不接收也不校验对象所属 workspace。普通已登录成员可通过 Web BFF 构造请求，若获知另一 workspace 的 requestId，可决定或过期对方请求并触发对方积分退款。

- Web BFF：`mkfast-template-main/src/routes/api/core/p1/confirmation-requests/$requestId/decide.ts:6-20`
- Core route：`apps/core/src/server.ts:2339-2360,2388-2408`
- Service：`apps/core/src/p1/agent-session/execution-confirmation-service.ts:309-318,386-425`

建议：command 输入必须带 authoritative workspaceId；查询使用 `(workspaceId, requestId)`；service 内再次校验 ownership；补 foreign-workspace decide/expire 负向测试。

### P0-2 确认 decision/status/refund 非原子，重放会谎报已退款

拒绝链顺序为 append decision → mark status → refund，三步不是同一事务。append 后崩溃时，重试进入 prior-decision 分支，不再补 status/refund，却直接返回全部 `refundedCredits` 和“已退”文案。

- `apps/core/src/p1/agent-session/execution-confirmation-service.ts:335-370`

建议：把 request、immutable decision、ledger refund 放进 workspace credit transaction；为每个 crash point 写恢复测试，重放必须修复未完成步骤而非只返回 prior。

### P0-3 paid snapshot 与 confirmation request 循环依赖，V31-11/12/14 主链不可达

task admission 只为 `policy_exempt_copy` 组装 snapshot；付费 `merchant_confirmed` freeze 被忽略。confirmation gate 又要求先有 `executionPlanSnapshot` 才 createRequest，而 snapshot admission 需要 `confirmationDecisionRef`。结果形成 `decision → snapshot → request → decision` 的环，付费任务仍走 legacy。

- `apps/core/src/p1/harness/task-admission.ts:422-461`
- `apps/core/src/p1/harness/paid-generation-confirmation.ts:178-196,221-245`
- `apps/core/src/p1/harness/execution-plan-admission.ts:544-567`

同时 UI interaction requestId 与 domain requestId 不一致；domain decide 失败后 Web fallback 到 interaction-only resume，构成付费执行 fail-open：`mkfast-template-main/src/product/composer/use-composer-interactions.ts:279-303`。

建议：重新确定唯一确认状态机与唯一 requestId；正确顺序为 plan finalize → 原子 reserve + pending request → merchant decision → immutable decisionRef → snapshot admission → Make。删除失败后的付费 fallback。

### P0-4 Prompt Pack 和 HarnessRelease 形成双真相

生产 admission 仍全量 resolve 22 prompts，未按任务选择 pack；fresh boot 又用空 `promptBindings/promptPackBindings` 自动发布 production release，利用 validator 的空集合漏洞通过 strict gate，运行时实际 prompt 继续从 env 解析。

- full resolve：`apps/core/src/p1/harness/task-admission.ts:410-416`、`langfuse-prompts.ts:667`
- 空 bootstrap：`apps/core/src/p1/harness/harness-release.ts:109-170`
- 空集合校验通过：`apps/core/src/p1/harness/prompt-packs.ts:186-267`
- 自动 promotion：`apps/core/src/assembly/core-assembly.ts:467-484`

这破坏 exact release、rollback 和 eval attribution。建议禁止空 pack production release；从显式 seed manifest 冻结 exact pins；admission 按 carrier/task 选择 pack 并只解析 release 中的 exact version。

### P0-5 Artifact 写入错误 Thread，真实 Workbench 看不到

note/video producer 把 `executionPlanSnapshot.planId` 写进 semantic event 的 `threadId`；Composer 的 threadId 与 planId 明确不同，Workbench 订阅真实 Thread，Artifact 事件因此进入错误流。

- 错误写入：`apps/core/src/p1/harness/workflow-core.ts:2249-2254,2514-2519`
- ID 明确不同：`apps/core/src/p1/agent-session/composer-plan-session.ts:68-72,302-317`

生产 emitter 还只发 delta，没有 canonical snapshot producer；跳 revision 后的 fallback 测试 snapshot 是手造 fixture。

### P0-6 Memory 注入使用进程级可变全局，可能跨请求串租户

`memoryInjectionTurnBridge.current` 是模块单例。并发 turn 在 await 期间会互相覆盖 binding，使 receipt 记到错误 task/run/release，甚至跨 workspace。

- `apps/core/src/p1/agent-session/context-retrieval.ts:114-128`
- `apps/core/src/p1/agent-session/turn-runner.ts:523-559`

建议改用 AsyncLocalStorage 或显式参数传递，并补两个 workspace 并发交错测试。

### P0-7 Eval L0.5 使用合成 trace，生产 verdict 可假绿

Make 完成点无法看到真实 tool chain，于是自行合成 `read_context/generate/record`，再排除关键 assertions，并将 rights/redline synthetic gates 强制写为 passed。

- `apps/core/src/p1/harness/dbos-workflow.ts:1645-1718`
- `apps/core/src/p1/eval/production-sampling.ts:67-96`

没有可观察事实时应记 `not_evaluated`，不能制造 passed；应从真实 Session/Make trace 取数。

### P0-8 V31-25 六原语化未发生

Compiled carrier 的 units 只是 plan/trace 数据，executor 仍直接调用旧 copy/note/media program；测试源码也承认六原语重写未落地。

- `apps/core/src/p1/harness/runner-convergence.test.ts:193-209`
- `apps/core/src/p1/harness/workflow-core.ts:1395-1426`
- `apps/core/src/p1/harness/compiled-carrier-executor.ts:128-153`

因此票面“先六原语化 → 单 executor”未完成。应把 executor 真正改为解释 typed units 的六原语执行器，并用旧版本真实导出 fixture 做 before/after 对照。

### S2：修复生产权威与恢复

### S4：重写验收证据
