# V3.1 专项评审：产品优先 × 落地效率 × 框架对标 × 冗余识别

**日期**：2026-08-08
**对象**：`docs/design/0808规划/meiye-agent-v3.1-authoritative-plan-2026-08-08.md`
**评审问题**：① 功能调整是否符合功能及产品优先原则；② 实施落地是否简洁高效可维护；③ Mastra / pi.dev / LangChain 及其他成熟框架还有哪些可借鉴；④ 有哪些过早的无效兜底或冗余设计。
**对标输入**：三个独立 opus 研究 agent 实查——Mastra `@mastra/core@1.57.0`（2026-08-05 发布，含 Goals/Background tasks/Observational Memory/gates-verdicts/state signals）；pi.dev（badlogic 的极简 harness，`0.84.1`，2026-08-07 更新）；LangChain/LangGraph 1.x（langgraph py 1.2.10 / JS 1.4.8）+ OpenAI Agents SDK + Anthropic agent 工程指导。原始文档在 scratchpad，关键结论均带来源 URL。

---

## 0. 总判断

- **Q1（产品优先）**：V3.1 的功能调整**主体符合**产品优先原则——分级流程、Thread 连续、自报旅程、Goal 去管理面化都是直接的用户价值；三大框架对标**全部验证了核心架构方向**（控制流在代码不做 DSL、HITL 一等原语、跨线程记忆与线程状态分离、确定性代码与 LLM 混编）。残余问题是批次 5 的平台设施仍按「规模化形态」一次建满，与试点期规模不匹配（见 Q4）。
- **Q2（简洁高效可维护）**：合格但有一个结构性缺口——**policy 链只有 turn 级一个后置挂点**，缺 per-tool-call 级拦截与可组合的中间件序，这是三个框架一致收敛出的形态，不补会让批次 2-3 的门禁代码散落在各服务里。
- **Q3（借鉴）**：共 17 条可采纳，分三级：A 级 7 条建议直接修入 V3.1 合同；B 级 6 条进实施纪律；C 级 4 条记录备用。
- **Q4（冗余/过早兜底）**：识别 9 处，集中在批次 5 的灰度/评估机器（percentage rollout、L2/L3 全层、自动回滚门）和一次性建满的开关矩阵——处置原则沿用「验证期用最快栈、基建绑定触发点」：**功能不砍，时点后移、绑定触发条件**。

## 1. Q1：功能调整的产品优先判定（逐项）

| V3.1 调整 | 判定 | 依据 |
|---|---|---|
| 分级创作流程（Level 0-3，纯 copy 免确认） | ✅ 产品优先 | 摩擦只留在计费/权利真实需要处；确认门=计费门不是流程仪式 |
| Thread≠Work、Delivered 后继续同一 Thread | ✅ 产品优先 | 直接用户价值；Mastra thread/resource 二元同构验证 |
| Goal 去管理面化（Agent 提议、确认才建） | ✅ 产品优先 | 避免给非技术商家造「目标管理」负担；Mastra Goals 也是 thread-scoped 挂载 |
| Memory 双通道（session 内即时生效+跨会话候选确认） | ✅ 产品优先，一处需校准 | Mastra Observational Memory 证明 **working 类=上下文压缩不是承诺**，V3.1 §12.2 已定 working 自动维护无门——口径一致；校准点：working 的实现应走「后台压缩+有界重写」而非确认流（见 A6） |
| 商家自报旅程 + Proactive evidence 门 | ✅✅ 最强的产品优先项 | 闭环燃料从 schema 问题改成旅程问题 |
| plan-as-data（否决 grammar 解释器） | ✅ 产品优先（支撑「所见即所执行」承诺） | **三框架一致背书**：Mastra「control logic lives in the workflow itself」；pi「状态外置成数据不内置成 harness feature」；LangGraph Deep Agents 的 todo 也是结构化数据非解释器 |
| 双 Harness + ApprovedPlanSnapshot 冻结交接 | ✅ 产品必需 | pi 研究反面验证：pi 的「无权限系统、事后可观测」只在损失边界=开发者自己机器时成立；我们是非技术用户+真金白银副作用，**事前闸门是产品必需不是虚假安全感**。OpenAI handoff input_filter 同构 |
| Memory 注入透明化 | ⚠️ 需补一条产品功能 | pi 哲学「上下文注入必须用户可见」：商家须能在「经验」页看到**本次生成注入了哪些记忆**，否则会遇到「AI 记住了我没说过的事」的信任事故。V3.1 只有记忆的查看/撤销，缺**逐次注入清单**（建议补进 §12/§39） |
| 批次 5 平台设施（release/eval/控制面） | ⚠️ 方向对、形态超前 | 见 Q4-D1/D2/D3 |

**结论**：功能面无需回退任何调整；需补 1 项（记忆注入透明化）、校准 1 项（working memory 实现形态）。

## 2. Q2：落地方式的简洁高效可维护判定

### 2.1 已经做对的（对标确认）

- plan-as-data + DBOS TS 控制流 = 三框架收敛共识，无解释器负债；
- 收编现有 preference 三表而非新表 = 避免双真相；
- 砍半控制面 + Langfuse 承载展示 = LangChain 1.0 自己也在做减法（chains/AgentExecutor 全移出核心）；
- 无双写过渡期、事件基于现有三帧扩展 = 迁移面最小化；
- 「eval 证明才加 specialist」= Anthropic 多 agent 15× token 成本警告的正确姿势；
- 上下文预算 + 不给全量 transcript = context rot（注意力稀释）指导的正确姿势。

### 2.2 结构性缺口：policy 挂点形态（本评审最重要的工程发现）

V3.1 的策略执行只有一个挂点：turn 结束后对 `AgentTurnDecision` 跑 `Zod parse → 7 层 policy 链`（§19.1）。三个框架一致收敛出**两类钩子 + per-call 拦截**的形态，不补的后果是批次 2-3 的门禁代码会以 if-else 散落在 service/tool 实现里，每加一条门改 N 处：

1. **node 式钩子**（before_model/after_model，返回状态补丁）：承载计数、限额、上下文注入——对应我们的 question budget、AgentControlLimits、Memory 注入；
2. **wrap 式钩子**（洋葱包裹 model/tool 调用）：承载重试、降级、超时——对应我们的 model fallback、structured repair；
3. **`wrap_tool_call` per-call 确定性拦截**：租户/权利/配额门在工具调用前拦截，**返回模型可见的拒绝理由**（pi 的 `block:true, reason` 同构）——比「工具不存在」或抛异常炸轮次的行为好得多：模型收到 reason 会改走 ask_merchant，而不是胡乱重试；
4. **控制动作静态声明**（LangChain `can_jump_to`）：每条 policy 注册时声明有权做哪些控制动作（继续/终止本轮/退回提问），受限枚举、可审计——**不开放任意跳转**（我们控制流在 DBOS 代码里，这条边界必须保住）；
5. **钩子执行序 pin 进 HarnessRelease**（before 正序/after 逆序/wrap 嵌套），否则 policy 顺序漂移在 release diff 里不可见。

### 2.3 其余可维护性改进（并入 Q3 采纳清单）

- Interrupt payload 类型化协议 + **稳定 id 回注**（LangGraph 位置索引错位是反面教材；我们依赖分组天然产生同批多待审）；
- `AgentRun.durability: 'exit' | 'sync'` 显式分级：只读会话轮 exit（轮末落盘一次），付费执行恒 sync——省 Session Harness 的持久化开销且差异可解释；
- execution unit 级 RetryPolicy 声明，**照抄保守默认：绝不重试校验/合同类错误**（防止把确定性门失败当瞬时故障烧钱重试）；
- unit 级 CachePolicy，**cache key 必须含 harnessReleaseId**（防 prompt 改版吃旧缓存）；
- semantic event 加 `context_role: included | excluded | summarized` 字段（pi 的 entry 级标注）：把「事件持久化」与「上下文构建」彻底解耦，不让 semantic/ephemeral 分层兼职这件事。

### C 级：记录备用（4 条，出现触发条件再做）

- **state signals（snapshot/delta + cacheKey 幂等 context lanes）**：ContextBundle 从每轮全量重算改为命名 lane 增量——token 优化项，等上下文成本可测后做（Mastra signals）；
- **background tasks + untilIdle**：会话内派发长任务不阻塞对话、完成后回灌同一条流；`perAgentConcurrency + backpressure:'queue'` 是商户级限流现成语义——批次 4 后按需（Mastra）；
- **per-run release 覆写**：`resolve(release, { overrides })` 沿委派链传播，给单商户/单 thread 试 draft 不需要全局切换——与 D1 一起处理（Mastra editor versioning）；
- **虚拟文件系统式大结果卸载**（StoreBackend 形态、按租户命名空间）：素材检索/竞品结果写「文件」、上下文只留句柄——等检索结果膨胀触发（Deep Agents）。

### 反向确认：三框架一致警告、V3.1 已经躲开的坑

- 不引入 LangGraph/Mastra 运行时本身（checkpointer 与 DBOS = 两套持久化真相；Mastra recovery 明文会重发 LLM 调用与工具真实成本）——「借语义不借运行时」成立；
- 不做 DSL/grammar（三家都没做）；不做 council 原语（Mastra 明说让你自己拼 parallel）；
- Store 写即嵌入不可默认开（跨会话确认门之前不得生成向量副本，`index=False` 为默认）；
- 工具可用性裁剪必须留在确定性门里，模型只在已裁剪集合内选（LLMToolSelector 式「模型挑工具」在我们场景违反租户/权利约束）；
- pi 的「无权限/无沙箱/YOLO+事后可观测」整套安全假设不可移植（前提是损失边界=操作者自己的机器）。

## 4. Q4：过早的无效兜底与冗余设计（9 处）

处置原则：**功能不砍、时点后移、绑定触发条件**（承接「验证期用最快栈，合规/基建绑定触发点」的既有反馈；不是 MVP 式砍残，是排期语义）。

| # | 现文 | 判定 | 处置 |
|---|---|---|---|
| D1 | §31.3 canary「5%→25%→50%→100%」percentage rollout + industry allowlist（批次 5） | **过早**：试点期 workspace 个位数，百分比灰度无统计意义 | 首发只做 **workspace allowlist + per-run release 覆写**（C 级借鉴）；percentage 机器绑定触发点「付费 workspace ≥ 50」 |
| D2 | §31.3 L2 Journey Replay + L3 Shadow 完整通路（批次 5） | **过早**：无真实流量时 replay/shadow 语料≈0，通路建成即闲置 | L0/L1 + A4 Quick Checks + allowlist canary 先行；L2/L3 绑定触发点「历史任务 ≥ 数百量级」；建时必须带 B4 只读闸 |
| D3 | §31.3 自动回滚门 7 条监测 | **过早兜底**：依赖指标管道成熟度，试点期误触发比漏触发更伤 | 试点期=人工回滚 + kill switch + 回滚**演练**保留；自动化门绑定触发点「L4 指标管道稳定运行一个月」 |
| D4 | §38 SLO 表 20+ 指标全量作为试点目标 | **冗余**：测量基建成本高，且多数指标试点期无基线 | 拆两层：**硬门 6 条**（billing/rights 错误=0、fidelity=100%、duplicate=0、interrupt 丢失=0、Day-0 可达、自报覆盖率）进验收；其余降为观测指标不设门 |
| D5 | §7.3「将来可替换 OpenAIAgentsKernel/MastraAgentKernel」 | **投机叙事**：kernel 替换=全量回归，承诺可替换性没有消费者 | port 保留但收窄表述：**只为测试隔离与 AI SDK 大版本升级服务**，不承诺跨框架可替换 |
| D6 | §41.2 八个 kill switch 一次建满 | **过早**：`force_legacy_five_stage` 在批次 5 前无对象；`disable_specialist_agents` 与 `disable_agent_planning` 部分重叠 | switch 随批次引入（批次 1：memory 读写两个；批次 2：planning；批次 4：steering/proactive；批次 5：legacy 强制） |
| D7 | §41.1 十个 feature flag × 四声明字段一次定义 | 同 D6 | 声明纪律保留，flag 随批次开；文档标注每个 flag 的引入批次 |
| D8 | §23.2 shadow 对账（已砍到确定性字段+10% 抽样） | **残余冗余** | 保留但加硬时间盒：连续 2-4 周 deterministic-field mismatch=0 即提前关闭，不陪跑到批次 5 |
| D9 | §15 Capability 四分模型的**正式注册表** | **过早**：起步 Recipe/Skill/Tool 已够表达，Capability 注册表当前无消费者（商家能力目录尚不存在） | Capability 保留为**文档分类概念**；注册表实体绑定触发点「商家可见能力目录/商店」需求出现 |

**明确不算冗余的**（反向复核过）：双 Harness、ApprovedPlanSnapshot、PlanConfirmationRecord、semantic events outbox（跨 workflow 的 thread 级 replay 无法用 DBOS streams 替代）、七层 policy 链本体、D-153/计费原子性承接、附录 A 全表——这些对应真实计费/权利风险，是产品必需的复杂度。pi 研究的结论反向适用：**HarnessRelease 的 exact pin 是我们比极简派多出来的必要复杂度**（pi 连 prompt 版本化都没有，但它也不需要为别人的钱负责）。
