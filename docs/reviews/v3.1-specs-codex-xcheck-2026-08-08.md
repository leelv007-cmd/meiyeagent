# V3.1 九张开发 Spec 独立交叉复核（Codex，反驳立场）

**复核日期**：2026-08-08  
**复核对象**：V3.1-A～I 九张 spec（A～G 为 #429～#435 本地票面快照，H/I 待发布）  
**权威基线**：`docs/design/0808规划/meiye-agent-v3.1-authoritative-plan-2026-08-08.md`（下称 V3.1）

## 1. 总判断

九张 spec **方向覆盖广，但目前不能直接作为彼此独立、可并行开工的完整任务书**。主要产品裁决（纯 copy 免确认、确认前 reserve、两路径都冻结、Memory 双通道、release 三对象、人工 canary、商家自发发布）没有整体性倒退；阻塞点在实施合同：B 实际消费 G 而 G 又依赖 B/C，确认前 `snapshotHash` 与确认后才出现的 `confirmationDecisionRef` 无法同时保持快照不可变，A 缺 `sessionRevision` 与 sync child run 的持久关联字段，B/E 同时认领 Thread checkpoint writer，F 的 Opportunity 接受/忽略没有 canonical owner。覆盖层面还漏掉附录 A17 硬门，Recipe/Skill registry、Controlled Surface 总 owner、基线/试点/运行模式验收也只有权威正文、没有票面 owner。结论是：**先清零 8 个 BLOCK、补齐 15 个 MAJOR 的 owner/合同/验收，并拍板 3 个仍影响合同或放行的事项；之后 A→B→C→D 主线才可开工，E 可恢复为真正并行 lane，G 应拆出前置 release-contract slice，H/I 只在各自集成前置门满足后开工。**

严重度统计：**BLOCK 8 / MAJOR 15 / MINOR 4**。

## 3. Findings

### BLOCK

#### BLOCK-01：B 消费 G 的 release 合同，而 G 又硬依赖 B/C，形成开工循环

- **Spec/位置**：B `:29,34,58,62`；G `:5,20,27,36`；C `:36,53`。
- **证据**：B 要求 middleware 顺序随 release pin、limits 随 release 发布，并明确 `promptPack.resolveExact` “按 G 的合同消费”；G 却声明依赖 B/C。C 也冻结 `releaseId/prompt/skill/bounds`，但把 HarnessRelease 装配排除到 G。即使 A 先放了 branded release ID，也没有 `ResolvedHarnessRelease`、pack resolver、middleware composition、control limits 的可执行 bootstrap 合同。
- **影响**：按 issue blocker 执行时 B 不能完成 production path，G 也不能开工；测试只能各自造不兼容 stub。
- **建议修法**：从 G 拆一个依赖 A 的 **G0 release-contract/resolver slice**（artifact schema、resolved release、prompt pack resolver、middleware bindings、limits binding）；B/C 依赖 G0。G 剩余 publish/eval/rollout 可依赖 B/C 做集成验收。若不拆票，则删除 G 对 B/C 的开工依赖，改为“实现依赖 A，集成验收依赖 B/C”。

#### BLOCK-02：确认前 request 需要 `snapshotHash`，但票面又在确认后才冻结并把 decision ref 放进 immutable snapshot

- **Spec/位置**：C `:13,36-37`；V3.1 `:653-678,681-712`。
- **证据**：C Solution 写“含付费媒体=商家确认后冻结”；`ExecutionConfirmationRequest` 在确认前创建却必须保存 `snapshotHash`；`ExecutionPlanSnapshot` 的 `approvalBasis=merchant_confirmed` 又要求 `confirmationDecisionRef` 必填。决定在请求之后才存在。若补入 ref，snapshot 与 hash 发生变化；若不补，违反必填合同。
- **影响**：无法同时满足 request 锚定、快照不可变、hash 稳定和确认决定可追溯；不同实现会产生两套 hash 口径。
- **建议修法**：推荐先冻结不含决定的 immutable execution content，request 引用其 `snapshotHash`；决定继续是独立 immutable 对象；Make admission 使用 `{snapshotRef, decisionRef}` 的不可变 envelope 校验二者，不修改 snapshot。若坚持 decision ref 在 snapshot 内，则必须拆 `ExecutionPlanCandidate` 与 `ApprovedExecutionAdmission` 两个对象并分别 hash，禁止原地补字段。

#### BLOCK-03：U6 要求的 `sessionRevision` 没有 canonical owner 或持久字段

- **Spec/位置**：A `:22,47`；V3.1 `AgentThread :439-451`、`AgentTurnInput :828-844`、U6 `:1949`。
- **证据**：票面要求 `sessionRevision` OCC + 第二写 turn 返回 409，但 AgentThread 只有 `summaryRevision`；A/B 都没有说明 session revision 存在哪张表、何时递增、活跃 turn lease/唯一约束、409 返回哪一个 current revision。
- **影响**：#429 无法实现可证明的单活跃写 turn；把 `summaryRevision` 误作 session revision 会把摘要更新与并发仲裁耦合。
- **建议修法**：在 AgentThread 或唯一 Session repository 定义独立 `sessionRevision` 与 active-write-turn 原子 CAS 合同；列创建/提交/结束/crash recovery 的递增规则、数据库唯一约束、409 payload 和双端测试。

#### BLOCK-04：A 声称 sync child run 经 `workflowId + snapshotHash` 关联，但 AgentRun 合同没有这些字段或关联实体

- **Spec/位置**：A `:29,36,43`；V3.1 `AgentRun :462-480`。
- **证据**：`AgentRun` 仅含 `parentRunId` 与 `harnessReleaseId`，正文却要求 handoff child run 经 `parentRunId + workflowId + snapshotHash` 关联到 DBOS；九张票没有另一张 correlation 表或唯一写入者。
- **影响**：C 的 interrupt/recovery、G 的 exact trace、I 的 legacy replay 都无法稳定从 Session run 找到执行 workflow/snapshot。
- **建议修法**：在 A 定义 immutable `executionLink?: {workflowId, snapshotHash}`（sync child 必填）或单独 append-only `AgentRunExecutionLink`，加 workspace/parent 唯一性、创建 crash window 与重放幂等测试。

#### BLOCK-05：U11 的“unset 且拒进生产”在类型和 HarnessRelease 中都不可表达

- **Spec/位置**：B `:34,40`；G `:20,27,36`；V3.1 `AgentControlLimits :968-986`、伪代码 `:1005-1023`、HarnessReleaseArtifact `:1448-1483`。
- **证据**：limits 类型全部是必填 `number`，却要求未标定项显式 `unset`；运行代码读取 `release.controlLimits.maxLlmSteps`，但 release artifact 既没有 `controlLimits` 也没有 `controlLimitsRevisionRef`，只有语义不等价的 `budgetPolicyRevision`。
- **影响**：实施者只能拍默认数字、把 unset 伪装为 0/Infinity，或从 release 外读取 latest；三种都违反 U11/exact release。
- **建议修法**：定义 `AgentControlLimitsDraft`（允许 null/unset）与仅全量标定后可发布的 `PublishedAgentControlLimits`；HarnessRelease artifact pin exact `controlLimitsRef`/hash，resolver 返回非空 `controlLimits`；发布 gate 和运行拒绝测试同批落地。

#### BLOCK-06：B 与 E 同时认领 Thread checkpoint 的全量重写，违反 one-writer

- **Spec/位置**：B `:36,62`；E `:23,25,40`；V3.1 `:552-565,853-869`。
- **证据**：B 说 6 段 summary + retainedTail compaction 在 B 落地且 Session Harness 是唯一消费者；E 又说 working memory 由 Observer reflection 全量重写，并落 Thread checkpoint。V3.1 §12.5 明说 working 随 §18.3 compaction 全量重写，实际是同一持久面，不是两个独立缓存。
- **影响**：两个 agent 可各建 writer/schema/调度器，产生 checkpoint 覆盖、revision 竞争和恢复不一致。
- **建议修法**：指定一个 canonical checkpoint writer。推荐 B 拥有 Thread compaction/checkpoint persistence，E 只提供 working-memory extraction/projection policy并通过 B 的单 writer 写入；或反向让 E 提供唯一 service、B 仅消费。明确 revision/CAS、失败保留、async buffer 与 MemoryInjectionReceipt 边界。

#### BLOCK-07：F 的 Opportunity 有需持久的接受/忽略状态，却被声明为“无表 derived projection”且没有底层决定 owner

- **Spec/位置**：F `:22,25,34,40`；V3.1 `:1186-1200,1570`。
- **证据**：candidate 有 `proposed/accepted/dismissed/expired`，接受后还要幂等进入 Thread→Plan；V3.1 又禁止 OpportunityCandidate 表。九张票没有定义 proposal/decision append-only record、幂等键、expiry 来源或 projection 输入。仓库现有 `HotTopicOpportunityCard` 是 `active/expired/evergreen_fallback` 的取材卡，不是该生命周期载体，不能无损复用。
- **影响**：F 无法实现 refresh/replay 后仍记得“已忽略/已接受”，也无法证明接受一次只创建一个 turn。
- **建议修法**：在不新建聚合的前提下，明确复用哪个 canonical append-only DecisionEvent/proposal store，定义 `candidateId + revision + actor` 决定合同与 `accept` 幂等键；若现有载体不满足，必须显式修改 §33.1，允许最小 proposal/decision 表，不能把 semantic event 当业务 writer。

#### BLOCK-08：附录 A17 是“违反即批次不通过”的硬门，但九张票零承载

- **Spec/位置**：V3.1 附录 A17 `:1934`；A `:58` 只声称命中 A15/A16；九张 spec 搜索不到 OpenCLI/device bridge。
- **证据**：A17 要求 OpenCLI live 门与 device bridge 独立且均 fail-closed。XHS spec 仍要求 live 未核销时不得标可用，GAP 计划还把 bridge 注入列为供给项；没有票负责验收证据、回归门或声明其已由既有 lane 完成。
- **影响**：九票全绿仍可违反权威硬约束，不能声称覆盖 V3.1 附录。
- **建议修法**：明确把 A17 分配给现有 XHS lane/具体 issue，并在相关 V3.1 票写“继承已完成证据 + 证据路径 + 回归命令”；若仍未完成，新增最小验收子票。OpenCLI 与 device bridge 必须分别有 fail-closed test，不得用一个 live 结论代替另一个。

### MAJOR

#### MAJOR-01：D 把 E 写成硬依赖，直接否定 E“并行且不阻塞 #433”的票面与 V3.1 路线

- **Spec/位置**：E `:5`；D `:5,39`；V3.1 `:1682-1690`。
- **证据**：E 明说与 #433 并行且不阻塞主线；D 却 `依赖 #432`。这不是循环，但会把 Memory 高风险 lane 变成批次 4 的硬阻塞。
