# V3.1 批次回顾（2026-08-13）——「近一周大量开发后仍不可用」定性与改约

> 历史证据快照，署树 `main@0487afd9`。当前集成、验证与 release 边界以
> `docs/ops/current-project-status.md`（CURRENT）为唯一入口；本文的改约条款（§4）
> 由 CURRENT 与 V31-77 承接为可执行事实，本文不再更新。

## 1. 结论（一句话）

V3.1 批次的问题不在实现质量，而在**「完成」的定义和批次的组织方式**：
从 08-01 规格到 08-13，没有任何一道验收门回答「一个零素材的新商家首访能否拿到成品」，
所有产能服务于票面自洽，没有服务于旅程可用。最有效的质量活动是 08-13 主控半小时的
手工浏览器走查——它发现了全批次最重要的 P0（V31-73），且该 P0 通过了此前全部规格评审、
票面验收与 e2e。

用户可感知增量很小。

## 3. 四个根因（按重要性）

1. **Done 的定义错了**。票关＋测试绿 ≠ 可用。V31-73 的死路通过了规格评审、票面验收与
   e2e，因为 `seedComposerInlineAuthorize` 恰好把真实用户会死的提交门绕掉（V31-54 种子）。
   验收体系在系统性地回答一个没人问的问题。
2. **默认路径无人设计**。规格文化重正确性门（fail-closed、合规、计费），轻第一次使用。
   「用户没有案例图时被引导去哪」没有属主——Core 侧 fail-closed 是对的，缺的是产品设计层
   对 Day-0 空状态旅程的回答。
3. **测试体系双向说谎**。假绿：e2e seed 掩码、dev 档 runtime-profile 恒 fixture（开发者从未
   见过真链路）、fixture 把 failed 当合法态。假红：35/42 仪器级联、spec 死线 5 天无人知。
   仪器不可信 ⇒ 每条红都要人肉定性 ⇒ 判红吃掉的时间超过写功能。
4. **批次太大、横向属主真空**。26＋40 票全是纵切票，每 lane 只对自己的 AC 负责；08-02
   已点名「属主真空」，08-13 原样复发——修复方式仍是继续开纵切票，没有人持有横向旅程。

## 4. 改约（用户 2026-08-13 拍板「按你的建议」）

- **R1（release gate 改约）**：「零素材新商家首访 → 提交 → 拿到成品」是 v3.1 的首要
  release gate。`v31-zero-source-image-text-first-visit.spec.ts` 升格为 v31 浏览器门的
  fail-fast 首位；day-0 类旅程 spec 禁用提交门种子（掩码纪律可执行化）。
  → 落地票 **V31-77**。
- **R2（旅程票先行）**：此后每个批次先开一张旅程票（属主＝主控，验收＝真浏览器走查、
  不接受 seed/fixture 背书），后开纵切票。
- **R3（冻结与清红队列）**：冻结新功能票的开票与派工，直到 Day-0 旅程门绿。解冻前只做：
  ① 候选分支 PR ＋ 同 SHA `Core quality / required` 绿（核销全部 release-verification-pending）；
  ② V31-76 两条红；③ V31-29 AC6 required 实跑；④ V31-41 residual ＋ 积分 100→0 疑似
  预留泄漏取证；⑤ V31-71 等 CI 再现。仪器票永远优先于功能票。
- **R4（批次减半）**：单波 ≤12 张票，且每波必含一张 R2 旅程票。40 票/波的吞吐是假象：
  集成后置的返工波把省下的时间加倍还回去。
