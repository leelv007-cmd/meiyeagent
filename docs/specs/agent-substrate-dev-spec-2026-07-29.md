## Problem Statement

商家（美业老板娘、品牌负责人）今天用这个产品，会遇到三件她说不出名字但持续感受得到的事：

1. **它不记得她。** 她纠正过的表达、确认过的偏好、用顺手的素材，下一次生成时系统当作从没发生过。用得越久，重复劳动越多，而不是越少。
2. **它不告诉她缺什么。** 信息不足时，系统照样生成一份平庸的东西交给她，而不是先说「要做好这条，我还需要知道你这次主推的项目和价格」。她得自己猜为什么效果不好。
3. **它让她看到不该看到的东西。** 内容生成完才在下游被红线拦下，她看到的是一次失败或一次被拦的交付——而不是一份已经自己改对了的稿子。

运营人员则遇到第四件事：**任何调整都要找开发。** 场景配方、行业话术、触发条件都埋在代码里，改一个字要走一次发布。

这四件事有同一个技术根因：**系统缺的不是编排能力，是反馈回路** `[S§11.6]`——模型看不见自己的结果（七门跑在生成链下游）、系统看不见自己的结果（记忆无使用遥测）、运营看不见自己的结果（改完不知效果）。

同时，代码库已积累一批「建好没通电」的债务：**142 条模块命令中 94 条（66.2%）零生产调用方** `[R11§Q3]`，前台另有一批按钮点了没有任何下游 `[反向扫描 15 条]`。这些不是孤立缺陷，是同一种完成度定义问题的分布 `[S§14A.7]`。

**v2 补充的三个新事实**（改变本 spec 的成本假设与工作切法）：

5. **病灶已定位，不再是弥漫症。** 我方代码七条「重蹈」假设逐条核实 `[V]`：红线门禁、幂等核心面、SDK 落库解耦**实测健康**；不通电的部分**全部聚在 Skill 层**（schema 契约五层全空、planner 选片零写入方、Langfuse 运行期软降级、正则测试冒充行为验证）。**修复面从「全仓治理」收窄为「Skill 层 + 验收纪律」**，即 #246。
6. **「注册即通电」对我方结构性不成立。** `@meiye/core` 是被 `@meiye/web` import 的库形态；Mastra 语料明证约定发现与自动暴露在库消费下失效 `[M§4/digest-D C-4]`。**正确路线 = 未通电可被构建/启动期检测并硬失败**——本 spec 的防复发机制据此从「票面纪律」升级为「机器可检」。
7. **竞品已从产品形态证明可行性，且同类实现独立收敛到同一套结论。** Miora（腾讯）以 Agent 工作台形态完整落地了我们的目标功能（D-163 三裁由其实证校准）；Mastra 用一个 v1 大版本偿还的债恰是我方同族病灶——**它的迁移文档等于替我们付费踩完了坑**，78 条可吸收候选已聚成九个决策包 `[M§3]`。

## Solution

从商家视角，这一轮之后：

- **它开始记得她。** 系统观察到她反复做同一件事时，会用一句人话问她「以后都这样？」；她点是，这条就成为她自己的经验，之后每次生成都用得上。她随时能看到自己攒了哪些经验，能改，也能删掉不想要的。
- **它开始问她。** 信息不够做到「好」时，系统在结果里明确说缺什么、并给出一个她点得动的补充入口，而不是硬生成一份平庸的。
- **它开始自己改对。** 内容生成后、交给她之前，系统先自查红线与结构；查出问题就自己改一遍再自查，改不动才交给门拦住并告诉她原因。
- **她能给结果打分。** 每条生成结果末尾有一个评价按钮（行业通用形态）。这个动作既是她的表达，也是系统学习的燃料。
- **她用得到的场景越来越多。** 市面上出现新的内容玩法时，我们把它转译成平台能力，她在快捷入口里直接一键用上，不需要她做任何配置。

从运营视角：**新增第八个能力域「Skill 目录」**，在既有控制台里增删改查场景配方与行业话术，走既有的草稿→评测→发布→回滚治理链，改完能看见效果数据。只有原语签名、门禁判据、工具注册表这类才需要开发介入。**换默认模型不动任何 Skill**（Skill 只声明能力需求，D-165①）；**生成结果差时能按三个版本轴分开归因**——是提示词、模型还是配方的问题，一条事件记录里就分得开（D-165④）。

从工程视角：建立**六个基质原语 × 大量 Skill** 的能力组织方式，取代「一个场景加几个命令」的堆叠；并把 94 条零调用命令与 8 条未兑现前台承诺一次清掉。**v2 追加**：六原语落地**吸收**既有 `operation`/`mode` 词汇而非并行新建（D-166⑥）；每个自纠环、每次执行都有**落成数字的边界**且触顶转可续挂起态（D-167）；一切「已建成」的宣称以**行为证据**验收——六格链 `defined → registered → bound → exposed → invoked → persisted`，源码正则测试全面废止（D-166⑤）。

从商家视角（v2 追加，Dashboard 与长任务）：**一进来就是工作台**（单路由三段式，D-164①），确认卡只读、改动就地纠偏（D-164③⑤）；任务跑到预算或次数上限时，**拿到的是当前最好的结果和一句「还可以继续」**，不是一次失败（D-167②）；离场再回来，任务还在、流还能接上、错过的部分补得齐（包⑦）。

## User Stories

### 商家 · 记忆与经验沉淀

1. 作为美业商家，我希望系统注意到我连续几次都把价格放在文案结尾时主动问我一句，这样我不用每次都手动改。
2. 作为美业商家，我希望这类询问用一句人话说清「我发现了什么、建议怎么做」，而不是弹出一个我看不懂的配置面板。
3. 作为美业商家，我希望我点「以后都这样」之后，这条偏好真的在下一次生成里生效，而不是点了没反应。
4. 作为美业商家，我希望能看到我一共攒了哪些经验，这样我知道系统到底记住了什么。
5. 作为美业商家，我希望能修改某条经验的描述，这样我可以让它更贴合我实际的说法。
6. 作为美业商家，我希望能删除某条我不再想要的经验，这样系统不会一直用一个我已经改主意的做法。
7. 作为美业商家，我希望被否掉的建议不会隔几天又原样弹一次，这样我不会觉得系统没在听。
8. 作为美业商家，我希望我确认过的可复用素材能在下次创作时被自动带出来，这样我不用每次重新找。
9. 作为美业商家，我希望系统能把我做过的几次同类内容识别成一个系列，这样我可以延续风格而不是每次从零开始。

### 商家 · 充分性与引导

10. 作为美业商家，我希望在信息不足时系统直接告诉我缺什么，而不是先生成一份平庸的东西让我猜哪里不对。
11. 作为美业商家，我希望这个「缺什么」是具体的（比如「这次主推的项目和活动价」），不是「请完善资料」。
12. 作为美业商家，我希望补充信息的入口就在我看到提示的地方，点一下就能填，不用去别的页面找。
13. 作为美业商家，我希望我补完之后能立刻重新生成，不用重新走一遍流程。
14. 作为美业商家，我希望系统只问真正会影响结果的那几项，不要把所有字段都问一遍。

### 商家 · 自纠与交付质量

15. 作为美业商家，我希望交到我手上的稿子已经过了合规自查，而不是我发出去才发现有问题。
16. 作为美业商家，我希望系统自己能改对的地方就自己改掉，不要把明显的问题留给我。
17. 作为美业商家，当系统改不动时，我希望它用人话告诉我为什么不能这么写，而不是给我一个错误码。
18. 作为医美类商家，我希望合规限制被明确解释，这样我知道边界在哪，而不是反复试错。

### 商家 · 结果反馈

19. 作为美业商家，我希望每条生成结果末尾有一个评价按钮，这样我能一键表达好不好用。
20. 作为美业商家，我希望这个评价形态跟我在别的 AI 产品里见到的一样，不用学。
21. 作为美业商家，我希望我评价过之后，系统的下一条产出真的往我喜欢的方向变。
22. 作为美业商家，我希望能记录内容发出去之后的实际情况，这样系统知道什么真的有用。
23. 作为美业商家，我不希望系统要求我填一堆转化数据——我只想简单说一下结果如何。

### 商家 · 场景与快捷入口

24. 作为美业商家，我希望我在别处听说的新内容玩法，过几天在这个平台上就能用到。
25. 作为美业商家，我希望这些新玩法以一键入口或组合包的形式出现，而不是让我自己拼配置。
26. 作为美业商家，我希望能把几个现成能力组合成我自己常用的一套，方便以后重复用。
27. 作为美业商家，我希望我组合出来的东西能改名、能改描述，这样我认得出它是干什么的。
28. 作为美业商家，我希望能删掉我组合坏了的东西，不留垃圾。

### 商家 · 前台承诺诚实性（存量修复）

29. 作为美业商家，我希望界面上点得动的按钮都真的有用，而不是点了什么都不发生。
30. 作为美业商家，我希望生成过程中的「停止」键真的能停下来，或者干脆不要显示它。
31. 作为美业商家，当系统说「点发送会先带你确认」时，我希望它真的带我去确认。
32. 作为美业商家，我希望「重新同步撤权」这类操作要么生效，要么明确告诉我为什么不能做。
33. 作为美业商家，我希望通知的「关闭」在我刷新后仍然是关闭的。
34. 作为美业商家，我希望「比较版本」真的能看到对比，而不是只换个按钮文字。
35. 作为美业商家，我希望结果漂移提示里的「恢复」真的把内容填回草稿。
36. 作为美业商家，我希望三级结果信号里的每一级都可能真的达到，而不是有一级永远是空的装饰。
37. 作为美业商家，我希望我勾掉的人设适用范围真的会被遵守，而不是模型仍然可能用上。

### 运营 · Skill 目录维护

38. 作为运营人员，我希望在后台看到当前有哪些场景配方与行业话术，以及各自属于平台层、行业层还是某个门店。
39. 作为运营人员，我希望能按来源筛选（收割转译／手写／归纳），这样我知道哪些是我们自己写的、哪些是外部来的。
40. 作为运营人员，我希望能新增一条配方，通过点击、选择和简单输入完成，不需要写代码。
41. 作为运营人员，我希望能编辑一条配方的正文与描述，并且系统提示我描述的长度预算。
42. 作为运营人员，我希望能设置这条配方在什么情况下生效（输出类型、品类、阶段），用选择而不是写规则。
43. 作为运营人员，我希望改动先进草稿，不会立刻影响正在跑的任务。
44. 作为运营人员，我希望在发布前能跑一次这条配方自带的评测，看到「改前 vs 改后」的对比。
45. 作为运营人员，我希望发布之后能一键回滚到上一版。
46. 作为运营人员，我希望能停用一条配方而不必删除它。
47. 作为运营人员，我希望看到每条配方被用了多少次、命中了哪些任务。
48. 作为运营人员，我希望看到哪些配方从来没有命中过，这样我知道描述或触发条件写坏了。
49. 作为运营人员，我希望看到配方命中之后结果信号有没有变好，这样我能判断它到底有没有用。
50. 作为运营人员，我希望所有改动都有审计记录，出问题能查到是谁什么时候改的。
51. 作为运营人员，我不希望我能改到合规红线——那应该走专门的评审流程。

### 运营 · 收割转译

52. 作为运营人员，我希望有一套明确的步骤，把市面上一个现成的方法论转成平台里可用的配方。
53. 作为运营人员，我希望在转译前能快速判断某个外部方法论能不能用，不用读完全文。
54. 作为运营人员，我希望转译进来的东西标注了外部来源与来源时间，方便日后追溯与复核。
55. 作为运营人员，我希望转译完成后有一个可测的验收，能说明它到底有没有让输出变好。

### 开发 · 原语与工具面

56. 作为开发人员，我希望能力面由少量基质原语构成，这样新增场景不需要新增命令。
57. 作为开发人员，我希望工具有一个注册表，这样白名单校验有实在的依据而不是校验一个自报的字符串。
58. 作为开发人员，我希望模型的工具调用被关在步骤内部，这样崩溃重放的语义不变。
59. 作为开发人员，我希望自纠循环有明确的次数与预算上限，这样成本仍然可以预先报价。
60. 作为开发人员，我希望红线判据只有一份实现，被门禁和自纠循环共用，不出现两套。
61. 作为开发人员，我希望模型永远拿不到租户与计费身份，这些由环境注入。
62. 作为开发人员，我希望模型只能发起提议、不能代替商家确认。

### 开发 · Skill 契约与标准

63. 作为开发人员，我希望我们的 Skill 文件能通过官方校验器，这样标准工具链可以直接用。
64. 作为开发人员，我希望治理字段放在标准结构之外，不污染标准部分。
65. 作为开发人员，我希望不再维护标准已经覆盖的自造概念。
66. 作为开发人员，我希望第三方的 Skill 拿进来不需要双向格式转换。

### 开发 · 债务清理与防复发

67. 作为开发人员，我希望零生产调用方的命令被清理掉，这样代码库反映真实在跑的东西。
68. 作为开发人员，我希望清理是逐条复核的，不会误删掉「被更好的实现顶替」的那些。
69. 作为开发人员，我希望新增命令的票在关闭前必须给出真实派发点，避免再产生一批死代码。
70. 作为开发人员，我希望「零生产调用方命令占比」是一个能持续看到的数字，这样我知道情况在变好还是变坏。
71. 作为开发人员，我希望源码文本匹配类的测试不再被当作行为验证的证据。

### 开发 · 存量工程债（既有票）

72. 作为开发人员，我希望提示词位点全量登记在提示词平台上，运行时按锁定版本拉取。
73. 作为开发人员，我希望登记失败会明确告警而不是静默降级。
74. 作为开发人员，我希望外发队列有重试上限与运维命令，不会无限重试。
75. 作为开发人员，我希望生产装配级的准入有端到端验证，而不只是构件级。

## Implementation Decisions

### 1. 六个基质原语（净新建）

能力面由六个原语构成，领域覆盖来自 Skill 在原语之上组合，而非新增领域命令 `[S§10.10]`：

| 原语 | 语义 | 副作用等级 |
|---|---|---|
| `read_context(scope, query?)` | 查——商家档案／素材／历史结果／偏好／平台规则／品类先验 | `read` |
| `generate(kind, brief)` | 造——文案／图／视频／**抽取解析** | 计费 |
| `revise(target_ref, instruction)` | 改——有界修改，走 OCC revision 围栏 | 计费 |
| `record(kind, payload, provenance)` | 记——**仅提议级写入** | `bounded_write` |
| `check(target_ref, rulesets?)` | 校验——红线／平台规则／结构，确定性、不调模型 | `none` |
| `ask_merchant(question, options?)` | 人是逃生舱——**异步、不阻塞** | `none` |

- `generate` 的 `kind` 枚举**须含「抽取／解析」**——素材解析是调外部供给且计费的生成类动作，塞不进文案／图／视频 `[R11§Q3.2]`。
- 签名对照现成实现校准 `[R13§6.3]`：`read` 采用 `(offset, limit)` 分页语义；`revise` 对照 `edit(old_string, new_string, replace_all)`；`record` 的记忆分层对照 `users/{profile, preferences, entities}`。
- **`revise` 与 `ask_merchant` 在现有 142 条命令中零实现；`check` 名义有 2 条但均为死代码且不含红线** `[R11§Q3.2]`。三者按净新建对待。

**安全不变量**（不可协商）：
1. 租户与计费身份**环境注入**，永不作为模型可传参数
2. `confirm_*` 级动作**商家专属**，模型只能 `propose_*`
3. `check` 作为工具是**附加**的，**不替代**既有确定性门禁
4. `generate`／`revise` 调用次数计入报价预算，**超限失败关闭，不静默计费**

### 2. 工具注册表与白名单补锚

- 建立工具注册表，六原语首批注册。
- `allowedTools` 校验从「比对调用方自报的 `toolId` 字符串」改为「**对注册表校验**」——该前置闸已存在且在子调用执行前生效，缺的是锚 `[R07§5.2]`。
- 工具描述与输出遵循硬预算纪律；工具规模增长时采用 schema 按需加载 `[R06 D6/D7]`。**当前不实施**，仅保留设计位。

### 3. 有界工具循环：交付前自纠环

- **循环关在单个 workflow step 内部**，DBOS 步骤边界不变；崩溃重放＝重跑该 step，循环从头再来。**幂等由 step 保证，不由循环保证** `[S§14A.6]`。
- step 内核保持 `(input, tools) → output` 纯函数，**工具经参数注入、不从环境抓取**，循环仅为实现细节，不绑定 runtime。
- 环形：`generate → check →（有违规则 revise，硬性封顶 N 次）→ 再 check → 仍不过则门禁拦下 ＋ ask_merchant`。
- `check` 确定性、不调模型、成本可忽略 ⇒ 循环内可自由调用；`revise` 计费 ⇒ 次数硬封顶，预算属 quote 的一部分。

### 4. 七门红线前移

- `validateHarnessPolicy` 当前调用点全在 operations 层（审批、可见文案）与评测侧，**无一在生成链内**；而 `HarnessPolicyPhase` 类型已含 `'execution'` 档，从未接上 `[S§14A.5]`。
- `check` 原语**收编该判据的同一份实现**，在 `'execution'` 相位调用。**不得复制第二份红线逻辑。**
- 门禁层行为不变：`check` 让模型更早自纠，**拦不拦仍由门决定**。

### 5. Skill 载体：三层 PG 目录 ＋ 标准格式 ＋ sidecar 治理

- 规范**不强制存储位置**，故落 PG 合规 `[R03§1.5]`。
- 三层归属：**平台层 → 行业层 → 门店层**，下层覆盖上层；**红线层不可被覆盖**（属门禁，非知识）`[S§12.3]`。分租户形态对照 BiSheng 的 `{tenant_id}/` ＋ `built-in/`。
- 三个来源并列，均为一等输入通道 `[S§10.8]`：**收割转译**（平台层）／**手写**（红线、平台规则实测、突发响应、冷启动兜底）／**向上归纳**（门店层→行业层）。
- frontmatter **只用标准字段**；治理字段（预算、副作用等级、租户、计费）**走 sidecar**——PG 中落为独立列或表，概念是「把治理数据挡在标准结构之外」，不是文件 `[D-161①]`。
- **退掉三个自造枚举**：绑定阶段枚举（标准无此概念，职能改由确定性触发条件表承担）／部署产物类型（标准目录约定的换名，**且补上遗漏的 `assets/`**）／评测套件引用（标准已用 `evals/evals.json` 覆盖）。
- **`description` 按标准认真写**（含字符预算）——它同时是运营目录页的识别字段与转译时的挂载判据，非纯期权。
- **激活方式：确定性显式注入**（按阶段 × 品类 × 租户查表），不启用模型自主选择——绕开标准最不稳的一环。

### 6. Skill 生命周期与运营界面（第八能力域）

- 界面是既有五个生命周期命令（定义／接受／绑定／回滚／部署）的**面**，不是新机制。**建这个界面即为这五个命令提供第一个生产派发点。**
- 治理沿用既有 admin-config 的 CAS ＋ 审计 ＋ 回滚；**不另建管理运行时**（D-037／D-048）。
- **在途任务不受影响**：run 启动即绑定不可变 revision 快照，与 OCC revision fencing 同源。
- 商家侧：**可用、可编辑、可删除，不提供下载**——沉淀产物引用租户内资产与平台层标识符，非自包含，导出物在别处无法运行 `[D-160②]`。商家侧界面遵**确认式而非配置式**。
- 权限边界：运营改内容与绑定；开发改原语签名、门禁判据、工具注册表、循环预算；**红线本身走合规评审**。

### 7. 反馈回路三处

- **模型侧**：自纠环（决策 3／4）。
- **系统侧**：记忆属主与使用遥测——写入侧后台抽取管线（两阶段，含租约认领与重试退避）、读取侧独立注入路径带使用遥测、排序与淘汰（使用计数 ＋ 闲置天数）、并发一致性 `[S§2]`。**载体为既有 durable workflow，零新增依赖。**
- **运营侧**：Skill 使用面板（命中次数、绑定关系、效果信号）。**该面板的价值上限由使用遥测决定；无遥测则退化为 CRUD。**

### 8. 结果信号：评价按钮

- 及格线的即时信号 ＝ **流式输出结果末尾的评价按钮**，采用行业通用形态。**不建平台外归因管线** `[D-160③]`。
- 该按钮是三级结果信号中「已验证」层的**生产者**——该层当前结构性恒空 `[反向扫描 #11]`，本项同时修复它。
- 商家自报发布结果的记账构成**延迟信号**，确认在 D-155 冻结面之外；两者均为商家自报，**都不是归因管线**。

### 9. 提议管线通电（十个死工具）

- `propose_* → confirm_*` 是「系统扮演策展人」的全部实现，其 propose／confirm 分野**正好等于「模型可调／仅商家可调」** `[D-159②]`。
- 通电范围：偏好信号记录、偏好提议／确认／撤销／视图、可复用资产提议／确认、复用任务创建、可复用资产视图、系列建议。
- **提议的触发时机与频率须随本轮定义**——系统提议质量直接等于产品质量上限（商家不会主动索要提议，也不会纠正方向错的提议）。
- **须同时提供「该出而未出的提议」的观测手段**，否则策展质量不可测。

### 10. 充分性判定（重估，非从零）

- 既有事实满足度判断模块**已存在且已接通生产链**，并已绑定提示词平台 `[S§14A.5]`。**先读它做了什么，再决定补什么**，不按新建对待。
- 判定结果是 `ask_merchant` 的触发源；补充入口须就地可点，补完可直接重生成。

### 11. 存量债务清理

**11.1 后端：零生产调用方命令（94 条）**

- 判据：是否有生产代码把 action 字符串送进模块派发口；派发口仅两条（web 的查询/命令客户端、core 的幂等模块命令执行器）`[R11 证据形态]`。
- **逐条复核后删除，禁止盲删**——已知反例：某条录入确认命令被更完整的收尾命令顶替，**属设计意图（D-151）非遗漏**。
- 复核标准须能区分「遗漏」与「设计意图顶替」。
- **该清理不依赖任何架构决策，可立即启动**；其收益属既有债务，**不得计入原语化收益**（否则高估 3.8 倍）`[D-161③]`。

**11.2 前台：未兑现承诺（8 条）**

停止键、素材来源确认跳转、字幕开关、结果漂移恢复与对比、改写冲突比较、通知关闭持久化、命令面板加入创作、素材重新同步撤权。

- 处置方式为**撤回承诺**（比补齐能力更便宜也更诚实）；字幕开关已由 D-133 修订裁定退役。
- 与 11.1 打成同一个「债务清理」包，共用复核标准，一次过审。

**11.3 真产品缺口（4 条，需产品判断）**

- 三级信号「已验证」层恒空 → **由决策 8 的评价按钮修复**。
- 人设授权范围有软消费者无硬门 → **由决策 4 的 `check` 收编覆盖**（该字段正是七门之一的判据对象）。
- 五步录入部分确认缺一道门 → 姊妹面已有正确写法，对齐即可。
- Pro Studio 精修跳转丢失上下文且无返回 → 属冻结面，形态待该面解锁时一并定。

### 12. 存量工程债（既有票并入）

- **提示词位点全量登记 ＋ 请求时版本钉扎 ＋ 登记失败显式告警**——与 Skill 的提示词承载同属一个体系，**须协调，避免重复建**。
- **外发队列重试上限与运维命令**。
- **生产装配级准入的端到端联接**（构件级 fixture 已存在，缺与真实媒体端口的端到端联接）。
- **评测正负控核销 ＋ 事实满足度判断位 golden 集**——**阻塞第一刀验收**，须排在其前。
- **硬门负向用例**——与决策 4 的 `check` 收编同属硬门体系，**须协调**。
- **长期红的创作循环 spec 族退休与信息架构翻新**——与商家侧 Skill 编辑界面、评价按钮**同动前台创作面，须串行**，否则定位器再次过时。
- **反向校验更正值缺口**（更正后的值被比对忽略）。
- **基线红两类** ／ **17 个 spec 首屏复验**。
- **价格事实有效期入口**（限时活动价被静默存成永久有效）。
- **生成物入库问题**（每次安装弄脏工作树且固化了某台开发机的密钥名单）——需产品裁决取消跟踪或重新生成并加门。

### 13. 防复发机制两条

1. **票面收口须给「生产派发证明」**：新增命令或契约的票，关闭前须给出真实派发点位置。作用在开票收口，而非事后复核。
   - 附证：既有的「生产装配」测试是**源码文本正则匹配**，运行时启动即崩仍会绿；且其断言的正是一根**上游无水源**的管子 `[S§14A.7]`。**故要求的是派发证明，不是测试覆盖。**
2. **「零生产调用方命令占比」列为受监控指标**（当前 66.2%）。

### 14. 暂停待判（不在本轮实施，须先裁存废）

- **文案／媒体双投影器统一**：疑似被 `generate(kind)` 原语吸收。
- **创作入口源包链路**（源内容包字段有读侧无写侧）：疑似被 `record` 的血缘 provenance 吸收。

### 16.（v2）有界执行 —— D-167，工程票 #247

- **术语统一：四上限**（`maxIterations`/`maxCostCents`/`maxWallClockMs`/`maxDelegations`，`maxDelegations` 为第四个独立上限——委派次数不是迭代的派生计数）。D-167 标题的「三闸门」为历史名，口径以本节为准。
- **修订第 3 节（自纠环）**：「硬性封顶 N 次」落成四上限数字进执行钉扎（+ `stopReason` + 触发上限标识）；**触顶 = 可续挂起态**（当前最好结果 + 未达标说明 + 可继续），转 HITL 介入点，不抛错；权限类失败（七门 `subject_asset_rights`/`external_action_approval` 命中）不进自纠环；三层重试（模型 SDK/自纠环/工具层）收敛单一口径不叠乘。
- **未标定即禁用**：数值未标定的上限必须显式 `unset`，且**拒绝进入要求该上限的生产路径**——「先落字段后定值」不得静默退化为无界（标定票 #255 为 #247 关票依赖）。
- **判定分类例外（与 D-166④ 的接缝，显式写死防止导出相反验收）**：「决定是否放行」的判定类（校验/评分/门禁）缺配置 = fail-closed；「仅决定是否启动增强自纠」的判定器缺配置 = **自纠环显式关闭并留痕、主链路照常**——前者乱放行非法，后者乱判非法、关闭合法。两类各配负向测试。
- **修订第 3 节（step 纯函数）**：追加「分支谓词位无副作用」——条件/判断位禁止写状态/发事件/挂起（D-167⑤）。
- 失败姿态合同：挂起路径 fail-open、恢复路径 fail-closed——恒前进的边界是「不让坏数据前进」（D-167④）。

### 17.（v2）HITL / `ask_merchant` 深化 —— 包③ `[M§6]`

- `ask_merchant` 拆**出站 question schema / 入站 answer schema 两张契约**；回答的服务端校验**默认强制**；校验失败转新追问不抛错；「跳过」是 answer schema 显式枚举值（`answer | {deferred} | {skipped}`）。

- **超时 = 语义层默认回答**（系统代答，仅限无对外副作用的问题），留痕区分商家答/代答；不做载体层挂起过期（过期→失败/取消是被禁形态）。**与 D-116 确认卡超时自动继续统一为同一原则**：超时的唯一合法结果 = 采用默认答案继续；D-116 两条安全边界推广到 `ask_merchant`（编辑中暂停倒计时；涉外部副作用或超额度不自动继续，回落硬门显式确认）。
- **待确认状态持久化**（重启/换设备后有效）；渲染不了确认卡的渠道**挂起而非放行**。
- 补**条件性确认承载位**：`confirm_*` 保持无条件形态，另立「执行体内按运行时条件挂起」路径；条件判断不交模型。

- resume 三元组 = `runId + step + resumeData`。
- D-013 扩两类节点（运行时缺参索取／资源闸门介入，D-168③）；七类补载体维度（对话内/任务卡/通知）。

## Testing Decisions

### 什么是好测试

只测**外部可观察行为**，不测实现细节。给定输入与前置状态，断言返回值与持久化后的可观察状态；不断言内部调用顺序、不匹配源码文本。

> **本轮明确废止一类做法**：以读取源文件并正则匹配其内容作为「已接通」的证据。既有实例证明它在运行时完全不工作时仍会通过，且能满足朴素的「有测试覆盖吗」检查却什么都不证明 `[S§14A.7]`。
> **v2 升级为机器可检（D-166⑤）**：替代物 = 注册表快照断言（实际 vs 期望清单，显式记账枚举盲区）+ 一次真实入口调用的行为断言；验收走六格链 `defined → registered → bound → exposed/reachable → invoked → persisted/traced`，新建能力全格取证、改动补受影响格。负向回归五件套为每个新能力域的标配：`available-but-unbound` / `dynamic-not-in-inventory` / `inventory-blind-to-closure` / `invalid-shape-silently-inert` / `duplicate-authority-key`。
> **v2 追加一条判定类纪律（D-166④）**：判定类能力（校验/评分/门禁）缺配置的正确行为是 fail-closed，测试须含「缺配置时必须失败」的负向用例——no-op 返回通过是假绿的教科书形态。

### 测试缝：三个，**全部既有，零新建**

**主缝 · 模块派发口**（`P1OperationModule.execute({context, input, idempotencyKey})`，入口为 web 查询/命令客户端与 core 幂等模块命令执行器）

覆盖：Skill 生命周期五命令、评价按钮的记录、商家自报记账、提议管线十工具、**以及零调用命令清理的验收**。

选它作主缝的理由：**该缝已是本项目对「接通了没有」的操作性定义**——判断有无生产调用方，判据就是「是否有生产代码把 action 字符串送进这个派发口」。在此缝测试等于直接测「通电与否」。

**次缝 · Harness 阶段端口**（阶段端口与 Skill 指令解析端口）

覆盖：Skill 注入进生成链、自纠环、充分性判定的触发。

不能压进主缝的理由：Skill 注入发生在 workflow 内部、不经命令派发；从主缝测它须跑完整 durable workflow，过重且脆。次缝是能覆盖它的最高点。

### 本轮成果的最大风险

本 spec 多处以「接线即可」估算成本。**该乐观估计的前提是接线这件事有人负责到底，而本仓历史证据显示该前提不成立**——一天内撞见六例「建好没通电」，命令面 66.2% 零调用是其度量。

**第一刀之所以要求走完完整通路并有可测验收，正是这条风险的对冲，不是流程洁癖。**

### 主控已知的判断不确定性（如实标注）

- 双投影器的具体形态未完全摸清，「被原语吸收」属**疑似**，不是既定事实。
- 反向扫描曾把某个交接面的「记录发布结果」判为空操作，而另一处同名功能有真实调用方；**疑为两个入口一通一断，须核实。**
- 提议触发时机与频率、「该出而未出的提议」的观测手段，**主控明确未想清**，须在实施中定。
- 「归纳出的行业层不可复制」在归纳机制建成前无法验证。
