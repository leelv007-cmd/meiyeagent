# 美业宣发经营 Agent 全量功能开发规格

> 本规格把合并权威版细化为实现合同；#25–#49 主实施批与 D-042~D-046 后续批已合入，故不再是新建 worktree 的开工清单。规格正文保留需求与验收语义；当前完成度、环境门和 release gate 以 `docs/reviews/implementation-gap-ledger-2026-07-19.md` 与代码/测试为准。阶段定性仍按 D-040：**功能完善的产品开发阶段**，任何可见入口只有满足完整成品合同才对用户开放。

## Problem Statement

面向生活美容、美发、美甲美睫、皮肤管理单店的实际内容操作者（店主/主理人/员工/代运营），当前产品还不能兑现权威文档承诺的核心体验：

- 说一句"把新团购做一套能发的"，拿不到一个可直接采用的完整宣发成品包（主推荐 + 平台成品 + CTA + 事实权利状态）；现有代码有文案生成与素材的零散能力，但没有把它们串成"意图 → 成品包"的编排主干。
- 抖音与微信视频号变体缺视频成片：成片管线（provider 抽象 + Ark provider + ffmpeg 合成）已建约 2500 行，但未接通当前模型目录，用户拿不到成片。
- 对话层没有 token 级流式与生成式 UI：用户看不到逐字回应，缺料时也没有"一次只问一个问题"的单问卡，结构化输入仍隐含表单思维。
- 长任务不可靠：没有 durable 编排载体，离开页面、进程崩溃或部署都会丢任务，无法"离开-恢复-回到精确版本"。
- 资产不复利：门店事实、IP 身份、素材授权、历史采用没有形成可就地纠错、带来源与生效期的经营上下文，第二次同场景制作不比第一次省力。
- 修改不闭环：成品上的快捷修改（更像本人/换素材/换平台/做成海报）没有派生版本机制，"做同款/存系列"没有入口。

## Solution

按权威文档 Product Shape 完整落地"主动宣发 Agent"（Approach B + 场景货架兜底）：

- **首页三件事**：今天值得发什么（主推荐 + 完整成品预览 + 冷态诚实降级）、一句话 Composer、五类任务入口（场景上下文切换，不跳页不弹表单）。Day-0 与 Day-N 同一界面，示例橱窗冷态 + 流内资产积累。
- **五类入口完整成品合同**：日常项目曝光 / 热点借势 / 品牌与个人 IP / 促销团购转化 / 宣传物料，每类按权威文档表格交付完整 MarketingPackage（ContentPackage 的宣发称谓，唯一聚合）与诚实降级；小红书、抖音、微信视频号三平台变体，视频变体含成片。
- **编排层五段式 Harness**（D-033）：①意图正名 → ②上下文注入（六维编译不可变 ContextBundle）→ ③Brief 编译 → ④执行与择优（N→1 候选评估 + 七项硬失败门）→ ⑤回装与交付（revision + chips 可解释）。确定性主干 + 智能节点，durable 载体 = **DBOS Transact 已锁定**（D-041；PoC 七面全过，证据 `.scratch/dbos-poc-2026-07-18/REPORT.md`）。
- **三进三出前后端合同**（D-032）：后台只出白话进度事件、单问卡、成品 revision；前台只进意图、结构化决定、chips 信号。对话流是投影，真相在 ContentPackage 与三条账本。
- **HITL 五类介入**：品味选择 / 临时纠偏 / 事实权利冲突单问卡 / 资产晋升 / 外部行动一次性批准；每任务最多一个阻塞点，异步收件箱聚合。
- **承接与结果产品面**：chips 补记线索信号、三级信号分层、结果阶梯周复盘，不做假归因。
- **观测评估基建**：Langfuse 自托管（Task=trace、五段=五 span、prompt 版本化先行）+ promptfoo 红线 CI + BeautyPreferenceMemoryEval 纯 Vitest 评测台 + 自建 PG 审计表双写（审计表为权威）。

合规与运营（Week 0 预登记 + 义务清单落盘、门店两波进场、WOZ 人工运营、证据合同登记仪式）全部置后，见 Out of Scope。

## User Stories

### Day-0 与首页

1. As a 新注册的门店内容操作者, I want 首屏就是工作界面、没有前置建档向导, so that 我不用先填资料就能开始第一个任务。
2. As a 新注册的门店内容操作者, I want 冷态下看到明确标注的示例门店成品橱窗并能对它做同款, so that 我第一分钟就理解产品能交付什么。
3. As a 门店内容操作者, I want 「今天值得发什么」给出一个有本店依据的主推荐与完整成品预览（冷态时诚实显示示例推荐或建店邀请，不做伪个性化）, so that 我不用自己想选题。
4. As a 门店内容操作者, I want 主推荐说明为什么适合现在、用了本店什么、希望顾客做什么, so that 我能快速判断敢不敢发。
5. As a 门店内容操作者, I want 只在需要时展开不超过两个明显不同的备选方向, so that 选稿不是必经步骤。
6. As a 门店内容操作者, I want 热点机会卡带来源、采集与过期时间、本店相关性解释和失效时的常青降级, so that 我不会错借势或蹭过期热点。

### Composer 与最少输入

7. As a 门店内容操作者, I want 用一句话下任务（如"把新团购做一套能发的""用小林的口吻讲这个热点"）, so that 我不需要学习任何工作流概念。
8. As a 门店内容操作者, I want 点击五类入口后 Composer 的推荐词与工具集合整体切换、不跳页不弹字段表单, so that 场景切换零学习成本。
9. As a 门店内容操作者, I want 粘贴公开可访问或已授权的链接直接解析，失败时自动切换截图/OCR、粘贴文本或选素材, so that 解析失败不阻塞任务。
10. As a 门店内容操作者, I want 系统自动读取已有事实，只在关键事实缺失、冲突或过期时一次问一个阻塞问题, so that 我不被连环追问。
11. As a 门店内容操作者, I want 非关键素材缺口先用安全回退交付成品、再提示可选补料, so that 缺料不等于交不了活。
12. As a 门店内容操作者, I want 对话回应 token 级逐字流式呈现、长任务显示白话阶段进度, so that 我始终知道 Agent 在干什么。
13. As a 门店内容操作者, I want 结构化输入以生成式 UI 卡融入对话流, so that 我永远不用面对六张表格。

### 五类入口与完整成品包

14. As a 门店内容操作者, I want 日常项目曝光入口交付本店项目主张、证据素材、封面/图文成品、可选口播或拍摄清单和咨询/预约 CTA, so that 一次任务就是一条能发的内容。
15. As a 门店内容操作者, I want 缺顾客案例时系统改用环境、流程、产品或专业解释模板并说明原因, so that 产品永不伪造案例。
16. As a 门店内容操作者, I want 热点借势入口交付本店原创角度、匹配事实素材、平台成品和机会过期提示, so that 借的是流量机制不是抄袭表达。
17. As a 门店内容操作者, I want IP 经营入口交付明确表达身份、栏目锚点、身份一致的成品和系列续写入口, so that IP 内容有连续性。
18. As a 门店内容操作者, I want 促销团购入口只使用已核验的价格/权益/期限，无权威价格时不写具体优惠, so that 我不会发出错误报价。
19. As a 门店内容操作者, I want 宣传物料入口交付选定用途的成套模板、明确尺寸、可替换文字素材和确定性导出, so that 物料能直接用于印刷或上架。
20. As a 门店内容操作者, I want 每个成品包按所选平台交付小红书、抖音或微信视频号变体, so that 不用自己改格式。
21. As a 门店内容操作者, I want 成品包附带事实与权利状态说明, so that 我知道哪些内容有依据、哪些素材有授权。
22. As a 门店内容操作者, I want 未满足完整合同的入口被隐藏而不是显示假按钮, so that 我看到的每个入口都真能干活。

### 视频成片

23. As a 门店内容操作者, I want 抖音与视频号变体直接拿到视频成片, so that 我不需要自己会剪辑。
24. As a 门店内容操作者, I want 成片自动记录来源信息并按开关烧录标识, so that 成片的产出过程可追溯。
25. As a 门店内容操作者, I want 系统从多个候选中自动择优后再交付, so that 我拿到的是最好的那一版而不是抽卡结果。
26. As a 门店内容操作者, I want 成片能力未通过验收时得到口播稿+视频脚本+拍摄清单（标注仅"成片自动生成"为辅助完成）, so that 文案层交付不被表述为降级。
27. As a 门店内容操作者, I want 视频任务异步执行、离开可恢复、显示白话进度而非假百分比, so that 长任务不用守着等。

### 快捷修改与纠偏

28. As a 门店内容操作者, I want 在成品上就地用自然语言修改并看到 diff、支持 undo，普通修改不需要审批, so that 纠偏像改口头稿一样快。
29. As a 门店内容操作者, I want 一键"更像主理人本人"或换成其他登记过的表达身份, so that 内容口吻可控。
30. As a 门店内容操作者, I want 一键"不要太促销"或"加强优惠和到店动作", so that 促销力度随场景可调。
31. As a 门店内容操作者, I want 一键换成本店另一组素材, so that 素材不合适不用重来。
32. As a 门店内容操作者, I want 一键把成品换平台变体，或导出朋友圈/线下物料版本, so that 一次任务多处使用。
33. As a 门店内容操作者, I want 把成品做成海报、项目套图、口播或预约引导卡, so that 同一主张能变成多形态物料。
34. As a 门店内容操作者, I want 所有普通修改默认只影响当前任务，只有明确"以后都这样"才进长期偏好, so that 系统不会悄悄学错。

### HITL 确认与外发批准

35. As a 门店内容操作者, I want 价格、身份、来源、时效或素材用途冲突时收到一张展示来源和影响的单问卡, so that 我确认的是具体事实而不是抽象弹窗。
36. As a 门店内容操作者, I want 每个任务同一时刻最多一个阻塞点, so that 我不会陷入审批链。
37. As a 门店内容操作者, I want 异步收件箱聚合所有任务的待办并一次置顶一个, so that 多任务并行也不乱。
38. As a 门店内容操作者, I want 公开发布、扣费和账号权限变化必须一次性批准并绑定精确成品、账号、平台、时间与费用, so that 不可逆动作永远不被静默执行。
39. As a 门店内容操作者, I want 价格或授权到期时只有相关成品和发布批准失效, so that 我不用重填整套资料。
40. As a 门店内容操作者, I want 主推荐旁被动显示"为什么用了这些"chips 并可一键换项目/身份/素材, so that 可解释但不构成审批步骤。

### 长任务与恢复

41. As a 门店内容操作者, I want 关掉页面后回来任务还在原进度, so that 我可以随时离开。
42. As a 门店内容操作者, I want 服务崩溃或部署不丢任务、断点续跑不重复已完成步骤, so that 长任务可信赖。
43. As a 门店内容操作者, I want 挂起等我确认的任务在我答复后立即继续，且若期间事实已变会重新编译再继续, so that 恢复后的结果仍然正确。
44. As a 门店内容操作者, I want 随时回到任意成品的精确历史版本, so that 改坏了能找回。

### 资产进入、纠错与生命周期

45. As a 门店内容操作者, I want 给门店主页、价目表、团购截图或相册后，系统提取候选事实与素材并在成品旁用一句话摘要预览"本次理解了什么", so that 建档发生在干活过程中。
46. As a 门店内容操作者, I want 对理解错误就地改错或替换、主流程不出现大表格, so that 纠错不打断创作。
47. As a 门店内容操作者, I want 影响真实性的资产都带来源、适用范围、生效与过期时间和版本, so that 过期价格永远不会进新成品。
48. As a 门店内容操作者, I want 顾客肖像等受限素材只在上传时打了同意标记后才可用于成品, so that 授权是素材属性而非每条内容的关卡。
49. As a 门店内容操作者, I want 示例门店内容与我的事实账本物理隔离, so that 示例数据绝不混入我的门店事实。
50. As a 门店内容操作者, I want 后续任务只做增量补足、缺什么才要什么, so that 资料越用越全而不是一次填完。

### IP 身份

51. As a 店主, I want 品牌 IP 与个人 IP 作为独立资产登记（所有者、专业边界、允许平台、表达样本、授权与生效期）, so that 身份不是语气下拉框。
52. As a 店主, I want 员工离店或撤销授权时停止该身份新生成并使待发布引用失效, so that 不会用前员工身份发内容。
53. As a 门店内容操作者, I want 个人 IP 未确认时系统用品牌官方口吻且绝不代言或编造经历, so that 身份表达永远真实。

### 做同款、系列与复用

54. As a 门店内容操作者, I want 对任何历史成品一键做同款作为新任务起点, so that 第二次同场景制作明显更省力。
55. As a 门店内容操作者, I want 把成品保存为系列并获得续写入口和下一条建议, so that 内容有栏目化连续性。
56. As a 门店内容操作者, I want 资产晋升前预览固定项、变量槽、作用域、来源与权利并确认后按最窄范围生效, so that 沉淀的是稳定结构不是整篇成品。
57. As a 门店内容操作者, I want 稳定模式由系统观察后提议、经我确认才生效, so that 长期记忆永远不越权。

### 承接与结果

58. As a 门店内容操作者, I want 发布或导出后低负担补记发布地址与状态, so that 成品和结果能对上。
59. As a 门店内容操作者, I want 用一排可选 chips 补记私信、加微、预约、买券、核销和到店, so that 记录一次观察不超过十秒、不用维护 CRM 表格。
60. As a 门店内容操作者, I want 结果按已验证信号、门店记录信号、推断相关性三级分层展示, so that 产品从不把相关性说成因果。
61. As a 门店内容操作者, I want 周复盘只回答发了什么、观察到什么、下一轮验证什么，并支持一键续做、换 CTA 或停止系列, so that 复盘直接驱动下一轮动作。
62. As a 门店内容操作者, I want 每个成品沿"已发布 → 获得注意 → 发生咨询 → 预约/买券 → 核销/到店"的结果阶梯展示进展, so that 我看得懂内容的经营价值。

### 我方运营与工程侧

63. As a 我方工程师, I want 每个 Task 在 Langfuse 形成一条 trace、五段各为一个语义 span 可回放, so that 任何一次交付的决策链路可复盘。
64. As a 我方运营人员, I want 提示词在 Langfuse 做版本化发布与回滚、不改代码, so that 提示词迭代不等发版。
65. As a 我方运营人员, I want 场景配方以自由格式存入现有配置后台（双作用域 + 追加式修订 + 审计）, so that 配方可改可回滚可追责。
66. As a 我方工程师, I want 七条硬红线的回归用例在 CI 中阻塞合入, so that 红线回归永远到不了用户面前。
67. As a 我方工程师, I want 红线门禁与审计事件同步双写自建 PG 审计表并以 traceId 关联 Langfuse 富回放, so that 审计权威不依赖第三方存储的 TTL。

## Implementation Decisions

1. **运行拓扑不变**（ADR-0006）：Workers 壳（营销站/认证/仪表盘壳/薄 BFF/上传签名，不拥有产品事实）+ 单 Node 服务（Core 域逻辑、编排、视频合成、AI runner）+ 单托管 Postgres（唯一真相源，Better Auth 表同库）+ 对象存储适配器。Workers→Node 单跳共享类型包与服务令牌；SSE 直通失败时前端直连 Node 兜底。
2. **三层架构与三进三出合同**（D-032）：对话层（AI SDK token 流式 + 生成式 UI）/ 编排层（每任务一条独立可恢复工作流）/ 能力层（模型 API、ffmpeg、发布导出适配器，可替换、不含业务真相）。后台→前台只有三种载荷：白话进度事件、需要用户的单问卡、成品 revision；前台→后台只有三种：意图（一句话+场景上下文+素材）、结构化决定（进决策账本）、chips 信号补记。此合同是本规格的最高稳定边界，前台形态迭代不改后台合同。
3. **五段式 Harness**（D-033）：①意图正名（LLM 节点：模糊输入→结构化任务声明）②上下文注入（确定性节点：六维编译，三池取料，优先级链固定为本次指令>有效事实>已确认资产>已确认偏好>行业配方>模型通识）③Brief 编译（LLM 节点：ContextBundle→每执行单元完整 brief）④执行与择优（混合节点：模型目录路由 + N→1 候选评估 + 七项硬失败门）⑤回装与交付（组装 ContentPackage revision，主推荐+按需备选，chips 可解释）。每段选择依据落 DecisionTrace。
4. **五条工程约束无条件生效**（D-038）：五段 step 写成 runtime 无关纯函数，载体只当外壳；step 一律按 at-least-once 设计业务幂等；大产物走对象存储、编排状态只存引用；⑤段 revision 写入一律业务层 OCC 条件写；发布 SOP 含 in-flight 实例排空/版本粘滞。
5. **Durable 载体已锁定 DBOS Transact**（D-041 supersede D-034 PoC 门）：PoC 七面（六题+审计双写）全过，DBOS Transact（@dbos-inc/dbos-sdk）锁定为五段式 Harness 的 durable 执行载体；system DB 独立分库；workflowID=Task ID；五段新 kind 只进 DBOS、存量 pg-boss 原地共存不硬迁。证据 `.scratch/dbos-poc-2026-07-18/REPORT.md`。挂起等待用载体原生挂起态，答复即续、恢复带版本围栏。
6. **审计双写已随 D-041 验证**（待验证 18 双写半边关闭；promptfoo×火山 spike 仍开放）：自建 PG 审计表为权威，先写审计表（与业务同库可同事务）后发 Langfuse；审计写失败=任务硬停，Langfuse 写失败=降级容忍+补偿重发；task_id/workflow_id/span_id 三方对齐，幂等键取自载体的 workflow/step 标识。
7. **①③结构化节点**（D-035）：以 AI SDK 现行结构化输出 API 实现（ai@7 口径，`generateObject` 已 deprecated 不得使用），各自封装为独立非流式函数边界；外层埋点记录首过校验率、repair 率、retry 率。BAML 为触发式升级路径，不默认引入。
8. **流式钦定**（ADR-0007/0010）：副驾对话 `streamText` token 流式；文案生成部分对象流式（现行 API）+ 前端 `useObject`；长任务（图/视频）走异步 Job + 白话阶段叙事 + 自动轮询或推送，禁假百分比。
9. **ContentPackage 唯一成品聚合**（ADR-0011）：MarketingPackage 是宣发语境命名别名，不引入第二聚合；Task 全部产物打包为 ContentPackage，修改类交互=派生 Task 产出 derived revision；revision 不可变；Product Core 是唯一物理写入入口。
10. **三条真相链**（D-017）：经营事实、人类决定、AI 记忆各自独立账本；结构化字段只引账本（事实 grounding）；学习旁路只写候选，未确认候选在架构上无法生效（结构阻断），晋升必过确认卡且全留痕。
11. **七项硬失败门为结构性护栏**（D-040 边界澄清）：跨店/跨 IP 串线、无来源关键事实、未授权主体素材、身份冒用、过期或错误价格、错误版本外发、未批准公开/付费动作——全部在④段自动拦截，字段引账本、素材出授权库、身份出登记资产。
12. **条件权利门窄触发**（D-022）：只在当前成品使用可识别顾客素材时计算主体/用途/平台/期限；权利不足按"换安全素材→匿名化→请求授权→放弃该表达"顺序处理，单个素材不可用不阻塞整个任务。
13. **能力门三态**（D-024）：每项外部能力只有已验证/辅助完成/不可用三种前台状态，未验证能力隐藏或诚实降级。开发期验收作为工程质量检查与数据留存执行，证据合同的预登记仪式随运营重启补办（D-040）。
14. **视频管线接通**（D-027/D-028）：已建 provider 抽象 + Ark provider + ffmpeg 合成接通当前模型目录；成片走分镜→首帧→片段→N→1 择优→合成链路；标识烧录按开关、来源信息如实记录；单片成本、端到端时延、可用质量率、开关行为、来源记录五项验收数据留存。文案层（口播稿/脚本/拍摄清单）是一等交付物，与成片两层独立交付，组合由入口意图决定。
15. **观测评估三件套**（D-036）：Langfuse 自托管承载 trace/回放/实验/prompt 版本化（Task=trace、五段=五 span）；promptfoo 承载七红线回归 + 对抗用例的 CI 阻塞门，并为④段择优判分器提供范式；BeautyPreferenceMemoryEval 用纯 Vitest 自写 runner 跑多轮对话→管线→记忆状态硬等式断言，结果导出 Langfuse datasets。
16. **非代码可变层**（D-037）：提示词走 Langfuse prompt management（发布钉住不可变版本/内容哈希）；场景配方以自由格式存入现有 admin-config（双作用域 + CAS + 审计），强类型 artifact schema 与四态发布门缓建（证据门挂待验证 19）。
17. **模型供给**：provider registry 混合路由（ADR-0005），生成计费沿用现有双账 ledger（reserve→commit/refund）模式；工具包装层统一写 tool_calls 审计与用量。
18. **前端体系**：mkfast Workers 壳继续承载；Composer 场景 chips 切换（点击整体切换推荐词与工具集，不跳页不弹表单）；视觉按 DESIGN.md「门店橱窗」范式（氛围层+磨砂玻璃+Composer 主轴+玫瑰金火花）；流式渲染用既定组件栈（ResponseStream + Streamdown-cjk 逐字渲染）。

## Testing Decisions

- **好测试的定义**：只测外部行为，不测实现细节。本项目的"外部行为"有两个稳定面——三进三出合同的载荷，和五段纯函数的入出参。测试永不 import durable 载体、不断言内部状态机，换载体（DBOS→Inngest）时测试原样通过是判据。
- **主接缝 = 三进三出合同**（Core API 的 HTTP + SSE 边界）：合同测试覆盖三出（进度事件序列、单问卡出现与答复即续、revision 产出与 OCC 冲突拒绝）与三进（意图受理、结构化决定入账本、chips 补记落库）。前台形态迭代不触碰这层测试。
- **次接缝 = 五段 step 纯函数内核**：每段以 ContextBundle/brief fixtures 直接单测，覆盖六维编译优先级链、硬失败门七项逐一对抗用例（每项各有一个"必须拦下"的用例，阈值 0）、择优器 N→1、⑤段幂等重放（同 step 重复执行结果一致）。
- **既有先例沿用**：Core 侧同目录 `*.test.ts` + `tsx --test` 串行跑（product/postgres-repository 测试为样板）；真机模型调用按 `.live.test.ts` 约定隔离（视频 Ark provider 已有先例），CI 默认不跑 live；壳侧 Playwright e2e smoke 延用现有三步冒烟并追加 Composer 冷态与流式渲染路径。
- **评估层**：promptfoo 七红线回归进 CI 阻塞门；BeautyPreferenceMemoryEval 断言 `false_persistence_rate === 0`、supersede 后旧值不复现、abstention 行为，是 Stage 2 偏好学习放行的前置门（评测台本身在本阶段建成并进 CI）。
- **DBOS 载体行为**（崩溃恢复、挂起恢复、SSE 通路等）已在 D-041 PoC 层验证并通过（证据 `.scratch/dbos-poc-2026-07-18/REPORT.md`）；常规测试面仍不 import DBOS、不断言内部状态机。

## Out of Scope

- **合规与运营执行**（D-040 整体置后）：Week 0 预登记文档与 D-039 合规义务清单落盘、门店两波进场与回放窗、WOZ 拦截操作台与 intervention_log 人工运营、eval 集运营采集、「已验证」证据合同的预登记锁定仪式。触发点 = 全量功能开发完成、重启验证/试点。
- **admin-config 强类型 Harness artifact schema 与 candidate→eval→approve→publish 四态门**（待验证 19，证据门：回放校准后的配方真实字段是 schema 的核心输入）。
- **Stage 2 偏好学习放行**：候选链与确认卡机制在本规格内建成，但学习到的偏好实际影响输出的放行以 BeautyPreferenceMemoryEval 过关 + 回放数据为门。
- **触发式挂账项**（D-035/D-037）：BAML 迁移、Mastra 四项 spike gate、Dify 子流引擎、CF AI Gateway 火山 spike——各绑触发点，不预建。
- **Pro Studio 升单线**：由既有 vozeb 采用规格（issue #23）拥有，本规格不重叠。
- **医疗美容**（D-025）：不入默认范围，独立研究探针另行处理。
- **未验证平台自动发布与付费投放**：能力门约束——点评/美团只作权威输入、朋友圈只作导出成品，账号级发布链路未验证前不宣称自动发布；付费投放不入首发。
- **店务管理非目标**（D-030）：预约管理、收银、库存、CRM、排班、财务不进产品。

## Further Notes

- **阶段口径**（用户 2026-07-18 拍板，D-040）：此前编排把运营与合规当发布前硬门槛，但产品处于打磨阶段、功能随时迭代，过早的运营/合规测试投入会随迭代反复作废。本阶段功能自由迭代，不冻结验收矩阵，不走预登记仪式；结构性护栏（硬失败门、权利门、审计双写、红线 CI）不属此列，随功能同批建。
- **Wave 术语澄清**：项目只有一个 Wave 级阶段（Wave 1 验证合同，D-026），其内部"两波"指门店进场批次；该阶段整体属运营执行，已随 D-040 置后。
- **接缝已确认**（2026-07-18）：主接缝三进三出合同 + 次接缝五段纯函数内核；不在 durable 载体层建测试面。
- **实施顺序建议**（非合同）：三进三出合同类型与骨架 → **DBOS 已锁定（D-041）** ∥ 视频管线接通 → 五段 Harness 逐段落地（①③先行，AI SDK 现行 API）→ 对话层流式与生成式 UI → 资产与 IP 生命周期 → 承接与结果面 → 评估基建全绿。拆票时每票须能追溯到本规格的具体故事编号与实现决策编号。
- **诚实量级**：XL。五类入口 × 三平台 × 成片 + durable 编排 + HITL + 资产系统是一个完整产品面；建议按上述顺序分批拆票，但对用户可见的每个入口以完整合同为开放条件，不交半产品。
