# 开发规格：原地换壳保核 × D-101～D-131 产品合同全量落地（2026-07-25）

> 由 `/to-spec` 从 2026-07-24～25 Office Hours 决策层综合生成。权威来源：`docs/design/beauty-marketing-agent-product-design-2026-07-17.md`（D-101～D-131）、ADR-0013～0019、`docs/specs/bucket-disposition-matrix-2026-07-25.md`（223 行归桶终裁，用户已批准）、`docs/reviews/comprehensive-development-review-2026-07-24.md`（M/R/E 编号源）。冲突以决策日志为准（D-110 元原则：新裁决覆盖旧表述）。

## Problem Statement

单店单人的美业店主没有时间、没有专业能力做持续的宣发内容：写文案要学平台话术，做图要学设计工具，拍视频要学剪辑，发内容要懂各平台规则。现有产品要么是给专业运营用的工具箱（学习成本高），要么是模板套壳（产出千店一面）。

本代码库已有约 55 万行经真机验证的骨架（SaaS 底座、五段 Harness 编排、模型供给链、交付结果面），但当前交付面与 D-101～D-131 锁定的产品合同存在结构性断裂：新租户 Day-0 无法出活（装配失守——供给钩子未接、Harness 未激活）、输入到候选要走 8 步（对标产品 3 步）、图文没有合一交付物、平台变体合同单字段混淆内容语义与分发语义、旧交互面（槽位表单、旧 IA 页、compose/烧录链）与已拍板的对话式主线并存造成双轨混乱。

## Solution

**原地换壳保核（D-127）**：不重开、不整体重写。骨架保留+扩展，退役面真删，前端沿在途 Composer 主干换壳到 D-114 AGUI 对话流，新能力按 ADR-0019 纵切净新建。

交付后的产品形态：店主注册后进入「门店橱窗」风格的工作台，冷态看到三行业示例店、热态每天一条今日主推荐（D-126 冷热分工），一句话即可发起创作（D-043 计数口径：输入一句话到看到流式候选 ≤2 击）；定制主线＝agent 流式对话容器（意图正名→上下文注入→Brief 编译→执行择优→回装交付五段），产出四类输出（文案／图片／图文笔记／视频成片）；门店事实、品牌身份、素材经五步录入范式与 MinerU 解析管线沉淀为可复用资产；生成过程零内容限制、发布确认是唯一风控收口；计费＝套餐三桶（文案/图片/视频）+三类加油包，数字由运营后台手填。

执行序列单一权威（D-110）：**装配门（第 0 步）→ M-01～M-06 合入门 → R-01～R-08 试点/发布门 → E-01 发布工程门**；修复即建设（M/R 级修复直接按 D-101～D-131 当前裁决形态实施）；退役与换壳按归桶矩阵批次执行。

## 接缝（Seams）

沿用既有接缝，不新增（ADR-0019；越高越少越好）：

1. **三进三出 HTTP+SSE 合同**（D-032/ADR-0013，主接缝）——后台给前台只有三类：白话进度事件、需要用户的一个问题（生成式 UI 卡）、成品版本（ContentPackage revision）；前台给后台只有三类：意图（一句话＋场景上下文＋素材）、结构化决定（进决策账本）、信号补记（chips）。合同测试全部打在这一层、覆盖全部六类消息；前后端、四类编译器、计费扣点都经此缝验收。
2. **五段 Harness step 纯函数内核**（D-033/D-038①，次接缝）——step 级单测永不 import durable 载体（DBOS）。
3. **旅程级 e2e**（ADR-0019 DoD）——验收以旅程为单位：真服务启动、真数据点击；装配门「注册→首次出活」是第 0 号 required 旅程。
4. **前端组接缝**（D-131）——前后端同旅程拆票时，接缝合同与属主显式写在票面；前端组内部自闭环不接真后端＝未完成。
5. **非创作旅程接缝**——注册/录入解析/工作区/首页/运营后台/Landing/认证/退役切换不新增接缝类型：一律沿既有 route、command、canonical projection 接缝，每票在票面显式写明所用接缝与唯一属主、消费方（ADR-0019 票面第二要素），拆票时逐旅程落名。

## User Stories

**注册与 Day-0（装配门）**
1. 作为新店主，我要用邮箱+兑换码完成注册（运营可代开账号），这样试点期不依赖短信通道就能进入产品。
2. 作为新店主，我注册后平台已备好默认模型栈（文案=deepseek-v4-pro、图=seedream-5-pro 系、视频=seedance-2 系）与试用额度，这样 Day-0 不用做任何配置就能出活。
3. 作为新店主，我在冷态首页能看到三个行业示例店与示例作品，这样我第一眼就理解这个产品能为我产出什么。
4. 作为新店主，我点击示例任务能真实执行（扣试用额、产物允许导出、口径与正式使用一致），这样试用体验就是真实体验。
5. 作为店主，从输入一句话到看到流式候选 ≤2 次点击、0 个前置表单、0 次前置模型/额度确认，无冲突路径 0 张阻塞卡（D-043 计数口径，e2e 真实计数点击），这样我不会在门槛上流失。

**定制创作主线（对话容器）**
6. 作为店主，我在一个流式对话容器里说一句话就能发起创作，agent 会把我的口语表述正名为创作意图，这样我不需要学任何专业词汇。
7. 作为店主，条件缺失时 agent 用渐进引导轻问补齐（跟着意图走、每次 1～2 项、可跳过）而不是弹表单拦截；引导后仍不满足或我跳过时，自然路由到自由创作先出活、显式告知「本次按通用模式生成」并给升级预告，不静默降级（D-111 分流结果语义）。
8. 作为店主，我能看到 agent 的阶段宣告、确认卡与任务总结都是拟人化交付语言（不出现工程术语、成本价、内部 ID），这样我感到在与专业顾问协作。
9. 作为店主，意图确认卡有默认值并超时自动继续，这样我不回应也不会卡死任务。
10. 作为店主，执行中我可以介入修正（改方向、换素材、调文案），流程接受修正后继续前进而非推倒重来。
11. 作为店主，我提交时确认的平台、交付物与模型设置就是最终执行的设置（服务端签名冻结，无静默覆盖），这样所见即所得。

**自由创作（Pro Studio 已退役）**
12. 作为熟手店主，我可以走自由主线直接下指令生成，不被定制流程绑架。
13. ~~作为高阶店主，我能看到 Pro Studio 入口…~~ **RETIRED（D-170）**：产品无 Pro Studio 入口、加购或画布工作区；自由创作＝模型原生薄路径。退役实施见 `docs/specs/pro-studio-retirement-spec-2026-08-01.md`。

**四类输出——文案**
14. 作为店主，我要一句话产出平台适配的文案（轻输出走五段退化执行），候选以 token 流式即时开始呈现（不设固定数值 SLA；各类超时秒数＝运营参数）。
15. 作为店主，文案候选默认单主候选（择优收窄），我不用在一堆平行选项里做选择题。

**四类输出——图片**
16. 作为店主，我用商家语言描述图片需求：自由创作三入口「生成新图」「修改这张图」「用几张图合成一张」精确映射 image.generate/edit/reference_transform（无第四入口，v1 不开放套图）；定制创作中操作由系统自动选择、我无感——全程不需要懂提示词。
17. 作为店主，图片上的促销价格、门店名等精确文字必须与我确认的事实一致（精确文字校验门），错字图不会交付给我。
18. 作为店主，图片产出走七类语义 slot 的 ImageIntent 合同（subject_person／work_case／store_scene／product／brand_element／style_ref／composition_ref，work_case 的 edit invariants 绑真实性），我改需求时 agent 知道我在改哪个语义位。
19. 作为店主，改图操作按次计入图点额度并在动工前展示用量预估。

**四类输出——图文笔记**
20. 作为店主，我要的「图文」是合一交付物（NotePlan 页级计划：封面/痛点/方案/案例/价格/引导页结构由语义决定），不是文案与图片两次分开提交。
21. 作为店主，图文默认给我双风格草稿（干货科普/种草叙事），配图跟随我选中的版本。
22. 作为店主，单页不满意可以只重生成那一页（计 1 图点），不用全包重来。
23. 作为店主，图文全包在交付前经过五维一致性评估回炉，这样图与文不打架。

**四类输出——视频成片**
24. 作为店主，我要模型原生直出的视频成片（单调用，不走 ffmpeg 拼接链），亮点定位对齐套餐档位（3/6/9 条每月）。
25. 作为店主，视频任务超时或失败时 agent 白话申报并给出补救选项，额度不被白扣。
26. 作为店主，视频产物与图文一样进入统一结果面与工作区，可回看可导出。

**分发与平台变体（M-01）**
27. 作为店主，我只回答「发到哪/用在哪」一个问题，系统内部把它映射为内容变体（小红书/抖音/视频号）与分发方式（导出/手动复制/协办交接/代发）双字段，我不感知工程拆分。
28. 作为店主，朋友圈是交付目标（拿图文去发）而不是变体主体，我选朋友圈时得到的是适合私域转发的成品与协办指引。
29. 作为店主，能否代发在提交前就展示清楚（可代发/生成后导出复制），不存在提交后才报错。

**门店事实与录入（M-02 + 五步范式）**
30. 作为店主，首次录入走五步范式：看示例卡→行业推荐勾选→一句话+拍照代填→AI 编排为结构化草案（字段带 provenance）→逐项确认（AI 推断默认 unconfirmed），每步以代填与勾选为主、可跳过（不新增时长 SLA 承诺）。
31. 作为店主，我上传价目表截图/团购链接后，系统解析提取事实（MinerU 官方 API）、我逐项确认后入门店事实账本；此后创作时已确认事实是第一等满足来源（按满足度三态引用），不会要求我把确认过的事实再上传一遍。
32. 作为店主，上传外部文件解析时我能看到一句温柔的文字提示（数据经第三方解析服务处理），不设门槛不阻断。
33. 作为店主，Recipe 需要的事实（如团购价）优先由我已确认的门店事实满足，不会要求我把确认过的事实再用文本文件传一遍。
34. 作为店主，事实满足度判定为「部分满足」时，agent 按我的意图判断事实关键性：核心事实轻问补齐并顺手入账本，可省略事实直接生成并在结果侧提示；判断失败走引导保守路径（满足/部分满足/不满足三态合同）。
35. 作为店主，过期或已撤销的事实绝不会被用进内容（确定性硬校验），这样我不会发出过时价格。
36. 作为店主，批量录入走异步、单件走同步，我在对话里能看到解析进度而不是干等。

**品牌身份与发布收口（M-03 + D-117）**
37. 作为店主，营销身份建档是向导式的、可跳过的，Day-0 没有身份也能出活——回退为门店官方中性口吻（文案口吻回退，不播种任何中性身份数据实体），身份不是创作的前置闸门；系统对「查询失败/为空/未选择」三态显式区分（M-03）。
38. 作为店主，我有多个身份（门店号/个人 IP）时可显式选择并被记忆为默认，移动端同样能进入身份与素材管理。
39. 作为店主，生成过程零内容限制（允许美化演绎），软提示随行；发布确认是唯一风控收口，AI 生成提醒标识在发布位呈现。
40. 作为店主，发布确认/导出/协办交接按我确认的成品版本（ContentPackage revision）执行，我确认的就是我拿到的；人设域「创建人设」「设为默认」「本次会话选择」三动作显式分离，执行冻结 identity revision、人设相关投影缓存键含 identity revision（D-117）。
41. 作为店主，录入阶段的权利确认（客照肖像授权勾选）是软提示不阻断（D-119）；而生成使用与 dispatch 阶段，敏感素材的权利授权与 dataClass 政策是服务端硬校验（dataClass 服务端推导、dispatch 前重验、resolver 默认只返 metadata/hash、仅选定 Provider 读 bytes），不能被任何流程降级绕过（硬门③/R-03）。

**内容工作区（D-121）**
42. 作为店主，我有一个与租户严格分离的内容工作区，沉淀我的个性资产（作品、素材、事实、身份），按套餐 1/2/3 个+加油包扩容。
43. 作为店主，创作时可以引用工作区资产作为上下文入口，agent 自动注入相关事实与风格。
44. 作为店主，示例店资产（platform_sample）与我的资产隔离展示，不混入我的工作区。

**首页与日常经营（D-126）**
45. 作为店主，热态首页每天给我一条主推荐（确定性规则+行业先验受控配置），推荐说明含三要素——为什么今天适合发、用了本店什么、希望顾客做什么——点击即预填充创作对话，这样我每天打开就知道今天发什么。
46. 作为店主，首页展示我的额度余量与本月产出概览，缺额提醒、超额报停。
47. 作为店主，待办与审批集中在收件箱（批准请求恰一次消费），不会散落各页找不到。

**计费与套餐（D-123/D-124）**
48. 作为店主，套餐额度分三桶（文案点/图点/视频点），用量预估在动工前展示，扣点凭执行回执。
49. 作为店主，额度不够时可买三类加油包，缺额时 agent 提醒并给出选项而不是静默失败。
50. 作为店主，试点期我用兑换码开通付费能力（支付零开发承接），后续升级不换账号。
51. 作为运营，我在后台手填价格与额度数字（数字＝运营参数，线下核算），改数字不用发版。
52. 作为运营，我能人工动态开关/调整试用状态与试用额度，滥用应对靠运营收紧而非预建防滥用系统。

**运营后台（D-107/D-130）**
53. 作为运营，我在模型装配后台分层管理：文本模型供给目录（CatalogModel，默认 DeepSeek 型号可换）与图/视频执行通道（ExecutionChannel，方舟直连主通道、tuzi relay 容灾），带 CAS 审计与回滚。
54. 作为运营，Recipe Studio 让我用受控积木组装行业 Recipe（载体=PG 既有库），不用改代码上新玩法。
55. 作为运营，Skills 是一等能力单元（提示词走 Langfuse 版本化），我能受理、冻结、回滚提示词变更。
56. 作为运营，后台可视化（用量/任务/租户）基于 template-dashboard 组装，与商家前台视觉分离。

**Landing 与门面（D-125）**
57. 作为潜在用户，Landing 页诚实呈现产品当前真实能力（阶段一只改文案与前后链接），不夸大不预售未有功能。

**换壳一致性（D-127/D-130）**
58. 作为店主，全产品（对话容器、作品页、门店页、身份管理）是统一的门店橱窗视觉语言（Glass 主题），不再出现新旧两代界面并存。
59. 作为店主，旧交互面（槽位表单、旧任务收件箱、旧内容库）整批下线后，我在新主线都能完成原有任务，不需要回访旧页面。
60. 作为店主，我的线索台账（到店线索列表与详情、手工跟进）在换壳后保留可用（沿 Composer 主干换壳，不扩功能），不因界面升级丢失。

## Implementation Decisions

**路线与批次**
1. 开发路线＝原地换壳保核（D-127）：KEEP_EXTEND 156 行保留扩展；RETIRE 48 行真删（git rm，分四批：1A 立即删≈36 行/12,764 行代码已批准；1B 迁移完成后删；1C 模型原生视频切换后删；1D 换壳完成后删）；**原 FREEZE 7 行（Pro Studio 系）由 D-170 升格为 RETIRE/真删**——先迁 KEEP audio 能力，再按 `docs/specs/pro-studio-retirement-spec-2026-08-01.md` 阶段删除，不得再「只留入口」；REBUILD 10 行沿 Composer 主干换壳；NEW 8 项纵切净新建。每票动工前查归桶矩阵，禁止在 RETIRE 桶续命、在 REBUILD 桶打补丁。条件删除批机器可判谓词：1B＝迁移票双读零差异、1C＝原生视频链 live_verified＋旧链零流量＋全量基线绿、1D＝换壳票组全部合入＋旧页零路由引用；各批唯一前置票在票包显式声明。
2. 执行序列（D-110）：装配门（第 0 步 required 旅程：注册→默认栈→首次出活；**M-06 并入本批**——开发启动与 Harness 激活单一口径：单一 dev runtime profile、四服务启动 smoke、默认 DBOS system DB、能力缺失显式状态）→ M-01～M-05 → R-01～R-08 → E-01。修复即建设：M/R 级修复直接按 **D-101～D-131 当前裁决形态**实施（D-110 元原则后条覆盖前条，如 R-01 按 D-116/D-118 形态）；每项动工前对照校准。

**领域合同**

## Testing Decisions

1. 好测试＝只测外部行为不测实现：合同测试打在三进三出 HTTP+SSE 缝（覆盖三出三进全六类消息，不止提交→交付物），step 单测打纯函数内核、永不 import durable 载体（既有 harness step 测试为先例）。
2. 旅程 e2e＝DoD（ADR-0019）：真服务启动、真数据点击，fixture 可用但链路必须真走；装配门「注册→首次出活」进 CI required gate（先例：收件箱 e2e、auth e2e）。
3. M-01 验收＝8/8 正式 seed Recipe validator 合同测试（发布时/提交时/seed 三处同一 validator）；M-02 验收＝正式 8 Recipe × ContextBundle 集成测试（替换自造 Recipe 测试）。
4. 七条硬红线走 promptfoo CI 门+评估门既有通路（R-02 补可见文案位覆盖）；拟人化交付语言进评测面。
5. 退役批执行后全量真机基线不回归（先例：core 真机 1167/contracts 35/web 477 全绿基线）；换壳票验收含双主题（亮/暗）与移动端实走。
6. 真 PG/真 DBOS 基线为准（默认 env 门控跳过的持久层用例须在 CI 真机 job 跑）；R-06 双账本类结论只认真 PG 证据。
7. 每条外部集成必须有无凭证可跑的 fixture/种子值默认档：开发与 CI 默认档缺凭证不阻塞、不假红；真凭证到位后按既有 live_verified 门径一次核销，live 核销归供给门票、不进各功能票 DoD（D-132）。
8. M-04 浏览器硬门＝完整主线旅程 e2e（提交→流式候选→采用→交付→刷新恢复）覆盖三模态、绑定新 endpoint/schema；退役链路的旧 fixture/spec 随删除批清理或显式降级，不留监听幽灵。
9. 不可外部观察的架构红线走静态断言门（CI assert 矩阵先例）：新视频链禁 ffmpeg、禁引 agent runtime、唯一 mutation/唯一投影越界扫描、D-123 数字禁硬编码扫描、授权镜像不入库（gitignore 断言）、mount-pending 组件挂载断言。

## Out of Scope

- **E 门业务批（外部资源与商业闭环）**：支付真实通道接入、删除匿名化、取消退款补单、手机号短信登录、部署中国化、MinerU 自托管、平台代发真实账号（`publish:*` 能力门）——触发点到达时另开批次（凭证届时按 D-132 §D 同批索取）。注意：**E-01 发布工程门的仓库内工程（决策 27）在本 spec 范围内**，不随本条排除。
- Pro Studio 解锁/接入/新画布（**D-170 已闭合为全量退役**；实施跟退役规格，不在本 spec 再开「解锁」项）。
- Landing 阶段二精细优化；产品命名**定稿本身**（属主＝用户+运营，R 门收口前完成，票包以 R 门 checklist 依赖项跟踪，不设工程票）。
- 运营/合规执行阶段整体置后（D-040）：预登记、进场仪式、WOZ 人肉运营；结构性护栏（硬失败门/权利门/审计双写/红线 CI）随功能建不置后。
- god module 专项大重构；多店多人协作；**新增** CRM/店务经营能力（库存/预约等；既有线索台账仅换壳保留、不扩功能，见 story 60）。
- 1B/1C 条件删除批的提前执行（机器可判谓词见决策 1，未达谓词不动手）。
