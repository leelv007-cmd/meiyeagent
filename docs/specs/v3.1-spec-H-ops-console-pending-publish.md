# V3.1-H 运营控制面（单列）：Release 装配/审批/回滚台 + Tool Policy 管理 + Kill Switch 面板 + 事故处置

## Problem Statement

V3.1 上线后运营需要回答并执行：现在生产在跑哪个 release？候选表现如何、能不能放量？出事了怎么在一分钟内回滚或关停某能力？工具面的权限与拒绝原因在哪看？——这些操作目前没有面，只能靠工程师改库/改配置。

## Solution

只建 Langfuse 覆盖不了的自建运营面：Release 台（装配/diff/审批/allowlist 灰度/一键 rollback）、Tool Policy 管理、Kill Switch 面板；指标/trace/eval 查看走 Langfuse（releaseId tag 聚合）。配套回滚演练与事故处置流程。

## User Stories

1. As a 运营, I want 看到 production/canary/draft 三态 release 列表与任意两个 release 的可读 diff（prompt/skill/tool/schema/model policy 逐项）, so that 放什么、改了什么一目了然。
2. As a 运营, I want 发布 release 时看到 pack 覆盖校验结果，缺 pin 直接拒绝发布并指出缺哪个 key, so that 不可能发出半供给的 release。
3. As a 运营, I want 以 workspace allowlist 圈定 canary、给单商户指定 candidate release 试跑, so that 灰度粒度到店。
4. As a 运营, I want 看到 candidate 的 gates/thresholds/verdict 结果（scored 只记账），放量按钮由我人工点击（U12）, so that 放量永远有人把关。
5. As a 运营, I want 一键 rollback：新任务切回前一 production release、在途任务保持冻结、rollback reason 与 evidence 强制填写留痕, so that 回滚快且可审计。
6. As a 运营, I want Tool Policy 管理面（说明/参数 schema/side effect/approval/phase/data classes/timeout/调用上限/最近拒绝原因）, so that 工具面权限可治理。
7. As a 运营, I want Kill Switch 面板按颗粒关停（disable_agent_planning / disable_memory_write / disable_memory_read / disable_make_steering / disable_proactive_agent / force_manual_plan_confirmation / force_legacy_five_stage），每个开关显示当前状态与影响范围, so that 事故时不需要总开关一刀切。
8. As a 运营, I want 发布前完成一次回滚演练并留演练记录（周期性演练频率由 ops policy 另定，不在本票），事故时按 V3.1 §42 数据处置（append-only 不删事件、必要时只取消未执行任务并退分）, so that 处置有章法。
9. As a 运营, I want 指标/trace/eval 的查看直接跳转 Langfuse（按 releaseId tag 聚合的固定入口）, so that 不在自建面里找不存在的图表。
10. As a 运营, I want 所有运营写操作（发布/放量/回滚/开关/Tool Policy 编辑）有操作者、时间与理由留痕, so that 运营动作可追责。

## Implementation Decisions

- 自建面范围严格 = Release 台 + Tool Policy + Kill Switch + 操作审计；prompt 指标/trace/dataset/experiment 查看一律 Langfuse（V3.1 §30，D-037「零新增件」精神）。
- Release 装配 = 创建新的 immutable Artifact（一次性动作）；发布/放量/回滚只动 Lifecycle/Rollout（Artifact 不可变，#7 合同）；Tool Policy 编辑只产生新 policy revision，须经新 release 装配后才对生产生效（禁原地改动生产 policy）；percentage/industry 轴与自动回滚门 UI 待触发点（付费 workspace ≥ 50）再加。
- Kill switch 随各开发 spec 引入（V3.1 §41.2 批次归属），本 spec 提供统一面板与审计，不提前创建未生效开关。
- 面板落在管理后台现有骨架内，权限走既有 admin RBAC；不新增第二套后台。

## Testing Decisions

- 主 seam：运营 P1/admin action 边界——发布拒绝（缺 pin）、rollback 语义（新任务回旧、在途冻结）、开关状态变更留痕、越权拒绝。
- Playwright journey：release 发布→canary 圈定→candidate 试跑→人工放量→一键回滚全流程；kill switch 关停后对应能力立即降级且可恢复。
- 先例：现有 admin 后台整备波的 e2e 模式（admin RBAC + 行为断言）。

## Out of Scope

自动回滚门与 percentage 放量 UI（触发点后置）；L2/L3 replay/shadow 操作台（同）；Langfuse 自身的替代或封装；商家侧任何界面。
