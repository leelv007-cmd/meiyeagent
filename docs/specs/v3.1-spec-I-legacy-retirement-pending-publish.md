# V3.1-I Legacy 收敛与退役：三 runner 收敛为单 executor + 旧 UI/旧执行分支退役

> **状态：待发布到 issue tracker**（2026-08-08 发布时 GitHub 账号被自动封禁，#429–#435 已发布成功；本文与 V3.1-H 待账号恢复后补发，label: ready-for-agent）
> 决策权威：V3.1（`docs/design/0808规划/meiye-agent-v3.1-authoritative-plan-2026-08-08.md`）§22.3–22.4、§34.3、§35 批次 6 退役门；硬约束附录 A（A10 D-038 五条、A18 条件位禁副作用）。
> 依赖：#431（门与帧前置迁移已完成）、#433（新交付链全绿）、#435（release 设施可回滚）。**退役前置条件全部满足前不得开工**（见 Implementation Decisions）。

## Problem Statement

新链全量后，仓库同时存在两套真相：三套并列 runner（copy/note/media）与单 executor、旧卡片 UI 与 Workstream、旧 confirmation 语义与确认请求/决定、Thread=Work 假设的胶水代码——双轨每多存在一天，回归面与心智负担就多一天，且新人无法分辨哪条是权威路径。

## Solution

按 V3.1 §22.4 顺序完成三 runner 收敛（内部逻辑替换为六原语 → 收敛为单 `CompiledExecutionPlan → DBOS executor`，五阶段只留 trace taxonomy），随后按退役清单删除旧 UI 与旧执行分支；legacy durable replay 分支设明确保留期限后归档。

## User Stories

1. As a 平台工程师, I want 三套 runner 的重复逻辑先替换为六原语（intent→read_context/ask；brief→generate；execution→generate/check/revise）, so that 收敛前语义先统一。
2. As a 平台工程师, I want 最终只有一条 `CompiledExecutionPlan → DBOS executor` 执行路径，copy/note/media 全部由 typed unit 表达, so that 新增 carrier 不再复制整套 runner。
3. As a 平台工程师, I want 收敛全程满足 D-038 五条（纯函数 step 内核 / at-least-once 幂等 / 大产物对象存储 / 回装段 OCC / 发布排空与版本粘滞）, so that durable 语义不因收敛受损。
4. As a 平台工程师, I want 五阶段只保留为 trace grouping / admin explanation / metrics dimension（与 D-036 一致）, so that 拓扑与观测解耦。
5. As a 平台工程师, I want 退役清单逐项删除：Thread=Work 假设胶水、旧 result conversation glue、重复 planning DTO、第二份 Prompt pack 映射、手工硬编码 Tool allowlist、已无消费者的旧 Harness surface、重复 UI（旧卡片流）, so that 仓库只剩一条权威路径。
6. As a 平台工程师, I want 没有 ExecutionPlanSnapshot 的旧 durable task 在归档条件门满足前继续可恢复（独立 replay 分支），条件门满足并过安全缓冲后归档并 fail closed（U14）, so that 历史任务安全落地。
7. As a 运营, I want 退役每一步可回退（feature flag 逐个翻转，`force_legacy_five_stage` 最后删除）, so that 退役不是单向门。
8. As a 美业商家, I want 退役过程中我的使用体验零变化（新链已是唯一体验，退役只删死代码）, so that 清理对我不可见。

## Implementation Decisions

- **退役前置条件（全部满足才开工，V3.1 §35 批次 6）**：执行确认覆盖所有确认语义；新任务完全消费 ExecutionPlanSnapshot；Interrupt、费用、权利、stale 和 refund 旅程全绿；真实商家试点优于旧流程（试点执行、证据包与不劣化判定归发布 owner，非本票开发范围，本票只消费其结论）；rollback 已演练；legacy durable replay 归档条件门已定义并纳入监控（U14：零 active/pending 旧实例 + 最长 hold 窗口 30d 走完 + 审计导出与回滚证明齐备 + ops policy 安全缓冲，之后归档 fail closed）。
- 收敛顺序严格按 V3.1 §22.4（门与帧已在 #431 迁出为独立模块，本 spec 做步骤 2-3）。
- 行号引用以 symbol 为准（2026-08-08 快照见 V3.1 §22.4），开工前复核。
- 删除以「消费者证明门」为准：每个待删 surface 先证明零消费者再删（承接仓库既有关票纪律）。
- in-flight durable 实例处理走发布 SOP：排空/版本粘滞，不热切。

## Testing Decisions

- 主 seam：DBOS durable 测试缝——收敛前后同一 fixture 任务集的行为等价断言（交付物、结算、恢复语义逐项对比）；kill/restart 重复副作用=0。
- 现有全量 journey（V3.1 §37.4 A–K）在收敛后必须全绿，作为等价性的最终门。
- 退役每一项配「消费者为零」的构造性检查（grep 级 + 运行时引用计数二选一，取现有关票纪律先例）。

## Out of Scope

任何新功能；percentage 放量与自动回滚门（触发点后置）；`references/` 镜像与历史文档清理。
