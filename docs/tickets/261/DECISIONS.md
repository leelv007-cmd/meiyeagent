## D5 · 规划成本反馈：D-164⑥C 与 D-109 正面冲突（**优先级最高，决策 vs 决策**）

- 状态：**PENDING**
- 冲突两端（两条都是 `accepted` 决策原文，不是票面误写）：
  - **D-164⑥ 决定 C**（`docs/design/beauty-marketing-agent-product-design-2026-07-17.md` D-164 段）：「确认卡弹出前的规划推理**已经产生真实成本**，即便商家点『拒绝』也已发生。此成本**必须计入并明示**，不得让商家以为『拒绝＝没花钱』。」其证据是 Miora 实测（709.00 → 629.35，拒绝仍扣 79.65）。
  - **D-109**（同文件 `:1871`）：「一个用户主动任务只产生一笔产品权益预占。内部 **Planner**、LLM、图片/视频调用、评估、质量淘汰、fallback、系统重试和同 supplier task 恢复分别进入 **ProviderCost Ledger**，**不重复扣用户**」；并另定「**供应细节不可见**」（`:1865` / `:2082`「内部成本基准…**永不进前台**」）。
- 冲突性质：**Miora 的失效模式在本产品结构上不成立**——它的病根是「规划扣用户余额却不告知」，而本产品规划成本按 D-109 合同**根本不进商家额度桶**。商家点拒绝时，商家侧真实消耗**确实是 0**。
- 推论：若照票面验收「就地出现本次规划消耗反馈，金额＝真实消耗」实现，等于**凭空造一个不存在的扣费**，反而违反 D-109 的可信度基础，也违反「供应细节不可见」。
- 主控建议：**取「明示本次未消耗额度」**——拒绝反馈文案＝「已取消，本次没有消耗额度」，代码注释写明依据 D-109 ＋ 本次裁定。这既兑现 D-164⑥C 的立法意图（不让商家对成本状态误判），又不破 D-109。
- 若用户裁定「规划成本要计入商家桶」：那是**改 D-109**，须开新决策 + 后端加 `stage` 维度（`apps/core/src/p1/product-billing/provider-cost-snapshot.ts:16-32` 现只有 `attemptId/taskId/deploymentId`），**不在 #261 范围内**。
- 裁定：
