# 美业宣发经营 Agent：UI / UX 调整方向建议（完整版）

## 结论

**不建议把 Dashboard 继续做成“更大的聊天页”，也不建议退回“场景卡片货架”。最合适的目标形态是：一个单路由、随任务状态动态变形的 Agent 工作台。**

同一个页面应完成三种角色转换：

1. **待命时**：像一个极简任务入口，主动告诉商家今天值得做什么。
2. **执行时**：像一个可持续协作的 Agent 时间线，承载补问、计划、确认、进度和恢复。
3. **交付后**：像一个面向成品的对象工作区，允许查看、修改、采用、导出和再创作。

你们的最新产品方向已经给出了正确骨架：定制创作采用 Agent 流式对话，结果卡作为进入对象工作区的入口；Dashboard 使用“轻推荐＋创作面＋继续上次工作”；前台主轴是文案、图文、视频三类输出，而不是把五类宣发任务做成一级导航。仓库里 2026 年 7 月 29 日的 D-164 又进一步收敛为“单路由三段”，并将记忆提升为一级入口。

因此，下一轮不应再推翻信息架构，而应把现在的**静态三段页面**进一步升级为**状态自适应的 Agent Session Surface**。

# 一、对当前实现的判断

附件记录的产品方向状态是“已接受、研究开放”，仓库主分支则已经继续推进到 D-164 之后，因此下面以“附件中的产品合同＋仓库当前实现”共同作为判断基础。

## 已经做对的部分

当前代码已经具备相当完整的 Agent UI 基础：

- Dashboard 已按照“问候语 → 提议位 → 创作面 → 继续上次工作”组织。
- 定制创作提交后不立即跳转，进度、补问、候选和交付继续留在当前容器。
- 对话流中已经有身份卡、补问卡、进度卡、候选流、成品交付卡、恢复卡等类型化帧。
- 文案、图文、视频 lens、配方 pill、执行确认、额度提示、素材上传和异步恢复都已经接入。
- 一级导航已经包含工作台、内容、素材、门店、记忆。
- HeroUI Pro、Motion、`react-resizable-panels`、`cmdk`、Vaul、React Aria 等关键前端能力已经在依赖中，不需要为下一轮 UI 再换栈。

## 当前主要问题不是“缺 Agent 组件”，而是“Agent 组件仍然像模块拼装”

### 1. 页面状态不会随任务变化

当前页面始终纵向保留提议、创作和继续工作三段。对冷态首页是合理的，但进入执行后，顶部推荐和底部历史仍然占据空间；对话区本身又有最高约 70svh 的内部滚动，输入框位于对话区下方，容易形成“页面滚动＋对话区滚动”的双重滚动。

### 2. “今日建议”仍然过重

当前推荐卡完整展示标题、正文以及“为什么现在／用了本店什么／希望顾客做什么”三栏。信息合同是正确的，但作为 Composer 之前的主入口，它在视觉重量上容易与真正的创作入口争夺首屏。

### 3. 候选流与交付卡存在重复阅读风险

当前“流式候选”和“成品交付卡”是两个独立帧：候选流先完整展示内容，任务完成后又追加一个包含摘要、版本、评价、动作 chip 和三个操作入口的交付卡。技术语义正确，但视觉上容易让商家感觉“同一份东西出现了两遍”。

### 4. “继续上次工作”过弱

现在这一段本质上是一组带下划线的文字链接，缺少成品缩略图、真实阶段、下一步动作和是否需要商家处理等信息。对 Agent 长任务而言，它还不足以承担“时间桥”。

### 5. “记忆”已经升为一级入口，但产品化尚未完成

当前记忆页是四个纵向白瓷区块，其中三个领域明确显示尚未建设；非字符串值还可能直接 `JSON.stringify`。这适合作为工程占位，不适合作为商家能感受到“产品越来越懂我”的核心留存界面。

### 6. 当前中心列宽适合文案，不适合媒体成品

Dashboard 使用 `max-w-3xl`，对对话和文案很合适，但当图文套图、视频、来源证据和版本信息同时出现时，单列会迫使大量纵向堆叠。

# 二、推荐的目标形态：State-Adaptive Agent Workbench

逻辑上继续保留 D-164 的三段，但物理呈现不应永远固定。页面应至少有以下四种状态。

## 1. Idle：待命态

适用于 Day-0 或当前没有活跃任务时。

```text
┌──────────────────────────────────────────┐
│ 嗨，XX 店主，今天想发点什么？               │
│                                          │
│ 今日建议：换季前适合发一次头皮护理科普        │
│ 用了：头皮护理项目 · 主理人口吻    [用这条]   │
│                                          │
│ [定制创作]  [自由创作]                     │
│ [文案] [图文] [视频]                       │
│ [案例种草] [活动套图] [专业科普] [更多做法] │
│                                          │
│ 说一句今天想做什么……              [开始]   │
│ + 素材   发到哪   本次预计使用 1 条文案额度   │
└──────────────────────────────────────────┘

继续上次工作
[缩略图] 春季染发活动 · 已完成 · 继续调整
[缩略图] 抖音成片 · 正在生成 · 查看进度
```

这时推荐、示例店和快捷配方可以充分出现，因为它们承担降低空白输入成本的职责。

## 2. Active：执行态

用户开始任务后：

- 今日建议折叠成顶部一条小型 context strip，或者完全退出视线。
- “继续上次工作”退出主页面，进入侧栏任务入口或底部任务抽屉。
- 对话时间线扩展为页面主体。
- Composer 从居中大卡通过 Motion `layout` 动画下沉为**底部粘性输入栏**。
- 当前需要处理的补问卡或执行确认卡固定在输入栏上方。
- 页面只保留一个主要动作。

这样可以避免用户在活跃任务中还看到大量“开始新任务”的入口。Motion 原生支持通过 `layout` 和 `layoutId` 完成可中断的布局过渡，与你们已经安装的 Motion 体系完全匹配。

参考：<https://motion.dev/docs/react-layout-animations>

## 3. Waiting：长任务态

图片和视频任务进入等待时，不应只展示 Loader。

建议让任务卡至少包含：

- 当前正在做什么，例如“正在生成 4 张活动套图”。
- 已完成阶段与当前阶段。
- 商家是否可以离开。
- 预计是短等待还是长等待，但不承诺不可靠的精确时间。
- “离开继续处理”“取消任务”“查看运行说明”。
- 返回后精确恢复到同一个 Task 和 revision。

Replit Agent 的 checkpoint 模式值得借鉴的不是开发者 UI，而是它把长任务的阶段、稳定状态、恢复和成本绑定到明确节点，而不是只展示一根持续转动的进度条。

参考：<https://docs.replit.com/references/version-control/checkpoints-and-rollbacks>

## 4. Delivered：交付态

任务完成时，建议让**候选流原位变形成成品卡**，不要在下面再追加一个近似重复的交付摘要。

例如：

- 文案：从流式文本自然转为小红书／朋友圈真实排版预览。
- 图文：从生成状态转为封面＋前两页缩略图＋总页数。
- 视频：转为封面图、时长、比例和播放入口，不自动播放。
- 保留评价图标、2～3 个后续动作 chip。
- 只保留一个主动作，例如“继续完善并交付”；采用、导出、版本等进入次级菜单。
- 点击成品本身才打开深层结果工作区。

这会让用户感知为“Agent 把工作交到我手上”，而不是“聊天结束后又给了一个任务卡”。

# 三、Dashboard 各区域的具体调整

## 1. 今日建议：从大卡改为 Recommendation Strip

D-126 要求的三个要素不应删除，但可以分层呈现。

### 默认折叠态

```text
✨ 今天建议发：换季头皮护理科普
依据：头皮护理项目 · 主理人口吻   目标：引导预约
[用这条]  [为什么推荐]
```

### 展开后

再显示：

- 为什么适合今天。
- 使用了哪些本店事实和素材。
- 希望顾客采取什么行动。
- 推荐依据更新时间。
- 可替换的项目、身份或 CTA。

### 具体规则

- 桌面默认不超过两行正文。
- 移动端只显示标题、两个依据 chip 和“用这条”。
- “用这条”只预填，不自动发送、不扣额度。
- stale／pending 状态应收缩成一行诚实说明，不使用同等尺寸空卡。
- 当用户开始任务，推荐条自动折叠。

这既保留 D-126 的解释性，也避免推荐抢占 Composer 的主入口地位。

## 2. Lens 与配方：输出类型是一级，配方是轻量第二级

继续保留：

```text
文案 | 图文 | 视频
```

但建议首页只展示当前 lens 下最相关的 3～4 个配方：

```text
案例种草   专业科普   活动促销   旧内容换平台   更多
```

五类宣发任务仍然是 Recipe 的后台分组维度，但不必把每一组 legend 和多行 pill 全部展开在首屏。当前 `RecipePillRow` 会按照宣发任务分组渲染 fieldset，条目增长后很容易重新演变成场景货架。

建议：

- 首页：3～4 个强相关入口。
- “更多做法”：进入可搜索的完整目录。
- 配方切换只修改草稿，保留用户原文和素材。
- 发生参数、模型或 lens 冲突时才展示差异确认。
- 配方 pill 不显示“Skill”“Workflow”等内部术语。

## 3. 定制创作与自由创作：同一壳，不同显露深度

### 定制创作

默认模式。主界面只展示：

- 交付物类型。
- 发到哪里。
- 素材。
- 当前身份。
- 本次额度。
- 必要的补问与确认。

模型、Provider、Profile、路由等隐藏。

### 自由创作

切换后，在相同 Composer 内展开：

- 公开模型。
- 模型原生任务类型。
- 比例、时长、数量、分辨率。
- 参考素材角色。
- 当前额度。

不要跳到另一套首页，也不要让 Pro Studio 代替自由创作的基础路径。

## 4. 对话区域：采用“文档时间线”，而不是聊天气泡

推荐的视觉层级：

- 商家输入：可以保留一个轻量右对齐气泡。
- Agent 阶段说明：全宽文本行或 progress rail。
- 补问：全宽生成式 UI 卡。
- 执行确认：全宽只读确认卡。
- 候选／成品：全宽媒体卡。
- 失败与恢复：全宽状态卡。
- Agent 普通回复不要全部套气泡。

不应展示原始 chain-of-thought、工具日志或模型内部推理。AG-UI 把流式事件、结构化消息、HITL 中断和前后端状态同步作为标准构件，同时明确将“可视化思考步骤”与原始思维链区分开来，适合作为你们类型化帧协议的参考。

参考：<https://docs.ag-ui.com/>

## 5. Composer：初始居中，执行后粘底

建议实现一个 morphing composer：

### 空闲时

- 白瓷大卡。
- 高度较大。
- 显示 lens、配方、附件和目的地。
- 位于首屏中部。

### 进入会话后

- 通过布局动画移动到中心工作区底部。
- 保持在当前视口可见。
- 对话区域独立滚动。
- 底部导航和虚拟键盘打开时正确避让。
- 移动端键盘打开后暂时隐藏底部五项导航。

当前移动端底部导航固定占用约 4.25rem，再叠加未来粘底 Composer 时必须建立明确的 keyboard／safe-area 状态，否则两者会竞争底部空间。

## 6. 执行确认卡：只确认，不配置

现有 D-164 方向是正确的：

- 展示“将做什么”。
- 展示商家可理解的规格。
- 展示本次使用多少额度。
- 只有“返回调整”和“确认执行”。
- 参数修改回到前一层，不在确认卡里编辑。

建议文案使用业务语义：

```text
将生成 4 张 3:4 竖版活动套图
适合小红书和朋友圈使用
使用 4 张图片额度，完成后还剩 16 张

[返回调整] [确认生成]
```

不要显示 endpoint、模型内部尺寸枚举、供应商单价或 Token。

## 7. 继续上次工作：升级为 Activity Shelf

当前纯链接应改为最多三张紧凑对象卡：

```text
[封面] 春季染发活动套图
正在生成第 3/4 张
查看进度 →

[视频封面] 15 秒护理项目成片
需要你确认封面
处理一下 →

[文本图标] 朋友圈项目介绍
昨天完成
继续调整 →
```

每张只显示：

- 缩略图或媒介图标。
- 商家意图摘要。
- 真实状态。
- 更新时间。
- 一个状态驱动动作。

“所有历史”仍进入内容／最近活动页。长任务待办可以借鉴 Linear Inbox 的“只聚合需要注意的事项＋明确下一动作”，但不能把 Dashboard 变成 SaaS 待办中心。

参考：<https://linear.app/docs/inbox>

# 四、结果工作区应该采用“对话＋对象工作区”双层模式

D-114 把 Result Center 定位为“放大镜”是正确的。建议桌面端再进一步做成可展开的双栏，而不是始终跳整页：

```text
┌──────────── Agent 时间线 ────────────┬──── 成品工作区 ────┐
│ 商家意图                              │ 小红书笔记预览       │
│ Agent 进度                            │ 封面 / 5 页套图      │
│ 补问与调整                            │ 版本 3               │
│                                      │ 本次依据             │
│ [粘性 Composer]                       │ 导出 / 交付          │
└──────────────────────────────────────┴────────────────────┘
```

建议行为：

- 点击成品卡后，桌面端右侧展开 Result Inspector。
- 用户可以拖动宽度。
- 可一键扩展为完整 Result Center。
- 移动端直接进入全屏 Result Center。
- 关闭右侧工作区后仍回到同一对话和滚动位置。

Claude Artifacts 使用“主对话＋右侧独立内容窗口”，支持版本切换、复制和下载；ChatGPT Canvas 同样把需要持续编辑的对象从普通聊天中分离出来，并支持定点修改和历史恢复。这两个产品更适合参考“结果对象的纵深”，而不是参考它们的通用聊天首页。

参考：

- <https://support.anthropic.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them>
- <https://openai.com/index/introducing-canvas/>

你们已经安装 `react-resizable-panels`，可直接承担桌面双栏、折叠和布局恢复，无需增加新依赖。

参考：<https://github.com/bvaughn/react-resizable-panels>

# 五、“记忆”应该改造成可感知的经验系统

我建议前台显示名称从技术性的**“记忆”**调整为商家语言的**“经验”**，内部路由和对象名仍可保持 memory。

## Dashboard 内的三处露出

### 1. 执行前：本次使用了什么

```text
本次会参考：
主理人口吻 · 少促销感 · 小红书先讲问题再讲项目
```

点击进入右侧“本次依据”面板，而不是审批。

### 2. 交付后：非阻塞沉淀建议

```text
我注意到你最近 3 次都把“立即购买”改成了“私信了解”。
要设为“小红书项目种草”的默认表达吗？

[以后这样] [仅这次] [调整范围]
```

### 3. 用户纠错时

用户说“她不是老板，是店长”，应进入事实纠错；用户说“这次不要写价格”，只作用当前任务。两者必须在 UI 上使用不同反馈。

## 经验页的信息架构

不建议继续使用四个并列大区块。建议默认进入：

1. **待确认**：系统观察到、等待商家确认的经验。
2. **已经学会**：当前有效的门店偏好、表达身份、常用做法。
3. **我的纠正**：商家明确纠正过的事项及适用范围。
4. **来源记录**：每条经验为何出现、来源任务和时间。

每条经验卡应显示：

- 商家语言陈述。
- 适用范围。
- 来源和观察次数。
- 当前状态。
- 记住、拒绝、调整范围、删除。

绝不能把结构化值直接序列化成 JSON 给商家。当前实现中的这一点应列为 UI P0 修复。

# 六、视觉设计方向

现有“门店橱窗／玻璃＋白瓷”设计系统可以保留，不需要重做品牌视觉。它已经明确规定内容是主角、玫瑰金只用于 AI 时刻、正式支持双主题。

下一阶段建议进一步收紧使用边界：

## Glass 只用于壳，不用于所有内容

适合 Glass 的位置：

- 侧栏。
- 底部移动导航。
- 粘性 Composer。
- 浮动任务状态。
- 轻量 chip 和 popover。

适合白瓷的区域：

- 补问卡。
- 执行确认。
- 成品预览。
- 事实冲突。
- 记忆建议。
- 结果工作区。

避免玻璃卡里继续嵌套玻璃卡。

## 氛围背景只服务待命态

- Idle 时保留磨砂渐变和问候语。
- 进入执行后降低背景对比，让工作区更接近中性画布。
- 结果工作区展开后，媒体内容成为真正视觉主角。
- 不要让氛围图、推荐卡和成品同时争夺注意力。

## 宽度动态变化

- 对话态：约 760–840px。
- 图文／视频工作区展开：整体扩展至约 1180–1280px。
- 右栏默认约 320–420px，可拖动。
- 不要全程把媒体成品压在 `max-w-3xl` 中。

## 动效只表达状态变化

使用 Motion 完成：

- 推荐条折叠。
- Composer 居中→粘底。
- 补问卡进入与退出。
- 候选流→成品卡形变。
- Result Inspector 展开。
- 版本替换后的局部高亮。

不要给每个按钮、卡片和背景持续加动效。

# 七、开源项目与组件使用建议

## 优先复用现有栈

| 能力 | 建议 |
|---|---|
| HeroUI 3 / HeroUI Pro | 继续作为壳、Popover、Dialog、ListBox、Autocomplete、Tabs、AI Chat 组件来源。HeroUI 的交互组件基于 React Aria，具备键盘导航、读屏提示和焦点管理。参考：<https://heroui.com/en/docs/react/components/autocomplete> |
| React Aria | 图片套图排序、列表选择、拖放优先使用 React Aria 的可访问交互，不必为了排序再引入另一套拖放体系。其拖放支持鼠标、触摸、键盘和读屏等价路径。参考：<https://react-spectrum.adobe.com/dnd> |
| Motion | 用于 Dashboard 状态变形、Composer 移位、结果面板展开，仓库已有依赖。参考：<https://motion.dev/docs/react-layout-animations> |
| react-resizable-panels | 用于桌面对话／成品双栏和用户布局记忆，仓库已有依赖。参考：<https://github.com/bvaughn/react-resizable-panels> |
| cmdk | 用于“全部配方／全部创作能力”的搜索式命令面，仓库已有依赖；它本身是可组合的 command menu／combobox。参考：<https://github.com/pacocoursey/cmdk> |

## 适合参考，但不建议整体迁移

### AG-UI

最适合借鉴：

- 类型化事件。
- 中断／恢复。
- generative UI。
- 共享状态。
- 前端工具调用。
- 长任务事件流。

AG-UI 是 MIT 开源、传输无关的事件协议，可以工作在 SSE、WebSocket 等通道上。你们可以把现有“三进三出＋SSE”映射到其事件语义，但没有必要因此替换 DBOS、ContentPackage 或账本真相。

参考：<https://github.com/ag-ui-protocol/ag-ui>

### assistant-ui

适合参考：

- Thread viewport。
- 自动跟随最新消息。
- Composer。
- 附件。
- ActionBar。
- inline approval。
- generative UI。

它可以连接 Vercel AI SDK、AG-UI、LangGraph 或自定义 runtime，但你们当前已经有 HeroUI Pro ChatConversation 和自己的 canonical task/session，**不建议整体接入 AssistantRuntimeProvider**。更适合做隔离原型，吸收 Thread 的滚动、焦点和消息 action 设计。

参考：<https://www.assistant-ui.com/docs/ui/thread>

### Vercel AI Elements

AI Elements 提供 Conversation、Message、PromptInput 等可复制进代码库的 shadcn 组件。对新项目很有价值，但你们已有同类 HeroUI Pro 组件，不应形成第二套视觉组件库；可以阅读其源码，参考消息部件的拆分方式。

参考：<https://github.com/vercel/ai-elements>

### LangChain Agent Chat UI

值得研究：

- Tool Call 与中断渲染。
- Artifact 右侧面板。
- 线程恢复。
- 状态分叉。

但不要为使用这套 UI 引入 LangGraph runtime。它更适合作为交互原型仓库。

参考：<https://github.com/langchain-ai/agent-chat-ui>

## 有条件再引入

- **TanStack Virtual**：只有对话、任务或记忆列表实际达到上百条并出现性能问题时引入；目前不应先虚拟化短列表。参考：<https://tanstack.com/virtual/latest/docs/framework>
- **Tiptap**：只在文案／图文结果中心确实需要长文档局部选择、块级编辑和复杂格式时使用；不要把它放进 Dashboard Composer。Tiptap 的核心是基于 ProseMirror 的 headless 编辑器，适合对象工作区，不适合普通任务入口。参考：<https://tiptap.dev/docs/editor/getting-started/install/react>
- **React Flow**：继续限定在内部后台的能力依赖或 Workflow 可视化，不进入商家 Dashboard。

# 八、明确不建议的方向

1. **不做左侧大量会话列表＋右侧聊天的通用 ChatGPT 克隆。** 你的核心对象是 Task、ContentPackage、资产和经验，不是 message thread。

2. **不把 Dashboard 做成工具市场。** 模型、Skill、工具和配方都应服务当前任务，不应让商家先找工具。

3. **不显示原始工具调用、Provider、模型路由或 chain-of-thought。** 只显示商家可理解的计划、进度、依据和结果。

4. **不让推荐、Composer、任务列表、额度卡和工具卡同时争夺首屏。**

5. **不为 Agent 化增加更多确认。** 一个任务同一时刻最多一个阻塞节点；确定性编辑零确认，重新调用模型才走现有执行确认。

6. **不让“记忆”成为一个孤立的管理页。** 经验必须在任务前、交付后和纠错时持续可见，否则一级导航本身不能产生留存感。

# 九、建议实施优先级

## P0：先解决主入口的 Agent 感知

1. **Dashboard 状态自适应**：Idle／Active／Waiting／Delivered 四态。
2. **Composer 居中→粘底**，解决双滚动和移动端键盘问题。
3. **推荐卡压缩为 recommendation strip**。
4. **候选流原位转成交付卡**，减少重复帧。
5. **交付卡增加真实媒介预览**，而不是只有文字 excerpt。
6. **继续上次工作升级为三张状态对象卡**。
7. **记忆页去 JSON、默认展示待确认经验**。

## P1：增强对象工作区

1. 桌面端右侧可展开 Result Inspector。
2. 文案／图文／视频各自使用媒介专属工作面。
3. “本次依据”侧栏统一展示事实、身份、素材、Recipe 和经验。
4. `cmdk` 承接完整配方／能力目录。
5. 长任务全局 task dock 与站内通知收敛。

## P2：形成真正的个性化复利

1. 基于结果评价和修改行为生成 Memory Proposal。
2. 推荐卡解释哪些经验影响了本次建议。
3. 动作 chip 根据 Recipe 和当前结果动态选择，但必须由受控集合生成。
4. 建立“经验被采用后是否提高小改采用率”的评测，而不是只统计记忆条目数量。

# 十、验收指标

这轮 UI 重构不应以“做了多少组件”为完成标准，建议至少验收：

- 冷态进入后，Composer 是否无需滚动即可看到。
- 一句话到首个可判断结果的显式操作次数。
- 推荐预填后进入真实生成的比例。
- 补问卡的回答、跳过和放弃率。
- 长任务离开后恢复成功率。
- 成品卡到“采用／继续调整／导出”的转化。
- 后续动作 chip 点击率及点击后的真实完成率。
- 记忆建议的确认、拒绝和范围调整比例。
- 使用已确认经验的任务，其直接采用／小改采用率是否提高。
- 390×844、320×720、桌面 1440×900、200% 缩放和 reduced-motion 下是否都只有一个主要动作、没有双重焦点或底栏遮挡。

**最核心的判断标准是：用户是否感觉自己在和一个“越来越懂本店、能持续把事情做完的宣发 Agent”协作，而不是在操作一组已经接上 AI 的表单和卡片。**
