# Web First Product Fit

审查日期：2026-07-06  
审查对象：美业到店 + 医美/医疗资质准入制商家创作副驾 P0  
结论性质：产品端形态决策，不是 UI 详细设计。

## Question

Web 优先到底是开发偏好，还是符合本产品特性的产品选择？需要结合功能闭环、用户使用场景、竞品形态、平台发布能力、合规审计和后续移动端/桌面端扩展边界做综合判断。

## 结论

Web 优先不是单纯开发偏好，而是 P0 当前产品特性下的正确主线；但准确表述应是：

> P0 采用 Web 控制台优先，移动端作为素材采集、发布检查、线索补录和提醒确认 companion，桌面原生延后。

原因是 P0 的核心不是“在手机里拍摄和剪辑”，而是把门店档案、真实素材、内容版本、多平台发布包、医美/医疗资质准入轻量版、线索台账、用量账本和审计记录组织成一个可持续运营系统。这个系统更像 B2B SaaS control plane，而不是单点移动工具或本地剪辑软件。

## 功能维度

适合 Web 优先的功能：

- 门店档案、项目价目、账号状态、素材授权、内容版本、发布包、线索台账、周报和客户成功后台都是多对象管理，适合大屏表格、侧栏、筛选、批量操作和审计视图。
- 医美/医疗资质准入轻量版需要展示资质、广告审查、平台规则、AIGC 标识、素材授权和提示留痕；这类核验更适合结构化 Web 表单和留痕流程。
- P0 默认 L3 发布包，不承诺全平台自动发布。Web 可以生成可复制、可下载、可转发、可扫码交接的发布包，不依赖移动端平台 SDK。
- 图文渲染、AI 生成、合规检查、发布包导出和用量扣费都应在服务端完成，客户端主要是控制台，不需要桌面本地算力。

不适合 Web 独占的功能：

- 门店素材大多来自手机拍摄。
- 商家最终发布小红书、抖音、点评等内容时，很多动作仍会回到平台 App。
- 咨询、加微、预约、核销等线索常发生在手机端，移动补录入口会明显降低摩擦。

所以 Web 是主工作台，移动端是高频入口；两者是主次关系，不是二选一。

## 用户维度

P0 用户不是专业运营团队，而是老板、前台或店员。这个事实不能直接推导出“移动 App 优先”，因为他们的任务分两类：

| 用户任务 | 更适合端 | 原因 |
|---|---|---|
| 拍照、上传、临时补素材 | 手机 / 移动 Web | 素材天然在手机相册里 |
| 首次建档、价目表、项目、人设、禁忌话术 | Web | 信息多、需要整理和复核 |
| 生成本周内容、比较 3-5 条候选、批量改平台变体 | Web | 大屏更适合并排比较和批量编辑 |
| 医美/医疗发布前核验 | Web 优先，移动可确认 | 核验项多，需要清楚展示和留痕 |
| L3 发布包交接 | Web 生成，手机发布 | 发布包可通过二维码、复制、下载或分享转到手机 |
| 线索补录 | 移动优先，Web 汇总 | 线索发生在聊天/平台 App 中，但复盘适合 Web |
| 客户成功陪跑、后台查看、问题排查 | Web | 需要跨商家、跨内容、跨状态管理 |

如果 pilot 发现老板几乎不打开电脑，结论也不是推翻 Web 主线，而是 P0 必须把 Web 做成响应式/PWA，并优先打通手机上传、扫码打开发布包和移动线索补录。

## 竞品维度

公开竞品形态支持“Web 控制台 + 移动 companion”的判断：

- Canva Business 把内容计划、日历、发布、协作、审批和数据洞察放在一个平台里，同时强调从 desktop 到 mobile app 管理资产，说明内容管理类产品通常不是纯移动端。
- Buffer 的核心能力包括 Create、Publish、Analyze、Community、Collaborate，支持多平台排期、AI assistant 和移动 App；它的移动端是随时管理账号的补充，不是替代 Web 控制台。
- Hootsuite 明确是“Everything social. One place”，强调 AI、内容计划发布、社交 inbox、洞察和大量集成，典型是 Web 管理台范式。
- Sprout Social 的移动 App 价值在于随时访问内容日历、社交 inbox 和工作流，能排期、排队、草稿和发布，但它被描述为把平台能力带到手机上，说明移动端更像 companion。
- 剪映/CapCut 同时强调电脑端和移动端，适合视频剪辑、素材处理、数字人和专业创作场景。如果本产品头牌变成视频剪辑器，桌面/移动原生权重会上升；但 P0 现在不是剪辑器，而是门店内容运营副驾。

竞品启发不是“大家都有 Web 所以我们也做 Web”，而是：一旦产品涉及多账号、多内容、多状态、多审批、多团队、多平台，Web 控制台天然是主阵地；移动端承担即时采集和通知。

## 平台发布能力维度

本地平台能力矩阵已经决定 P0 默认 L3 发布包：

- 小红书没有普通商家笔记自动发布 API 证据，P0 只能承诺 L3；L2 浏览器辅助已移出 P0，后续仅在 pilot 发布耗时数据支持后重评。
- 美团/点评更适合后续线索、核销、评价和经营数据接入，不适合作为内容自动发布承诺。
- 微信公众号、抖音可以做官方能力验证，但都必须先 account-level verified。

这意味着 P0 不是“手机上一键发布到所有平台”的产品。Web 控制台生成稳定发布包，再让商家在平台 App 或 verified 官方通道完成发布，更符合真实平台约束。

## 技术维度

Web 优先还能降低 P0 的工程风险：

- 直接复用 `mkfast-template` 做 SaaS App Shell，最快跑通登录、工作台、设置、支付、上传和后台。
- Core API/Postgres 作为事实源，天然服务 Web 控制台、移动 Web、未来小程序或原生 App。
- Agent Service 和 Worker Pool 都是服务端边界，Web 客户端只需要显示状态、触发任务和确认结果。
- 原生移动 App 会引入 App Store/应用市场审核、双端开发、推送权限、相册权限、兼容性和版本发布成本，对 P0 的验证目标不是必要条件。
- 桌面原生会引入安装、升级、权限、浏览器自动化和本地文件安全问题；除非 P1/P2 需要强本地剪辑或稳定浏览器辅助，否则不应前置。

## 风险

Web 优先的主要风险不是工程，而是商家使用场景：

- 如果门店老板没有电脑使用习惯，纯桌面 Web 会卡住 onboarding。
- 如果素材上传路径不顺，真实素材库会成为瓶颈。
- 如果发布包从 Web 到手机交接麻烦，L3 的节省时间会被抵消。
- 如果线索台账只能在 Web 录入，商家可能不会持续记录。

这些风险需要通过移动 companion 化解，而不是通过一开始做完整原生 App 化解。

## 产品建议

P0 端形态建议：

1. Web 控制台优先：创作台、内容库、素材库、账号中心、发布包、线索台账、周报、合规核验、客户成功后台。
2. 移动 Web/PWA 必做轻入口：手机上传素材、扫码打开发布包、复制文案、查看发布 checklist、线索快速补录、合规确认提醒。
3. 不做原生移动 App：除非 pilot 数据显示移动 Web 无法完成素材上传/发布包交接，且 3-5 家付费样本明确因 App 缺失流失。
4. 不做桌面壳：除非后续 L2 浏览器辅助重启评估或本地视频/图片编辑成为付费核心，且 Web 方案验证无法满足。
5. P0 验收增加端形态指标：素材上传来源、首次建档设备、内容审阅设备、发布包打开设备、线索补录设备、每条内容从 Web 到平台 App 的交接耗时。

## 决策

Web 优先是真正符合当前 P0 产品特性的选择，不只是开发偏好。它的产品定位应该写成：

> Web-first SaaS control plane with mobile companion workflows.

如果中文表达，建议写：

> 云端 Web 工作台优先，移动端负责素材采集、发布交接、线索补录和确认提醒。
