## 一、数据模型（API 实测合同）

`GET /api/persona/detail?id=24070` / `POST /api/persona/save` 请求体：

```json
{
  "platform": "xiaohongshu",            // 单平台绑定，一人设一平台
  "name": "阿楠",                        // ≤20 字，AI 起名
  "avatar": "persona_avatar3.svg",       // 预置头像库自动分配（/api/persona/avatar/list）
  "tracks": ["美护发 闺蜜向", "头皮护理 闺蜜向", ...],  // 6 条「赛道名+空格+风格类型」字符串
  "audience": "有头皮、护发问题的年轻女性白领…",          // ≤100 字
  "accountPosition": "你是开护发门店的老板娘，性格亲切直爽像闺蜜…",  // 第二人称 system prompt 片段
  "mainContentThemes": "围绕头皮护理和日常护发分享干货，拆解护发谣言避坑，到店护理项目科普…",
  "contentStyle": "",                    // 创作案例：300~1000 字范文，few-shot 风格样本槽
  "genSource": "custom"                  // 创建来源：custom=从头创建（另有从已有账号生成路径）
}
```

- 摘要列表 `GET /api/agent/persona` → `[{id, icon, title}]`＋内置 `{id: -1, title: "不带人设"}`；分页列表 `GET /api/persona/page?page=1&count=3`（count=3 硬对应配额）。
- **人设定位直接以「你是…」prompt 形态存储**——人设对象=结构化 prompt 组件包，不是抽象画像。
- 系统赛道字典（`/api/topic/v3/track/info`）只有 23 个通用大类（时尚美妆/健康医疗…），「美客引流」「护发避坑」等垂直赛道均为 **AI 按背景自由生成**，不受字典约束；赛道风格类型跟随用户风格输入变化（小柔=「干货实用」、输入「像闺蜜」后阿楠全部=「闺蜜向」）。
- 每字段带显式用途说明（产品语言）：平台→选题推荐+创作风格；赛道→选题推荐；内容方向→选题范围与核心领域；受众→内容深度角度；人设定位→口吻/视角/专业属性；创作案例→表达习惯/语气/结构。

## 二、创建全流程（对话式向导，`/personalSet` 路由）

1. **开场**：拟人化打招呼（用账号昵称）+ 两张完整示例人设卡（阿卡=公众号科技赛道、阿玲=小红书家居赛道，可「换一换」；示例的「创作风格」直接展示整篇范文全文）。三入口：**根据已有账号生成人设** / **创建新的账号人设** / **暂时不需要，直接去创作**（可跳过，不阻断）。
2. **选平台**：小红书/公众号/今日头条/百家号 四卡片；也可直接打字描述想模仿的账号。选小红书后回「当前有超过 80% 的绘文用户也在创作小红书哦」（社会证明话术）。
3. **意图分流**：四选项——用人设打造**个人 IP**未来变现 / 为某**产品/服务**推广 / 塑造**品牌**人设 / 没想好随意试试（与我方 D-111 资产类别个人IP/产品/品牌几乎同构）。
4. **自由描述**：AI 给提问框架（核心卖点/目标受众/推广风格如「闺蜜风、达人风」）+ textarea +「**添加参考文件**」上传（.doc/.pdf/.txt/图片）。
5. **AI 生成**（「账号人设思考中……」十几秒）→ 直接落入**预填编辑表单**：名字/平台/6 赛道/内容方向/受众/人设定位全部生成完毕，创作案例留空待用户贴范文；用户可全字段改后「创建人设」保存。
6. 实测输入「护发门店老板娘＋年轻女性白领客群＋像闺蜜一样帮避坑」→ 生成「阿楠」：人设定位吸收风格词（「性格亲切直爽像闺蜜…说话接地气不啰嗦」），同一背景不同风格输入产生可区分变体（vs 小柔「性格直爽热心」）。

**交互本质：对话流+选项卡片混合向导（D-114 同款范式）→ 一句话输入 → AI 扩展为全字段结构化对象 → 用户校对保存。**

## 三、应用面（四处实测）

1. **首页「你的人设专属选题」**：按人设生成选题卡（实测小柔的四条全部老板娘视角：「老板娘揭秘：白领最常踩的 6 个护发智商税」——受众字段直接影响选题），每条带**灵感来源**（检索页面标题+链接）、话题 tag、「开始创作」直达。**新建人设触发专属选题重算**（区块变「你的专属内容正在赶来的路上」loading）。
2. **Composer 挂载器**：输入框右下角人设切换（头像+名字+下拉：阿楠/小柔/不带人设）；**新建人设自动成为当前挂载**。
3. **创作请求注入（决定性合同证据）**：挂载人设提交后 `POST /api/agentHomepage/create` 请求体 **`styleId: 24071`（=personaId）**；不带人设时 `styleId: -1`（Codex 交叉证实）。**人设在合同层复用「风格 id」字段**——人设被建模为风格的一种。任务页确认卡与生成全程右上角持续显示挂载人设名。
4. **官方应用面口径**（人设管理页文案）：「选题推荐、创作风格口吻塑造、**关联记忆激活**」——「人设记忆」在卡片文案出现（「人设记忆等更多信息」），但 detail API 无字段、bundle 无 memory 路由、猜测端点全 404：**当前版本为口径预告，未见实装面**。

## 四、商业面

- **人设配额：免费/低档 3 个，「升级权益可获取更多」**——人设数量是付费维度。

## 六、取证边界与服务稳定性观察（收口）

**正文级「带人设 vs 不带人设」口吻对照未取证**——原因是生成服务连续故障，非取证方法问题。当日带人设任务全记录：

| 任务 | 模式 | 建立方式 | 结局 |
|---|---|---|---|
| 18210943 | 快速+人设 | UI 主路径 | 确认卡自动继续→「当前对话正在处理中」+「任务已停止」（快速假进度故障，第 3 次复现） |
| 18210949 | 深度+人设 | API 直建 | 任务壳无首条 chat（空对话流）；补发后 `<gy protocol-only response` 协议故障（深度模式亦复现）；req 无 res 卡死，重发被前端拦截 |
| 18210981 | 快速+人设 | UI（切档点反） | 未跟进 |
| 18210984 | 深度+人设 | UI 主路径 | 确认卡自动确认后**页面刷新→任务直接「已停止」**（确认指令 req 停 status=6，与 Codex 快速故障样本同值；同任务不可复活） |
| 最后一单 | 深度+人设 | UI 主路径（未跳转） | 服务端自跑未跟进（用户叫停反复尝试） |

**人设应用的已取证据充分**，口吻对照结论以下述四层为准（第 4 层由 Codex 任务 18210911 补齐）：

1. **选题层（实证，最强）**：人设专属选题的标题/视角/客群完全人设化——小柔（干货实用）出「老板娘揭秘：白领最常踩的 6 个护发智商税」，受众字段（年轻女性白领）与人设身份（老板娘）都直接进入选题语言。
2. **合同层（实证）**：创作请求 `styleId=personaId` 注入，任务全程右上角挂载人设名，确认卡建议补充维度随主题动态生成。
3. **官方口径（佐证）**：模型 tip 明示「绘文 V4：**账号人设效果更优**，创作要求理解更佳」——人设进正文生成链路是产品明示能力。
4. **全管线对照（Codex 18210911 实证，控制变量=仅 styleId）**：人设注入**上游而非末端润色**——主题定位变化（「控油技巧分享」→「控油防晒清洁指南」）、搜索词注入受众（「职场女性 夏季头皮控油…」）、正文第一人称店主化（候选 A 弱角色「我店里这阵子来得最多的」/候选 B 强角色「作为开了快十年护发店的老板娘」）、图片规划店铺化（店内交流/产品陈列/试用装礼盒/活动海报）。执行注入形态=Agent 配置 `role` 字段（「主要受众：…\n人设定位：…」两行拼接文本，contentStyle→style），`confirm/continue` 不重传 styleId（服务端任务配置为事实源）。

**⚠️ 人设幻觉经营事实（Codex 取证）**：用户只给了「护发门店老板娘+年轻女性白领」，成品却出现「**开了快十年护发店**」（虚构经营年限）、「**店里最近推的 TWG 乳酸菌海盐洁发膏**」（第三方搜狐软文里的产品被改写成本店在售——provenance 从检索到写作间丢失）、「**抽一位送同款试用装**」（虚构促销履约承诺）、「后台好多来店里的小姐姐」（虚构客户案例），且图片阶段把这些视觉化成「证据感」更强的店内陈列与海报。绘文把「人设角色提示」与「可公开声明的经营事实」混在同一自由文本上下文。

> **【用户裁决 D-117（2026-07-24），修正本文与 Codex 文档中「硬阻断」定性】**：生成过程**零内容限制**——上述演绎（美化/多角度演绎/场景叙事）是产品力的一部分，商家自有信息不足以支撑丰富输出；规避项=AI 生成软提示（绘文「内容由AI生成，请注意甄别真实性」同款已足够）；风控唯一收口=发布提醒与发布审核（外部发布确认门），内容真实性责任在商家，平台不承担全流程风控。Codex §16 四条硬规则不采纳为硬门，降级为生成质量偏好（已登记事实优先注入，缺失时自由演绎）。硬门仅保留两类且均为既有决策：忠实性（商家已提供的信息不得生成错，D-115 校验门）与红线硬停（D-025 准入层）。MarketingIdentity×StoreFact 分层的价值定位相应调整为「让真实事实可被优先注入」而非「阻断演绎」。

**架构级发现（本轮最大增量）**：绘文生成**无服务端 durable**——SSE 客户端断开≈任务死亡（刷新即停、同任务不可复活、失败无退款语义）。故障清单：快速模式假进度 3/3 稳定复现、`<gy` 协议故障跨模式偶发、任务壳与首条消息非原子（API 直建即空壳）。与我方 DBOS durable workflow（浏览器关闭照跑、Last-Event-ID 续传、服务端权威终态）形成最硬对照。

**绘点损耗全程记录**：充值 3000 起，收口时约 2900——混合消耗含成功深度任务 6 点、快速故障链 44 点、人设创建+选题重算约 24 点、其余隐性扣点约 20+ 点（无逐项账单可查，**失败/中断均无退款迹象**）——反面印证我方 quote→reserve→settle/release+失败释放的必要性。
