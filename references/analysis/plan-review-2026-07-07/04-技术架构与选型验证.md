**一句话总判**：产品域设计（合规、账本、发布路由、审计）成熟且高质量，但**基础设施选型踩了两颗对"全大陆客户"致命的雷（CF Workers 可达性 + AIGC 备案），且把一个 pre-PMF 产品拆成了成熟期才需要的四服务/双库形态**。P0 的正确形态是"国内云上的 modular monolith + 单 Postgres + 国产已备案模型"，把方案的服务边界降格为模块边界，保留全部产品域设计。

## 一、被评审架构概述

方案 04§2（`合集:997-1042`）与 08§7（`合集:3103-3151`）定义的 P0 四服务边界：

```
Cloudflare Workers App Shell (mkfast-template fork)
  TanStack Start UI + Better Auth + D1 shell-local + R2 上传/proxy + typed BFF
      → Core API (独立 TS service + Postgres，产品事实源)
          → Agent Service (Node ≥22.13 + Mastra，Workflows/Agents/Tools)
          → Worker Pool (Node containers：SVG 编译→resvg-js 栅格化→sharp 合成，Playwright 兜底)
          → R2 (只存二进制)
```

- 队列：P0 Postgres-backed durable jobs；Mastra durable/signals/daemon 后置 P1/P2（`合集:1089`、`1157`、`2376-2398`）。
- 用量：reserve/commit/refund 账本 + provider registry 路由（`合集:1092-1094`、`1161-1182`）。
- 双库：Postgres 为产品事实源，D1 仅 shell-local auth/session/API key/payment/upload metadata（`合集:1088`、`2648-2684`）。

下面按"致命盲点 → 复杂度 → 逐项选型 → 契约质量 → 修订建议"展开。

## 二、[P0] Cloudflare Workers 大陆可用性 —— 选型级红线

**这是全案最严重的问题，且与"目标客户全在大陆、操作人用国内网络"的定位直接冲突。**

### 2.1 证据

- **workers.dev 默认域基本不可用**：GFW 对 `workers.dev` 做 DNS 污染 + SNI RST；443 端口发出 TLS ClientHello 后收到 3 个 RST ACK；部分 ISP 把该域 sinkhole。([Cloudflare Community: Workers blocked in China](https://community.cloudflare.com/t/cloudflare-workers-suspected-of-being-blocked-in-china/382155)、[Worker is not available in China](https://community.cloudflare.com/t/worker-is-not-available-in-china/497419))
- **自定义域也不保证**：2025-03 社区报告同一 Worker 自定义域"部分大陆用户能开、部分开不了"，ping 超时、DNS 正常但 traceroute 停在 ISP；2025-04 报告 CF IP 被 GFW 封。([Can't access my site from China Mainland](https://community.cloudflare.com/t/cant-access-my-site-from-china-mainland/789666)、[Cannot access domain from China](https://community.cloudflare.com/t/cannot-access-domain-from-china/778741))
- **官方唯一低延迟通路 = Cloudflare China Network（京东云运营）**，且限制多：
  - **仅 Enterprise 版**可用。([Overview](https://developers.cloudflare.com/china-network/))
  - **每个 apex 域必须有有效 ICP 备案**，页脚展示备案号；备案 4–8 周；ICP 被吊销京东云可随时中止服务。([ICP 文档](https://developers.cloudflare.com/china-network/concepts/icp/)、[FAQ](https://developers.cloudflare.com/china-network/faq/))
  - **京东云对全部上线域名做内容审查（content vetting）**，首次开通 24–48h；PoC 也要先有 ICP + 京东云审查通过。对**医美/医疗**内容，这一层是重门槛。
  - **Pages 在大陆不可用**（pages.dev 证书不在境内），**Turnstile 不支持大陆**。([FAQ](https://developers.cloudflare.com/china-network/faq/))

### 2.2 对本方案的影响

- 方案把**商家直接操作的 App Shell** 放在 CF Workers（`合集:1002-1008`）。商家在门店用国内网络打开创作台、上传素材、确认发布——**这是产品每天的主路径**。若默认域被墙、自定义域部分不可达，产品在相当比例的门店"打不开或很慢"，直接击穿"10 家门店真实跑起来"的验收。
- CF China Network 对 P0 不可行：Enterprise 价格与 pre-PMF 不匹配；ICP+京东云内容审查（尤其医美）+ 4–8 周周期，与"4–10 周出 P0"直接抢时间且引入不可控外部审批。

### 2.3 R2 回源放大了这个问题（源码证据）

模板 `getPublicUrl` 走**同源 proxy**：`src/storage/provider/r2.ts:194-200` 返回 `${requestOrigin}/api/storage/file?key=...`，即每张素材/成品图的字节都经 Worker 回源下载，而非直连 CDN/预签名 URL。美业产品图片密集，大陆用户经 CF 边缘回源 = 延迟与带宽双重放大。即便迁 CF China Network，R2 桶本身与图片分发在大陆的表现仍需实测。

### 2.4 部署建议（P0 推荐）

> **把商家侧应用部署到国内公有云（阿里云 / 腾讯云 / 火山引擎），走 ICP 备案；对象存储用 OSS/COS；CDN 用国内厂商。彻底不把商家主应用放在 CF Workers。**

- ICP 备案可与开发**并行启动**（公司资质齐备时企业备案约 2–4 周），不阻塞编码，但要立刻开工。
- 这与方案已有决策**自洽**：方案本就把 Postgres 定为事实源、D1 只当 shell-local（`合集:1088`）。既然要落国内云，最干净的做法是**连 D1 一起去掉**，单 Postgres（见第四节）。
- 若未来确有"全球/港澳台"版再评估 CF；P0 不需要。

## 三、[P0] AIGC 生成式 AI 合规备案 —— 部署与模型选型的连锁约束

CF 之外的第二颗大陆特有的雷，且它**反向锁死了模型选型和整体合规路径**，选型报告未覆盖。

### 3.1 证据

- **属地管辖**：《生成式人工智能服务管理暂行办法》第二条——向境内公众提供生成文本/图片/音视频内容的服务即适用本办法，**无论模型部署在境内还是 API 来自境外**。([网信办备案公告](https://www.cac.gov.cn/2026-01/09/c_1769688009588554.htm))
- **SaaS/应用层也要办**：即使底层调用**已备案**模型（通义/DeepSeek/豆包），只要封装成独立应用面向境内公众提供，仍是"服务提供者"，须办**大模型登记（上线编号）**并视情况办**算法备案**；二次训练/微调则须走完整**备案**。登记不能替代备案。
- **境外模型基本"一票否决"**：海外主流大模型均未在网信办备案，用境外未备案模型对境内公众提供服务，在上架审查与网信核验中属高风险；数据路由到境外还构成**数据出境**。
- **执法在收紧**：2025-05 起"清朗·整治 AI 应用乱象"专项把"未按规定履行大模型备案登记义务"列为首要整治项；各大应用商店/小程序对 AI 写作/绘画类强制要求备案号+安全评估。全年累计 748 款完成备案、435 款应用完成登记（截至 2025-12-31）。

### 3.2 连锁结论

1. **模型路由的候选集被强约束为"国产 + 已备案"**（豆包/通义/DeepSeek/GLM/Kimi 文本；即梦/通义万相/可灵 图片）。方案 04§6 未点名厂商（`合集:1161-1182`），但在 F1/F2 约束下，这不再是"以后再选"，而是**选型报告此刻就该定 shortlist 的事**。
2. **OpenAI/Claude 直连服务境内 C/B 端 = 网络（被墙）+ 合规（未备案）双杀**。海外模型只可用于**内部**（研发、评测、非面向商家的能力），不可进商家主链路。
3. **产品自身要做大模型登记 + 算法备案**：登记较轻但仍需安全评估材料；这应进入路线图与法务预算，且与 F1 一并把部署钉死在国内云。

> 与既有记忆一致：兄弟项目"讯飞绘文2"已把"中国监管合规"列为 P0（见 `project-xfei-huiwen2-content-growth-agent`）。本案医美垂类更敏感，合规门更硬。

## 四、复杂度评估：四服务 + 双库 + 双运行时是否过度设计

### 4.1 判断：对 P0 过度设计

面向 **10 家试点、1–3 人开发、4–10 周**的 pre-PMF 阶段，四个独立部署单元（App Shell / Core API / Agent Service / Worker Pool）+ 两套库（D1+Postgres）+ 两种运行时（Workers+Node）带来的是**成熟期才需要偿付的分布式成本**，而 P0 拿不到对应收益：

- **跨服务身份传递**：App Shell 的 session 要签发/透传到 Core API（详见第五节）。
- **跨服务一致性**：内容创建要串 App Shell→Core API→Agent→Worker→回写，任一跳失败都要补偿；P0 没有这个吞吐压力却先背上了协议复杂度。
- **本地联调**：开发一个功能要同时起 4 个服务 + 2 个库 + wrangler 本地态，迭代速度显著变慢。
- **可观测**：4 份日志/trace 要拼 correlation_id 才能还原一次请求。

这与全局 CLAUDE.md 的"简单优先/外科手术式修改"、以及记忆中"成熟组件优先，不自写 framework"是同向的：**服务边界该由真实规模信号触发，不该在 P0 预先摊开**。

### 4.2 推荐 P0 最小架构：国内云上的 modular monolith

```
单 Node 应用（国内云 + ICP）
  ├─ Web/UI 层        TanStack Start（保留模板 UI/路由/组件）
  ├─ BFF/API 层        typed server functions（模板已有形态）
  ├─ 业务域模块        workspace/store/asset/content/compliance/publish/lead/usage/audit
  │                    —— 就是 Core API 的全部对象，但作为"模块/包"，非独立服务
  ├─ Agent 模块        Mastra（同仓，独立进程或同进程二选一，见下）
  └─ 渲染模块          satori→resvg-js→sharp（npm 库，P0 进程内即可）

单 Postgres（含 Better Auth 表 + 全部业务事实 + durable_jobs + 账本 + 审计）
对象存储 OSS/COS（替 R2）
队列 = Postgres durable_jobs（方案已正确设计，见第六节 F8）
```

- **Agent 边界怎么留**：方案坚持"Agent runtime 与业务解耦、独立故障域"（`合集:990`）是对的**原则**，但 P0 用**进程隔离**即可满足——同一仓库、`agent/` 独立 package、独立进程（`node agent`），通过内部 HTTP/本地 socket 调 Core 模块的 tools。**不需要独立部署单元和独立库**。这样既满足"App Shell/Core 不 import Mastra types"（`合集:1152`），又不背分布式账。
- **渲染边界怎么留**：resvg/sharp 是 CPU 密集，但 P0 图文量小，先跑进程内（或 Node worker_threads）；真出现事件循环被渲染阻塞的信号，再抽独立 worker 进程/容器。

### 4.3 何时再拆（拆分触发信号）

| 拆出的服务 | 触发信号 |
|---|---|
| Worker Pool（渲染/视频/Playwright） | 渲染/转码把 API 事件循环 P95 拖高，或引入 Playwright/FFmpeg 这类重依赖污染主镜像时 |
| Agent Service（独立部署） | Agent 长任务需要**独立扩缩容或独立发布节奏**（与 Web 发版频率冲突）、或要接 Inngest/PubSub 做 durable 时 |
| 独立库/读写分离 | 单 Postgres 出现明确瓶颈：账本写入热点、pgvector 重查询拖慢事务库、或进入多租户物理隔离阶段 |

**结论**：方案 08§7 的四层图作为**P1/P2 目标拓扑**是合理的、值得保留；错误在于把它当**P0 起点**。把它标注为"演进终态"，P0 收敛为 modular monolith。

## 五、[P1] Better Auth 跨服务身份：一致性与联调成本

### 5.1 现状问题

方案把 Better Auth 的 user/session 放 D1（App Shell），把 workspace/member/store 授权放 Postgres（Core API）（`合集:1088`、`1092`、`2511-2537`；契约 `p0-data-model-api-contract.md:38-39`）。源码上 Better Auth 现在是 `provider: 'sqlite'`（`src/auth/auth.ts:22-24`），user/session/account/apiKey 全在 D1。这带来：

- **身份相邻数据跨两库**：`user` 在 D1，`workspace_members`/角色在 Postgres，**无法用外键保证引用完整性**，删用户/改角色要跨库最终一致。
- **每个请求都要跨服务解析授权**：App Shell 拿到 session 后，要把身份签名透传给 Core API，Core API 再查 Postgres 里的 workspace 授权——多一跳 + 一套服务令牌/校验。
- **联调**：改一次登录或权限要同时动 D1 与 Postgres 两套 schema/迁移。

### 5.2 更简单的切法（推荐）

> **P0 把 Better Auth 也接 Postgres，单库单 auth。** Better Auth 官方支持 Postgres adapter；`admin` 插件给基础角色，workspace 成员/角色作为**同库业务表**，与 user 同事务、有外键。跨服务身份问题在 modular monolith 下**直接消失**。

- 迁移代价小：`src/auth/auth.ts:22-24` 的 drizzle adapter 从 sqlite 换 pg，`app.schema.ts` 的 sqlite 表换 pg 列类型（`integer timestamp_ms`→`timestamptz` 等）。
- 若坚持独立 Agent Service：Agent **不信任客户端身份**，只用**服务令牌**认证到 Core，并透传 `workspace_id`+`correlation_id`——这点契约已经建模对了（`tool_calls`/`agent_runs` 都带 workspace_id/correlation_id）。这与"单库 auth"不冲突。

### 5.3 附带收益：账本不再跨库

现状 payment 在 D1（`src/db/app.schema.ts:14-48`），而 `subscriptions/usage_ledger` 在 Postgres——**收款事实与用量/额度事实跨两库**，对"钱"是一致性隐患。单 Postgres 后，reserve/commit/refund 与订阅、支付回执可同库同事务对账。

## 六、mkfast-template 真实复用价值（基于源码审查）

模板 = TanStarter：TanStack Start + React 19 + Cloudflare Workers + Better Auth + D1 + R2 + Stripe/Creem（`package.json`、`wrangler.jsonc`、`CLAUDE.md`）。版本很新（wrangler 4.84、React 19.2、TanStack Start 1.132、Better Auth 1.4.12、Drizzle 0.45、compatibility_date 2025-09-02）。

### 6.1 逐能力复用评分

| 能力 | 源码位置 | 真实价值 | 判定 |
|---|---|---|---|
| TanStack Start UI/路由/SSR 骨架 | `src/routes/*`（dashboard/settings/admin/api 分区已在） | 省 UI 脚手架、文件路由、SSR 接线 | **高价值** |
| Better Auth 配置 | `src/auth/auth.ts`（admin+apiKey+email harmony+Google OAuth） | 登录/注册/找回/邮箱验证/账号删除即用 | **高价值**（但要 sqlite→pg） |
| provider 抽象模式 | `src/payment/index.ts:17`、`src/storage/index.ts:14`、`src/mail`、`src/newsletter` | 注册表/工厂模式干净，可套到模型/存储/支付多 provider | **模式高价值** |
| shadcn/Base UI/Tailwind v4 组件 | `src/components/ui/*` | 现成组件库 | **中高** |

### 6.2 最大拖累：与 Cloudflare 的深度耦合

模板不是"云无关的 TanStack Start"，而是**为 CF Workers 深度定制**的：`src/storage/provider/r2.ts:1` 直接 `import { env } from 'cloudflare:workers'`；DB 走 D1 binding（`wrangler.jsonc:63`）；入口 `src/server.ts` 是 Worker；构建用 `@cloudflare/vite-plugin`。一旦（因 F1）改国内云 Node 部署，这些 CF 专属层（估 30–40%）要么删要么重写：D1→Postgres、R2 binding→OSS SDK、wrangler→标准 Node 部署。

D1 schema 本身极薄——迁移总量仅 86+14+30+2 ≈ 132 行 SQL（`src/db/migrations/*.sql`），只有 auth 表 + payment + userFiles。**所以"扔掉 D1/CF 层"的沉没成本很小**，反而印证：模板真正省时间的是**前端 + auth + 抽象模式**，不是它的 CF 基础设施。

### 6.3 fork 长期维护成本

- fork 后与上游漂移：上游持续按 CF 方向演进（R2/D1/Workers），你按国内云 Node 方向改，**升级会持续打架**。建议**不做长期 fork 跟随**，而是"一次性取用 UI/auth/组件骨架 + 抽象模式"，之后当自己的仓库维护。
- 好处是模板依赖新、代码规范（Biome、knip、Playwright E2E 都在），起步质量高。

### 7.1 渲染链补件（F6 详解）

- **事实**：resvg-js 只把 SVG 栅格化为 PNG，**不做文本自动换行/排版**；sharp 只做缩放/合成/元数据，也不排版。SVG `<text>` 不会自动折行，必须**预先算好断行位置**，而中文断行要按字形宽度测量。([satori README](https://github.com/vercel/satori) 用 Yoga 做自动换行)
- **推荐**：用 **satori（React/JSX→SVG，Yoga 布局，支持 CJK 自动换行）→ resvg-js（SVG→PNG）→ sharp（合成/元数据）**。这正是 `@vercel/og` 的底层链路，成熟。产品本就是 React/TanStack 栈，satori 天然契合。
- **关键利好**：satori+resvg 跑在 **Node worker（非 Edge）**，**绕开 `@vercel/og` 在 Edge 上 500KB bundle（含字体）的硬限制**——而这正是 CJK 字体（全字库很大）在 Edge 上的老大难。方案让渲染在 Node containers 跑（`合集:1031`）反而是对的，问题只是没写 satori 这层。
- **字体版权**：正文默认用**思源黑体/思源宋体（Source Han，SIL OFL 1.1，可商用）**；**阿里巴巴普惠体**可商用但注意其授权条款细则；**避免微软雅黑（Microsoft，服务端嵌入渲染无授权）、方正/汉仪未授权字重**。字体子集化（按需抽字）降体积。Emoji：resvg-js 彩色 emoji 支持有限，需要时用 Noto Color Emoji 或 twemoji SVG 替换。（字体授权细则标 P2，落地前逐一确认。）
- **备选**：Puppeteer/Playwright 截 HTML 的排版最准（浏览器级），但重、慢、贵，P0 作兜底而非主链路；纯 canvas（node-canvas）也可但排版要自己写。satori 链是 P0 性价比最高解。

### 10.3 (b) 底层文档论证了但结论有问题

1. **四个"独立部署服务"作 P0 起点**（ADR-0002 status: accepted；`13:15-61`）。ADR-0002 的"Considered Options"四个备选全是**内部**的（全塞 Worker/D1、Mastra 当后端、client 渲染、L2 自动化），**没有一个备选是关于部署形态轻重或部署地理**的。它防的风险（壳变成 facts 的隐形拥有者）真实且值得防，但**"边界"被等同于"独立部署单元"**——同一个可审计性要求，用 monolith 内的**模块边界 + 单 Postgres**即可满足，P0 的 plumbing 成本只是零头。对 1–3 人/10 试点，四服务是过早工业化。**注意：ADR-0002 是正式 accepted，反转需要写 superseding ADR，不是改文档。**
2. **模型 P0 默认路由 = 境外优先**（`09:323`、`09:331-339`：draft/rewrite/platform_adapt/compliance/final_refine/asset_tagging/image 的 default 几乎全是 OpenAI/Gemini/Claude/Imagen，国产 DeepSeek/Qwen 仅 fallback/候选）。**路由机制是对的，默认选择是错的。** 根因是分析错误：`09:341` 把"中国业务可用性"列为"eval 分数、硬失败、成本、延迟、限流、账单稳定性和中国业务可用性共同决定"的**第 7 个软性权衡因子**，而它实际是**网络（被墙）+ 备案（一票否决）的硬二元门**；`09:192-200` 的 eval 权重（compliance 35%…）也**没有"可用性/备案"维度**，`model_providers` 表明明有"部署区"字段（`09:233`）却没让它驱动 default。**利好：因为 registry/routing 抽象是对的，把默认路由翻成国产优先只是改一张 default 表 + benchmark set，不是重构。**
3. **"先手写 SVG template compiler，不急着把 Satori 放进主链路"**（`10:114`）。这条子决策**增加而非减少 P0 工作量**：手写 SVG 编译器 = 要自己实现中文按字形宽度断行（SVG `<text>` 不自动折行）；`10:108` 把中文换行当成"要自己建测试集"的**测试问题**，但它其实是**实现问题**。satori（Yoga 布局）把 CJK 自动换行免费给你，且跑在 Node worker（非 Edge）不受 500KB 字体 bundle 限。→ 建议 satori 从第一天进主链路。（`10` 其余部分是 (a)。）

### 10.4 (c) 盲点：底层文档和合集都没考虑

1. **[P0] CF Workers 大陆可达性——完整盲点**。跨全部 analysis 文档 + 3 份 ADR 检索 `ICP|备案|大陆|GFW|china.*network|京东云|被墙|延迟`：**关于 CF/网络可达性零命中**。`13:365-385` 部署节直接写"App shell：Cloudflare Workers Paid + D1 + R2 binding"，`13:468-474` 的 Open Risks 列了容器平台/模型价格/CJK 字体/商家验证/微信抖音时间线，**唯独没有"大陆能否访问 App Shell"**——而这是产品每天的主路径、且 CONTEXT.md 已明确客户就是"beauty, aesthetic, and regulated medical-content businesses"（中国本地商家）。这是全项目最高严重度盲点，第二/三节已展开，标 **[P0]**。
2. **[P0] AIGC 大模型登记/算法备案作硬门——"已知但未传导"**。**不是完整盲点**：`06-compliance-implementation-plan.md:485` 有一行"若产品向中国境内公众直接提供生成式 AI 服务，需要进一步评估算法备案、安全评估、模型提供者合规和应用商店上架材料"。但问题有三：(i) 措辞是条件式"若…直接提供"，而产品**确定**向境内公众提供生成式 AI，不是"若"；(ii) 它被归入"后续风险 / 需进一步评估"，**没有作为约束回流**到 `09`（于是 09 默认了境外模型——正是备案禁止的）或 `13`（部署）；(iii) 合规文档抓到了它，架构与模型文档却当它不存在。→ **一个存在于项目内、却没能 gate 住它本该 gate 的两个决策的约束**，某种意义上比纯盲点更值得警惕。

### 10.5 对本报告 F6 的修正

我在第一版把渲染链写成"方案未指明布局方案"。读 `10` 后修正：**团队明确知道 satori、并有意识地选择先手写编译器后置 satori**（`10:114`），也预留了 `font_assets` license 表（`10:296`）和 CJK 字体授权风险（`10:329`）。所以 `10` 整体是 (a) 高质量文档；我的 F6 收窄为 10.3 第 3 条——**唯一可议的是"后置 satori"这一子决策**，它让 P0 反而要重造 satori 免费提供的 CJK 断行。结论方向不变（补 satori），但严重度从"缺件"降为"次优子决策"。

### 10.6 给 team-lead 的一句话

底层三份文档 + ADR 揭示的不是"能力问题"而是"**取景问题**"：团队在自足工程域（数据归属、队列、合规门、渲染、eval）做得很好，在外部约束域（大陆网络、AIGC 备案、模型地理）系统性失明，根因是"决策时无 live sources + 只在能力轴不在可达性轴上评估 CF"。修正成本**不对称**：模型默认路由、渲染补 satori 很便宜（抽象都对）；但 CF→国内云是**方向反转**，要写 superseding ADR，且会连带松动 mkfast-template 的 CF 耦合（见 F4）。
