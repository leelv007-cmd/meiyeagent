## 0. 执行摘要（结论先行）

这份合集的**产品判断是扎实的**（本地商家单轮、创作副驾收敛、L3 兜底、医美允许创作+发布前核验、不逆向），但作为一份"即将拍板的立项/选型报告"，它有三个结构性问题会直接影响拍板质量：

1. **口径未收敛**：同一个工具在 01/04/08 三章有三套命名（camelCase / snake_case / 动宾倒置），状态枚举在 Codex 两份深化文档里也有 3–4 套拼写。读者无法确定"哪个是真的"，工程一旦按不同章节实现就会对不上。
2. **范围与工期严重错配**：P0 = 12 模块 + 4 服务边界 + ~33 张表 + 服务端图文渲染管线 + 凭据保险库 + Mastra Agent Service，却承诺"4–10 周（≈6 周）MVP"。这不是 6 周的量，是 6 个月的量。且与方案自己反复强调的"先验证后建设""不一开始绑复杂框架"自相矛盾。
3. **报告缺决策脚手架 + 关键资产未迁移**：没有决策摘要页、未决问题清单、风险登记册；"本轮同步依据"引用的 4 份文件（analysis/13/14/15 + docs/adr/0003）**在新工作区 美业内容2 不存在，但完整存在于旧工作区 `美业内容/`**（已核实，合集文件两库字节相同）。新工作区只迁了合集、没迁它依赖的执行/试点/ADR 文档。更值得注意的是：**旧 14/15 比合集本身更严谨、更克制**，恰好能修掉本报告里的几处发现（见 A3、B1、E 章）。

**建议**：拍板前先补一页"决策摘要 + 最小可赢集合 + 待决策清单"，把 P0 从 12 模块砍到 7 项核心闭环，把工具/状态命名统一到 Codex 数据模型契约（`p0-data-model-api-contract.md` §7，snake_case），并明确"WoZ 阶段测意向/采用/付费、真产品阶段才测 5 分钟激活"。

### A3. 验收指标口径漂移（[P1]）

阈值本身基本一致（激活 70% / 采用 60% / 频率 50% / 线索 60%），但**指标清单在四处各不相同**，且发布包指标出现"P0 高于 P1"的倒挂：

| 指标 | 02 §4 (L780) | 05 §3.2 4–10周 (L1419) | 07 §9 (L1838) | IA 蓝图 §11 (L521) |
|---|---|---|---|---|
| 激活 5 分钟 70% | ✓ | ✗（缺） | ✓ | ✓ |
| 采用 60% | ✓ | ✗ | ✓ | ✓ |
| 频率 50% | ✓（持续使用） | ✓（留存） | ✓ | ✓ |
| 线索 60% | ✓ | ✗ | ✓ | ✓ |
| 发布包使用率 | ✗（缺） | ✗ | **≥60%** (L1842) | **≥60%** (L525) |
| 用量/审计 | ✗ | ✗ | ✗ | ✓ |

- **倒挂（有根因，非笔误）**：07 §9 把"L3 发布包使用率 ≥60%"作为验收（L1842），05 §3.3 把"发布包使用率 ≥50%"作为 P1 验收（L1442）。**根因在未迁移的 15-pilot-playbook**：15（旧库 L494）明确写"合集原验收给过 L3 发布包使用率 ≥50% 的下限；pilot **继续开发建议用 ≥60%** 作为更稳妥的 proceed 线"。所以 ≥60% 是"试点继续开发门槛"、≥50% 是"产品验收下限"，两者在**不同 gate**（pilot-continue vs product-acceptance），不是 P0/P1 之争。合集把 15 的 ≥60% 并进了 07 §9，却把解释留在了没迁过来的 15 里。
- **病句（是丢了上下文的合并痕迹）**："L3 发布包使用率**试点继续开发线** ≥60%"（07 §9 L1842、IA 蓝图 §1 L49）——这半句正是 15"pilot 继续开发建议用 ≥60%"被压缩成一个名词短语的残留。它本身不是随机 typo，而是"把 15 的结论并进正文、又没带上 15 的定义"。IA 蓝图 §11（L525）有干净版"L3 发布包使用率 >= 60%"。
- **[P1] 新增：激活口径"5 分钟" vs "5-10 分钟"自相矛盾。** 合集把激活指标写成"5 分钟"（00 §3.1 L177、02 §4 L780、05 §3.1 L1398、07 §3.1 L1601、07 §9 L1838"≤5 分钟"），但 07 §1 P0 目标（L1581）和 IA 蓝图（L24）写"5–10 分钟"。**未迁移的旧 14/15 全程统一用"5-10 分钟"**（14 M3 L119、15 L428、15 Admission Scorecard）。合集在做指标时把旧的"5-10 分钟"收紧成"5 分钟"，却漏改了 07 §1——旧文档反而是更一致的源。

> **建议**：建一张跨阶段验收总表（P0 / WoZ / P1 各一列），每个指标只定义一次；修掉倒挂与病句。

## B. 范围过载判定 + 最小可赢集合

### B1. 判定：严重过载（[P0]）

P0 声明的交付面（00 §4.1 L253–264 + 04 §2 + 08）实际包含：

- **12 个功能模块**：门店档案 / 真实素材库 / 文案 / 图片图文 / 视频脚本分镜拍摄清单 / 内容库 / 账号中心 / 发布包与受控发布 / 线索台账 / 合规 gate / 用量计费 / 首月 onboarding。
- **4 个服务边界**：App Shell（Cloudflare Workers fork）+ Core API（TS+Postgres）+ Agent Service（Node+Mastra）+ Worker Pool（Node 容器）。
- **~33 张表**：04 §7 约 24 张 + 08 §10 增补 9 张（agent_runs/tool_calls/content_tasks/approval_requests/skills/skill_versions/sources/automations/agent_evals）。
- **重基建**：服务端 SVG template → resvg-js → sharp 渲染管线 + Playwright（04 §2 L1032–1035）；凭据保险库 KMS 信封加密（03 §5.2 L905）；用量账本 reserve/commit/refund 幂等（贯穿）；广告法 + Regulated Content Mode 合规引擎；L1/L2/L3 发布路由。

对照目标"4–10 周（≈6 周）P0 MVP"（05 §3.2 L1402）和"新店 5 分钟产出首条"（00 §3.1 L177）：**6 周不可能建成一个 4 服务分布式系统 + 33 表 + 渲染管线 + 凭据保险库 + Agent 编排**。这是 6 个月量级。且与方案自述矛盾：01 §7（L510）说"不应一开始绑定某个复杂 Agent 框架"，04 §5（L1107）却已直接采用 Mastra；07 §11 与 06 §4 反复强调"先验证后建设"，但 P0 build 清单几乎把所有东西都放进了 build。

**纪律溯源（重要）**：未迁移的 14-backlog 其实**已经比合集更克制**，它的 sprint 计划（S0 本地基座 3-5 天 / S1 门店事实+素材授权 Week1 / S2 内容+Agent workflow Week2 / S3 合规+渲染+L3 Week3-4 / S4 线索台账+周报 Week5 / S5 试点加固 Week6）把 6 周 spine 限定在 L3 闭环，并把 **L1/L2 官方能力放到 Week7-8 且标记 optional**（旧库 14 L20/L372），**账号中心放 S5**（14 M11 L127），**统一收件箱放 Later**（14 L146），甚至把"P0 必须依赖 L1/L2 自动发布才有价值"列为 **No-Go 条件**（14 L453）。这套克制的范围恰好接近本报告 B2 的"最小可赢集合"。**过载是合集 08 章额外引入的**（内容任务收件箱 P0/P1、Skills version、Sources、Automations、permission 三模式）——它们既没进 14 的 backlog，也没进 02/07 正文，是 08 单方面扩张。换句话说：**范围纪律本来是有的，只是随 14 一起没迁进来；把 14 迁回并作为 P0 范围基线，过载问题一大半自动缓解。**

### B2. 最小可赢集合（建议：保 7 / 缓 6 / 砍 6）

**保（不可再砍的核心闭环，验证"门店知识 + 真实素材 → 平台原生成品 → 线索"这一条命题）：**
1. 门店档案（精简：基础信息 + 项目价目 + 人设 + 禁忌，先手填，冷启动导入后置）
2. 真实素材库（上传 + 标签 + 授权状态，**不做** embedding/pgvector）
3. 创作副驾文案生成（**只 2 平台**：小红书笔记 + 抖音口播；场景包用静态模板）
4. 内容库（草稿 / 已发布两态，**不做**版本树、平台变体矩阵）
5. L3 发布包（永远可用，纯导出，是产品价值下限）
6. 合规 gate（广告法敏感词 + AIGC 标识 + Regulated Content Preflight——这是红线，不能砍）
7. 手工线索台账（人工录入 + 内容关联；用飞书多维表都行，见 B4）

**缓（验证通过后再建）：** 图文套图渲染管线（Worker Pool 的 SVG→resvg→sharp，先用 Canva/剪映模板 + 人工顶替）；视频脚本（可留，纯文本 LLM 低成本）；账号能力矩阵四表（P0 只需记录账号存在，不需要 Publish/Observe/Engage/Attribution 四表）；周报（先人工 Excel）；Mastra Durable/Signals；用量账本完整 reserve/commit/refund（P0 先做简单计数额度）。

**砍（移出 P0）：** L1 官方发布**接入**（只保留"读官方文档验证边界"，不写接入代码）；L2 浏览器辅助（整体推到 P1）；内容任务收件箱；Skills version 系统（P0 用静态模板）；Sources registry；Automations；Permission 三模式（P0 只需"生成自动 / 发布人工"二态）；凭据保险库（P0 走 L3、不托管任何 cookie/session，就没有凭据要保管——**先砍掉托管发布，凭据保险库这个最高风险子系统自然消失**）。

**架构上**：P0 先落**单体**（Core API 内嵌 agent 逻辑 + 同进程渲染），把 4 服务边界作为"接口切干净、物理先合一"的目标，等出现真实瓶颈再拆。这恰好回到方案 01 §7 自己的原则。

**每一刀的风险**：砍 L1/L2 → 风险是"商家嫌 L3 复制粘贴麻烦"，但这正是 0–4 周 WoZ 要验证的（发布包是否够省时间，06 §4 L1561 已列为待验证）；砍渲染管线 → 风险是图文质量依赖第三方模板，但 P0 阶段用真实素材 + 模板足够验证"内容是否被采用"；砍账号能力矩阵四表 → 风险是 P1 补建有迁移成本，可接受。

### B3. WoZ 阶段的成功指标不可测（[P0]）

0–4 周成功标准（05 §3.1 L1397）：10 家愿付费 / **70% 用户 5 分钟内产出首条** / 60% 可直接采用 / 3 家愿连续 4 周。问题在 WoZ（人工模拟副驾，L1393）阶段**没有产品**：

- **"70% 5 分钟内产出"测不出来**：WoZ 是人工代做内容，人工产内容不可能 5 分钟，且这个指标测的是"产品性能"（须真产品 + 埋点），WoZ 阶段无从测起。它本来就重复出现在 02 §4 / 07 §9 的**产品验收**里——应留在真产品阶段。
- **可在 WoZ 测的**：60% 采用率（给商家看人工产的成品，记录采用/改稿——可测）；付费意向（意向金/预付——可测）；素材可持续供给（上传频率——可测）。

> **建议**：把 WoZ 阶段指标换成"**意向付费家数 / 成品采用率 / 素材持续供给率 / 4 周陪跑意愿**"四个可测信号；把"5 分钟激活 70%"明确挪到 4–10 周真产品阶段。这也是范围收敛的抓手：WoZ 要验证的是"命题成立与否"，不是"产品性能达标与否"。

### B4. 可用人工/表格顶替的 P0 项（符合"先验证后建设"，[P1]）

方案自己在 02 §2.10（L704）已承认线索台账"应允许人工登记"。以下 P0 项在验证阶段都可先用飞书多维表/Canva/人工顶替，不必进 33 表：
- **线索台账 + 周报** → 飞书多维表 + 人工周报（验证"商家是否真会记线索"这一 06 §4 待验证点，不需要 leads/lead_content_links/weekly_reports 三表）。
- **图文套图** → Canva/剪映模板 + 人工（验证"图文是否被采用"，不需要 Worker Pool 渲染管线）。
- **账号能力矩阵** → 一张飞书表记录各平台能力现状（不需要 account_capabilities + 四能力表）。
- **平台变体** → 人工改写 2 平台（先验证"跨平台适配"是不是真需求，再决定是否建 content_variants 矩阵）。

## C. CreatOK 学习吸收度逐条核对

## D. 报告结构本身的重构建议

**读者拍板时要做的决策**：(1) go / no-go 立项；(2) P0 范围锁定（做多少）；(3) 开工顺序与资源投入；(4) 几个关键架构/合规取舍（单体 vs 4 服务、是否托管发布、医美是否首发）。

**当前 9 章结构为什么不支撑拍板**：
- 是"改了什么"的修订说明（L10–34），不是"要你决定什么"的决策文档；没有决策摘要页 / 未决问题清单 / 风险登记册。
- 08 章与 00–07 高度重复（又列一遍工具目录、数据模型、P0/P1/P2、页面结构），且 08 引入的新概念（收件箱/Skills version/Sources/Automations/permission 模式）**未回并**到 00–07——08 §11 自己列了"对现有文档的修订建议"，等于承认"正文一套、附录一套、附录还没并回去"。
- 悬空引用（A9）+ 两份 Codex 深化文档未被引用，引用关系倒挂。

**建议重构大纲（目标：能据此拍 go/no-go 与开工顺序）：**

0. **决策摘要页（1 页）**：一句话产品 + go/no-go 建议 + 3–5 个必须用户拍板的决策 + P0 范围一张图 + 工期/人力/成本区间。
1. **待决策清单（Open Questions）**：每条 = 问题 / 选项 A-B-C / 建议 / 影响面 / 需谁拍板（如：单体 vs 4 服务、P0 是否托管发布、医美是否与生活美容同批首发、账号中心 P0 折叠 vs 独立）。
2. **风险登记册**：范围过载、6 周不可行、WoZ 指标错配、医美合规、凭据保险库、平台能力不确定、成本未实测——每条 概率 × 影响 × 缓解。
3. **P0 范围契约（Scope Lock）**：最小可赢集合（保/缓/砍三栏，见 B2）+ 明确的"P0 Done"定义。
4. **统一术语与契约表（Canonical Names）**：工具 id / 状态枚举 / 工作流名 单一事实源（采用 Codex 数据模型契约 snake_case），消除 A1/A2 三套口径。
5. **产品定义与闭环**（收敛 00）。
6. **页面与工作流**（合并 07 + IA 蓝图，引用原型 index.html）。
7. **数据与 API 契约**（引用 `p0-data-model-api-contract.md`，正文不再重复 33 表）。
8. **架构与选型**（04 + 08 借鉴合并为一套架构图，标注"P0 单体 / 目标 4 服务"）。
9. **商业与路线图**（05，修正指标错配，WoZ 指标与产品指标分列两表）。
10. **附录：调研证据**（CreatOK 拆解 / benchmark matrix / Codex 两份深化）+ **引用修复清单**（把 analysis/13/14/15 + ADR 从旧库迁入并修正链接，而非删除——见 E 章）。
