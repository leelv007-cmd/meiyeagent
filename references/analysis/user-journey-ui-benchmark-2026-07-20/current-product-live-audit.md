# 当前产品真实 UI 审计（本地 E2E）

日期：2026-07-20

范围：当前产品的登录后冷启动、图文/文案入口与首轮草稿候选。

结论口径：这是一次**本地 fixture UI 走查**，不是生产环境、真实模型质量或付费媒体生成证明。

## 1. 环境与证据边界

- 使用独立 OpenCLI Browser session：`beauty-current-0720`，视口 `1280 × 723`。
- 使用独立测试数据库 `meiye_audit_0720` 与独立 DBOS 数据库 `meiye_audit_0720_dbos`；没有读写真实用户数据。
- 测试身份是隔离账号 `e2e-live-audit-0720@example.test`，仅存在于上述本地 E2E 数据库。
- 本地 Web `/api/ping` 与 Core `/health` 均返回 200；P1 Worker 已启动；Canvas 本地服务已就绪。
- 新账号首次进入期间，Web 服务日志重复出现 `Verified workspace provisioning is still processing` 的 500；页面最终自行恢复并进入工作台。本轮没有看到面向用户的错误页，但这说明认证成功与工作区可用之间仍存在竞态。
- Core 明确运行 `APP_ENV=e2e`、`MODEL_EXECUTION_MODE=fixture`。候选文案只能验证交互和持久化表面，不能验证真实内容质量、真实成本或真实模型供应。
- 本轮只走到文案草稿候选，**没有采用候选、没有执行图片/视频生成、没有产生付费媒体调用、没有进入发布或内容库闭环**。
- 仅保留下列 3 张截图，且均已逐张进行视觉检查；浏览器右侧偶见的 Read Frog 浮标来自本机扩展，不属于产品 UI。

## 4. 当前 UI 已经成立的部分

1. **冷启动方向清楚。** “今天想发点什么”直接指向用户目标，左侧业务导航收敛为创作、内容、素材、门店，信息架构比工具清单更接近业务语言。
2. **主推荐优先。** 首轮结果把一条主推荐置顶，其余候选折叠，符合“先给可用答案、需要时再比较”的既定产品方向。
3. **安全本地态有标识。** 工作台中出现“本地测试可用”及 fixture 说明，没有把本地候选伪装成生产模型实测。
4. **基础语义较完整。** 页面提供跳到主要内容、业务导航标签、表单 label、fieldset/legend、`aria-live` 生成状态和具名用户菜单。
5. **从输入到候选可连贯完成。** 用户不必先进入独立项目管理页；一句意图即可建立 Work，并看到流式中间态和可采用候选。

## 5. 主要 UX 缺口

### P1：首次登录存在工作区配置竞态

隔离账号验证后首次进入 Dashboard，Web 日志重复记录 `Verified workspace provisioning is still processing` 并返回 500，之后页面才自行恢复。当前用户只看到“正在打开内容簿”，没有明确错误，但在更慢的数据库或网络条件下可能变成长时间等待或失败页。

建议：认证完成后用一个可幂等查询的 onboarding 状态机承接工作区配置；`pending` 返回 202/明确加载态，前端采用有上限的重试与“仍在准备 / 重新检查”，不要把正常的配置中间态当作 500。

### P1：快捷场景会无提示覆盖用户已经输入的文案意图

实测先输入“为杭州拱墅区新客写一条真实克制的显白猫眼小红书图文笔记”，再选择“项目 / 服务曝光”后，输入框被整段预设文本替换。页面没有差异预览、确认或撤销提示。

建议：快捷场景只应补充结构化参数或以可撤销的建议形式插入；若必须覆盖，先显示“替换当前内容 / 保留原文并补充”的明确选择。

### P1：“暂时跳过”的对象不明确

按钮位于图片素材区域附近，语义像“跳过上传图片”，但实测点击后整个创作入口收起，回到“开始第一条创作”。重新打开后输入仍可能恢复，使其既不像取消，也不像继续。

建议：拆成“暂不添加图片，继续创作”和“退出本次创作”；退出需要二次确认并说明草稿是否保留。

### P1：文本、图片、视频三模态的一级入口不对称

首层只有“做图文 / 做视频”。“图片生成”存在于全局命令工具中，但在普通创作流中不易发现。对用户而言，“做图文”既可能代表写小红书笔记，也可能代表生成一张视觉图，任务模型不够清晰。

建议：一级任务统一为“写文案/图文笔记、生成图片、生成视频”，再在各任务内部选择平台、用途和素材；全局命令保留作快捷入口，而不是唯一明显入口。

### P1：核心输入被建议、背景与大侧栏挤到首屏以下

冷启动视觉辨识度高，但 `1280 × 723` 下大幅背景、宽侧栏和“今天值得发什么”卡片占据主要空间，真正的输入框需要继续向下滚动。第二张截图中，用户同时看到图片上传、链接补救、额度、主按钮、五类宣发任务、六个细化场景与今日建议，选择密度偏高。

建议：首页保持一个强主动作：输入意图 + 三模态选择 + 最近素材；“今日建议”和细分场景合并为可横滑的单层推荐，更多项进入抽屉。

### P1：额度数字在相邻阶段缺少可解释连续性

入口显示“本次约 3 次额度 · 余 20”，生成草稿后的工作台显示“本次约 3 次额度 · 余 12”。两处使用相同措辞，但没有说明预占、实际扣除、返还或不同额度池，因此用户无法判断一次操作到底消耗了多少。

建议：固定展示“预计消耗 / 已预占 / 实际扣除 / 失败返还”，并明确是哪一种文案、图片或视频额度。

### P2：结果首屏与用户原始意图的对应关系较弱

草稿结果首屏很干净，但只显示标题、正文与转化钩子；看不到平台、小红书笔记结构、素材来源、采用后去向等关键上下文。fixture 文案也没有复现杭州、拱墅区、显白猫眼等输入细节，不过此项只能视为 fixture 内容限制，不能据此评价真实模型质量。

建议：结果卡固定展示“面向平台、采用了哪些门店事实/素材、哪些事实仍缺失、采用后生成什么成品”；真实模型质量另做 live provider 评测。

### P2：本地/fixture 说明位于结果首屏以下

用户先看到完成度很高的候选卡，fixture 说明需要继续向下滚动才能看到。在 E2E 环境尚可，但任何演示或测试环境都可能造成误解。

建议：在结果标题旁放置常驻的“测试数据”状态徽标，并在导出、采用等动作前继续保留来源说明。

## 6. 可访问性风险

### 已观察到的优点

- 有“跳到主要内容”链接，主要区域具备 `main`。
- 业务导航、异步任务中心、用户菜单、输入框、成品类型和灵感场景均有可识别的结构或标签。
- 生成中与决策状态使用 `aria-live`，不会只靠颜色传达。

### 需要复核或修复

1. 全局命令中的 `role=option` 在 OpenCLI 可访问性快照中没有暴露文本名称，虽然 DOM `textContent` 中存在“文案生成 / 图片生成 / 视频生成”。这会影响读屏搜索与自动化选择；应为每个 option 提供稳定可访问名称并验证键盘 Enter 激活。
2. 页面仍有多个只显示图标、快照中没有可访问名称的按钮（例如顶栏/抽屉类开关）。需要用 axe 与 VoiceOver 逐一核对，不能仅依赖 tooltip。
3. 场景条带使用横向滚动；需要确认键盘焦点进入后有可见 focus、左右键或 Tab 顺序合理，并避免最后一项被裁切却没有滚动提示。
4. 本轮没有覆盖缩放 200%、高对比、减少动态效果、移动读屏与触控目标，不应将基础语义良好等同为 WCAG 已通过。

## 7. 对下一轮讨论的直接输入

- 当前最值得保留的是“一句话开始 → 主推荐先出 → 其余候选按需展开”。
- 下一版应把三模态入口、素材输入和结果去向重组为同一套任务骨架，而不是让图片依赖全局命令、视频依赖另一条工作流。
- 与小云雀、CreatOK 比对时，应重点检验：首屏多久看到输入、图片/视频是否一个页面内完成参考素材与参数、任务离开后如何恢复、结果如何继续编辑/复用。
- 与讯飞绘文比对时，应重点检验：小红书/图文笔记是否有清晰的选题—大纲—正文—配图—平台适配连续链路，以及用户原文是否在任何模板选择中被安全保留。
