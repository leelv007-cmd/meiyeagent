# 讯飞绘文登录态增量 UX 审计（2026-07-20）

> 对象：讯飞绘文 `https://turbodesk.xfyun.cn`
>
> 重点：图文笔记、小红书内容与文案创作，不评价本轮图片/视频生成质量。
>
> 方法：复用用户现有登录态，以 OpenCLI Browser 独立 session `xunfei-huiwen-0720` 只读走查；未提交生成、发布、账号绑定、购买、授权、删除或设置修改。

## 1. 结论先行

讯飞绘文最值得借鉴的不是它的页面视觉，而是把“写什么”拆成用户能理解的写作动作，并让选题、附件、人设、知识、草稿和跨平台改写围绕同一个 Composer 组织：

1. **写作动作比模型/工作流更容易开始。** “直接成文、一题多写、文章仿写、文章改写、二次创作、跨平台适配”把空白框转成明确任务；选择后，输入区和案例随任务切换，不需要用户自己写专业 prompt。
2. **选题不是孤立热榜，而是“来源 + 赛道 + 话题 + 原文”的可解释链。** 当前可见来源包括直接发散、小红书、头条、百家号；用户知道话题从哪里来，也能从原文继续“发散”。
3. **跨平台适配被做成独立、高频的写作任务。** 输入合同是“选择已有内容/附件 → 目标社媒平台 → 可选主题、侧重、篇幅”，并用公众号转小红书、小红书转抖音等例句降低门槛。
4. **草稿、知识和图片形成连续资产面。** 近期创作在侧栏可见；资产页提供草稿、知识库、图片库，草稿支持搜索、时间/类型/标签筛选、网格/列表和批量管理。
5. **不应照搬其通用内容运营外壳。** 其一级导航同时放入选题、发布数据、账号空间、资产、矩阵运营和社区，且前台仍要求用户填写“文章类型/字数/主题”等空槽；这与我方门店任务导向和 D-031“前台无槽位填表”不一致。
6. **发布能力必须与我方边界切开。** 讯飞绘文页面提供小红书等多平台绑定、发布和数据看板，但既有逆向基线显示其桌面发布包含 Cookie、页面上下文、无头浏览器和 CDP 拦截等混合机制。该实现不能成为我方小红书自动发布承诺的依据。

对我方的直接含义是：

> 借鉴“写作动作 + 选题证据 + 文档式编辑 + 跨平台改写”的连续旅程；将通用动作改写成美业任务，用既有 ContextBundle 自动补齐事实，并让最终结果继续落在唯一 ContentPackage revision 中。

## 4. 分阶段观察

### 4.1 创作首页：任务动作驱动，而不是 prompt 驱动

首页文章创作区的默认快捷动作是：

- 直接成文；
- 一题多写；
- 文章仿写；
- 文章改写；
- 二次创作；
- 跨平台适配；
- GEO 内容创作。

选择动作后，Composer 本身原位变化。例如“直接成文”切成一句可读任务：

> 我想创作一篇「社媒文章」，篇幅为「字数」，主要关于「创作主题」，可补充附件素材的参考维度。

其下方案例同步切到“小红书美妆爆文、头条数码解读、小红书探店、公众号旅行攻略、小红书健身教程”。这让用户先理解交付物，而不是先理解模型、节点或 prompt 结构。

值得借鉴的部分：

- 任务动作切换不离开 Composer；
- 示例随当前动作变化，可一键成为输入起点；
- 附件、人设和发送保持固定位置，减少重新学习。

不应照搬的部分：

- “社媒文章/字数/主题”仍是三个前台空槽，本质上仍要求用户编译 Brief；
- “文章仿写/二次创作/GEO”是内容运营术语，不是门店经营者的自然语言；
- 会员促销 banner、积分和“立即升级”长期占据创作主视图，不应进入我方首屏主轴。

我方对应改写应是：

- 从案例图写小红书；
- 写一条朋友圈项目介绍；
- 把旧帖改成这周同城版本；
- 一题三写：科普 / 案例 / 团购；
- 把小红书笔记改成抖音口播；
- 为当前活动生成图文套组。

用户点选后，Agent 应先用门店事实、IP、平台和真实素材自动填充，再给一张可改 chips 的 Brief 摘要；不出现空白字段表。

### 4.2 选题中心：来源解释强，门店相关性与时效仍不足

live 页面提供两层筛选：

1. **搜索源**：直接发散、小红书、头条、百家号；每项附带用途解释。
2. **结合赛道**：本次账号显示“健康医疗”，并可切“不限制”或进入“修改赛道”。

精选话题页同时呈现：

- 热点主题词与扩展角度；
- 原文平台、标题、摘要与图片；
- 页面级更新时间；
- 从单条原文继续“发散”的入口。

这是比纯热榜更好的证据链，但本次页面也暴露两项边界：

- 2026-07-20 走查时，页面标注“更新于 07-13 09:59”，新鲜度已经跨越一周；
- “健康医疗”作为当前赛道时，精选主题仍以《功夫女足》、台风、足球、国际人物等泛热点为主，用户无法从首屏判断赛道是否真正约束了推荐。

因此，我方不应另建一个泛热榜大页。更合适的迁移是把选题证据折叠进“今天值得发什么”：

- 推荐角度；
- 适用门店/项目/平台；
- 来源与抓取时间；
- 地域、时效与证据等级；
- “用这个角度创作”主动作；
- 不适用/过期时的明确降级。

小红书搜索结果只能提供内容角度与表达证据，不能自动成为价格、项目效果、资质或门店经营事实。

### 4.3 跨平台适配：最清楚、最可迁移的一条文案旅程

选择“跨平台适配”后，输入区变为：

> 请将「请选择附件」改写成符合「社媒平台」的内容，可补充主题调整、侧重、篇幅等二创条件。

下方案例覆盖：

- 公众号内容转小红书，添加 emoji 与标签；
- 小红书转微博短文，突出重点与互动；
- 内容调整为公众号长文；
- 小红书内容转抖音文案；
- 文章转知乎回答。

其优势在于“复用已有内容”先于“重新写一份 prompt”，也把平台适配作为一等任务，而不是结果页角落里的工具。

我方应采用同一思想，但输入来源不能只写“附件”：

- 当前 ContentPackage revision；
- 近期内容；
- 用户上传文件或粘贴正文；
- 已登记门店项目/活动；
- 选题证据卡。

目标平台由任务入口或已有 ContentPackage 自动推断；只有冲突时才单问。适配结果必须显示保留了哪些事实、改变了哪些表达、哪些平台字段仍需人工完成。

### 4.4 人设与知识：能力位置正确，任务内反馈不足

“添加人设”位于 Composer 发送按钮旁，位置合理；但本轮点击后跳转 `/personalSet`，页面只显示返回与极淡的内容，未出现明确加载、空态、错误或可操作列表。该现象可能与当前账号数据或单次会话有关，不能外推为全量故障，但足以说明：**人设管理不宜成为创作主链的页面跳转依赖**。

知识库 live 页面提供：

- 文件类型筛选；
- 文件名搜索；
- 添加/上传文件；
- 空态和上传 CTA。

逆向基线另证实文件抽取、状态、重试、重命名、平台链接与预览接口存在。对我方而言，知识不应表现为一个需要用户先整理完整的通用 RAG 仓库；更适合映射到已有三池：门店与个人事实、真实素材/证据、当前即时信号。用户在 Composer 中只需看到本次已采用的来源 chips 和缺口提示。

### 4.5 历史与资产：值得借鉴其可恢复感，不复制对象模型

草稿箱提供：

- 网格/列表两种视图；
- 标题搜索；
- 更新时间、文章类型、标签筛选；
- 添加标签和批量管理；
- 侧栏近期创作快速曝光。

这形成了“生成不是一次性响应”的连续使用感。局限是草稿、知识、图片三个并列库与其通用文档产品吻合，却不应直接映射到我方：

- 我方内容成品仍由 ContentPackage 承载；
- 图片与视频由 Asset/Media 承载；
- Work/Task/Job 承载生成过程；
- Recent 只做跨对象投影与恢复入口。

本轮 OpenCLI 尝试点击两条历史草稿，没有进入可核验的编辑器状态，因此只能确认历史可见和管理表面，不能把“点击即恢复编辑”记为 live 已验证。

### 4.6 生成后编辑：方向成立，本轮不冒充 live 结果

由于本轮禁止消耗额度，未创建候选、未进入新文章编辑器，也未验证生成中状态。以下能力来自既有客户端/接口逆向基线，不属于本轮 UI 证明：

- TipTap/ProseMirror 文档编辑器；
- 选中文本后下 AI 指令；
- 多个改写结果择优插入；
- 自动保存与写作历史；
- 生成标题、摘要、封面；
- 内容分类与图片匹配；
- 校对、审核与反馈；
- 平台预览；
- Word 导出、PDF 预览。

这些能力说明“生成后继续编辑”是讯飞绘文的产品核心，而不是附加 polish。对我方的正确迁移不是引入另一套文档实体，而是在文案/图文 ContentPackage 结果工作区中提供：

- 标题、正文、话题、CTA 的轻量文档编辑；
- 小红书平台预览；
- 封面与图片序列；
- 选区改写、缩写、换语气、补事实引用；
- 常驻自由文本“调整方向”；
- 每次保存/AI 修改形成 derived revision，可比较、可撤销。

### 4.7 发布与数据：参考交接界面，不复制技术承诺

发布数据页将小红书、微信公众号、头条号、百家号、抖音和微信视频号并列，并显示账号、粉丝和收益概览。本次选中小红书时，页面明确显示“未绑定任何账号”和“去绑定”，同时右侧仍保留“发布新文章”。本轮没有点击发布或绑定，因此实际前置拦截、草稿同步、失败恢复和数据准确性均未验证。

更重要的是，既有逆向基线显示其桌面端发布不是统一官方 API：小红书链路包含页面上下文、Cookie、签名、无头浏览器和 CDP Fetch 拦截。对我方来说：

- 只有 `automatic_verified` 才显示自动发布；
- 未绑定、未验证或平台规则不允许时显示 L3 发布包/人工交接；
- 账号、平台、ContentPackage revision、时间、费用和批准回执必须精确绑定；
- 竞品按钮存在不能证明该能力适合我方部署、合规和稳定性边界。

## 6. 建议的图文笔记目标旅程

结合我方现状与讯飞绘文可迁移部分，图文笔记/小红书主链建议收敛为：

1. **入口**：统一 Composer 首屏，快捷任务包括“从案例图写小红书”“写项目科普”“把旧帖改成同城版本”“一题三写”“换平台口吻”。
2. **输入**：一句自然语言为主；`+` 同时承载真实素材、近期内容、门店事实和选题证据。
3. **意图正名**：Agent 自动识别小红书图文/纯文案/跨平台改写，生成一张 Brief 摘要；只显示平台、交付物、使用素材/事实、预计消耗和一个主 CTA。
4. **缺口处理**：一次只问一个关键问题；非关键缺口使用安全默认并说明。
5. **生成中**：同一 Task 卡原位展示“整理事实—生成—合规检查—组装笔记”，可离开、可恢复。
6. **结果**：默认展示一份主推荐：标题、正文、话题、CTA、封面、图片序列和小红书预览；备选按标题/Hook/段落局部展开。
7. **编辑**：选区 AI 快捷动作 + 常驻自由文本“调整方向”；所有修改创建新 revision，不覆盖原结果。
8. **交付**：采用、保存、导出发布包、账号级发布/人工交接分开；发布前显示平台能力与一次性批准。
9. **复用**：Recent 恢复本次 Task；“做同款”复用结构与偏好，由新 ContextBundle 注入当前事实。

## 7. 可访问性与基础交互风险

### 已观察到的正向点

- 选题与资产页的 tab 具备 `role=tab`、`aria-selected` 和 `tabpanel`。
- 文件上传使用真实 `input[type=file]`，生成/加载区域存在 `aria-live`。
- 内容区布局清楚，正文与侧栏的视觉层级稳定。

### 需要避免或修复的风险

1. **大量导航与快捷动作只是 `div`。** OpenCLI 可访问性树中侧栏菜单、写作动作、最近草稿和不少案例没有 link/button 语义；键盘与读屏可发现性不足。
2. **图标按钮缺少名称。** Composer 底部多个附件/模式/设置图标在快照中没有可读名称，图片 `alt` 为空；不能只依赖图形和 tooltip。
3. **自定义选择器暴露内部值。** 选题来源/赛道的可访问性树同时出现 `diverge`、`xiaohongshu`、`key-健康医疗` 等内部 option 值与另一套可视菜单，需统一 accessible name 与焦点模型。
4. **历史草稿卡缺少可操作语义。** 标题和卡片没有明确 button/link role；更多按钮也缺少名称。本轮自动化点击不能恢复编辑，至少说明事件目标与可访问路径不稳定。
5. **人设页缺少状态反馈。** 本次 `/personalSet` 几乎空白，没有加载、空态或错误说明，且可见内容对比度很低；即使属于单账号异常，也需要可恢复状态。
6. **低对比占位符与浅紫文字。** Brief 空槽、禁用/提示内容和人设页文字偏浅；需按 200% 缩放、系统高对比和 WCAG 对比度复核。
7. **嵌套滚动与浮层较多。** 主内容、侧栏、会员抽屉和浏览器扩展浮层同时存在；核心工作区应避免多滚动容器争夺键盘/触控焦点。
