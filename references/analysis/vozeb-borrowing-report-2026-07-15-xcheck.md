## 结论摘要

**主报告的工程骨架与全部关键数值经三重验证成立**:占位 baseUrl + 服务端注 Key、任务 fire-and-forget、心跳 30s / 僵尸 3min / TTL 1h、图片并发服务端 429 硬校验、先扣后退三通道、上游 2xx 锁定、视频路径回退链、错误分类两级重试、记录=持久单位/结果=投影双向序列化、种子版本化幂等注入、mojibake 修复、Canvas Agent 三段桥——全部为真。两条核心反面教材(异步任务创建即扣不退、视频并发仅客户端软限制)被独立复现。

**但交叉验证抓出主报告 8 处失准表述 + 一批主报告完全遗漏的 High 级安全洞。** 失准集中在一个模式:**我把 vozeb 说得比实际更安全、更自动、更彻底**(SSRF 防护、Base URL 隐藏、注入防御、幂等结算、健康嗅探、远程采集、Agent 上下文)。这正是交叉验证的价值——单轮深读会不自觉地"脑补完整性",独立盲读 + 源码终审把这些脑补逐条戳破。

下面按"必须修正"和"必须补入"两类给出,均已源码定案,可直接据此改主报告。

## 一、必须修正(主报告事实性错误 / 表述过强)

### M1 ★★★ §1.4 SSRF"三处复用同一 DNS 全记录校验"——硬错(三份裁决独立指认)

- 主报告原文:"SSRF 防御在三处(媒体代理/副本下载/参考图代理)复用同一实现:`dns.lookup(all:true)` 全记录公网校验 + `redirect:manual`"。
- 源码真相:DNS 全记录强校验**只有生成日志副本下载一处**(`generation-log-store.ts:349-383` `isSafeRemoteAssetUrl`);`/api/media-proxy` 与渠道 `_media` 用的是**未做 DNS 的字符串黑名单** `isBlockedHost`/`isBlockedProxyHost` 且 `redirect:"follow"`;"参考图代理"根本**不 fetch 远程 URL**(只接收 `data:` URL 落盘,`reference-assets/route.ts:13`),不存在 SSRF 出口。
- 改法:"DNS 强校验仅用于副本下载(`isSafeRemoteAssetUrl`);媒体代理是可绕过的弱黑名单,是反面教材;借鉴时以 `isSafeRemoteAssetUrl` 为唯一安全出口统一收口。"

### M2 ★★★ §1.1"真实 Base URL 只存服务端 / 对前端脱敏为占位地址"——错

- 源码真相:每次成功代理的响应都设置 `x-vozeb-upstream-url: <完整上游 URL 含路径查询串>`(`route.ts:382`),前端图片/视频代码**主动读取该头**解析媒体地址(`services/api/image.ts:659`、`video.ts:258`)。
- 定案:**API Key 隔离成立**(这条主报告没错),但 **Base URL 仅在配置下发层隐藏,运行时经响应头全量暴露给浏览器**。
- 改法:改写该句,并把 `x-vozeb-upstream-url` 列为坑——我方媒体转发不应复刻该头,或只回传经代理重写后的地址。

### M3 ★★★ §1.1"双重校验……杜绝注入任意上游"——过强,轮询链可绕

- 源码真相:`sanitizeConfig` 对 baseUrl/apiKey 的校验属实(M4 复核为真),但**只覆盖生成请求本身**。轮询链没防住:客户端可提交 `advancedConfig`,`queryPath` 只做 `textOrEmpty`(trim,`image-tasks/route.ts:630`),`imageTaskPollUrls` 显式接受绝对 `http(s)://` 地址(`:1055`),`taskHeaders` 又按 `config.baseUrl` 而非实际目标决定是否附带用户 Cookie(`:763`)→ 登录用户 POST `/api/image-tasks` 可让服务端携带原始 Session Cookie 轮询任意外部地址(**SSRF + Cookie 外带**)。
- 改法:删/弱化"杜绝注入",补反面教材:"任务侧协议配置(queryPath 等)必须以服务端存储的渠道配置为准,绝不信任客户端提交"。比主报告 P2 积压里那条泛泛的 SSRF 具体得多。

### M4 ★★☆ 执行摘要"幂等结算"——言过其实

- 源码真相:`pointsSettled` 是**请求闭包内的局部布尔**(`route.ts:68`),无持久化 ID / 状态 / 幂等键,跨进程/跨重试/崩溃恢复均不覆盖;`refundUserPoints` 自身可重复加钱(`store.ts:729` 无防重)。
- 改法:执行摘要"幂等结算"→"单请求内防重复退款(非持久化幂等)";并把"缺持久化结算状态机"补进 §1.5——正好让我方"配额结算挂任务终态"的对策论据自洽(那本就要求持久状态机)。

### M5 ★★☆ §1.3/§2.7 健康检查"自动嗅探协议并回填配置模板"——降精度

- 源码真相:①健康检查只跑**少量** payload 变体(非正式链路的几十种矩阵);②"推断"实为**首个 2xx 的路径 → 预定义配置模板的静态映射**(`channel-health/route.ts` 按 path 返回固定 `videoHealthConfig`),不从响应动态推导字段、不轮询验证到生成终态;③端点**不落库**,回填是管理端"一键检测"合并进 React 草稿(`admin-dashboard.tsx:1253`),须管理员手动保存。
- 改法:降精度为"创建端点探测(少量变体)+ 首个 2xx 按路径映射预定义模板 + 管理端草稿手动保存,无端到端验证"。产品借鉴方向不变,但我方若做"渠道接入向导",明确超越点=轮询到终态 + 人工确认。

### M6 ★★☆ §2.2 CDK"只存 hash"——错

- 源码真相:`createCdkCodes` 落库 `{...publicCode}` **明文 `code` 与 `codeHash` 并存**(`store.ts:499-517`),明文进 auth.json 和备份;`listCdkCodes` 还只列 `status==="active" && Boolean(code.code)`,禁用码/无明文旧码从管理视图消失(`:455`)。
- 改法:改为"码表含 hash 字段但明文仍持久化(反面教材)";我方规格定为"真·只存 hash,明文仅生成时展示一次"。

### M7 ★☆☆ §2.1 提示词库"远程采集"作为线上能力 + "只留能显示的远程图"——两处过强

- 源码真相:①采集器 `loadOriginalAuthorPrompts` **运行时零调用方**,线上只消费固化的 874 条 `original-author-seeds.json`——"远程采集"是**离线数据准备代码**,不是线上产品能力;②"封面可达性探测"实际被 `isTrustedImageHost` 白名单直通,当前 874 条**全在白名单内=实际未逐图探测**,且 HEAD 非 2xx 不 fallback 到 Range GET。
- 改法:"管理员策展 + **离线采集固化种子**";探测描述弱化为"白名单直通 + 非白名单才 HEAD/Range 探测,当前种子全走白名单"。**这反而强化我方该学的模式:采集与线上运行解耦。**

### M8 ★★☆ §1.7 Agent 三处失准

- **"上下文不塞 base64"只对画布快照层成立**:`buildToolAgentMessages` 把选中图片经 `imageToDataUrl` 以**完整 base64** 塞入 `image_url`(`canvas-assistant-panel.tsx:1389`),工具结果 before/after 是完整 metadata 快照(可能含 data URL)并回灌模型 + 持久化。改为"画布结构快照裁剪不含 base64;但选中图片引用仍以完整 data URL 送模型"。
- **"批准/拒绝后继续工具循环"错**:`rejectOnlineTool` 只标 rejected 不回灌模型(`:525`),**拒绝即终止,模型无修正机会**;只有批准走 `continueOnlineToolLoopAfterResults`。
- **"op 归一化在服务端全部展开"需限定**:本地 Agent 在 Node 进程归一化(`canvas-session.ts:47`),但在线画布助手的 `onlineToolToOps` 在**浏览器组件内**(`:1040`)。改为"两条路径各有一个归一化点,前端只实现一套 op 执行器"(后半句结论不变)。
- 附:工具数 23 正确(Codex 数成 22 少一个),但其中 3 个只读,**20 个写类工具**展开为 apply_ops。

### 另:两处轻量修正

- **§1.5 响应头名**:`x-points-*` → `x-vozeb-points-cost` / `x-vozeb-points-remaining`(机制无误,补前缀)。
- **§1.4/§2.6 三层兜底"自动降级"过强**:实为静态优选 `remoteUrl || serverUrl` 选一次(`generation-logs/route.ts:69`)+ `<img onError>` 标记丢失,**非运行时逐层 failover**。真正的"可观测 failover"应列为我方要补的增量,而非 vozeb 既有能力。
- **反面教材"批量删除=前端循环单删"过泛**:仅 admin 后台用户/提示词是循环单删;CDK 与生成日志是**真批量端点**(DELETE 带 ids body)。改为"用户/提示词批量删除为前端循环单删,CDK/日志为真批量,批量语义不一致"。

## 三、产品/战略层:无实质冲突,一处加限定

r8 产品视角与主报告 §三战略判断**无冲突**,但补一条关键限定并强化结论:

- r8 论证 vozeb 本质是"**带轻量账户与运营后台的本地优先创作工具,而非完成数据隔离的多用户 SaaS**"(README 自己警告不建议公网多人共用;A3/B3 的账号隔离缺陷是硬证据)。
- 因此主报告 §3.4"一个二开作者就能维护到可用水平"应限定为"**单人/小团队自部署形态**可用"。
- **这反而加强主报告的核心结论**:通用工作台的开源商品化只发生在**单机形态**;真正的多租户 SaaS 工程(数据隔离、耐久任务、计费闭环、SSRF 收口)恰恰是开源**没送**的部分——与美业垂直内核同为我方护城河。交叉验证审出的这批安全洞,本身就是"多租户化"这件事有多少隐性工作量的实证清单。
