## ⚠️ 先说许可边界(必须遵守)

vozeb 是 **AGPL-3.0**。这意味着:

- **可以**:学习其设计模式、协议兼容策略、数据结构、控制流,自行重写实现;
- **不可以**:把它的代码复制/改写进我们的闭源 SaaS——AGPL 具有网络服务传染性,哪怕只抄一个文件,理论上整个服务都要开源。
- 结论:本报告所有"借鉴"均指**范式借鉴 + 自主重写**,与 KickArt 的处理口径一致(范式参考,不套壳、不搬代码)。

## 执行摘要

vozeb 与我们高度同构:同样是"OpenAI 兼容渠道 + 图/视频异步生成 + 素材沉淀 + 配额计费 + 管理后台"的全栈单体。它在三件事上做到了工程上的"意外成熟":

1. **对非标准 AI 网关的暴力兼容 + 自动协议嗅探**——直接回答了我们视频成片 P0(Seedance/即梦/兼容网关直调)会遇到的所有脏问题;
2. **"刷新不丢任务"的异步任务生命周期**(任务句柄持久化 + 挂载扫描续跑 + 心跳/僵尸检测 + 服务端并发硬限制)——是我们异步任务中心缺失的韧性层;
3. **计费与代理合一**(先扣后退、abort 退款、幂等结算、积分走响应头回传)——给我们的条数配额口径一个经过实战的参照,连它的坑(异步任务创建即扣、终态失败不退)都替我们踩好了。

产品化层面,它的"公共提示词库(官方策展+采集)+ 我的提示词 + 素材沉淀"三件套,就是我们美业模板/话术库的通用形态原型;积分/签到/CDK 是现成的增长玩法组件。战略层面,它证明**通用 AI 创作工作台已经商品化(还是 AGPL 开源的)**——我们不应在通用工作台上消耗弹药,而应把它当作"免费的工程模式库",把差异化全部押在美业垂直内核(话术知识、合规、场景模板、本地商家工作流)。

## 一、工程机制层:可直接借鉴进现有代码的实现模式

### 1.1 模型渠道代理与密钥安全边界 ★★★(与 model-supply 直接相关)

vozeb 做法(`web/src/app/api/ai/system/[channelId]/[...path]/route.ts` + `lib/auth/store.ts`):

- 客户端只见占位 baseUrl `/api/ai/system/{channelId}`,模型编码为 `channelId::model`;真实 Base URL/API Key 只存服务端,在代理层注入 `Authorization`; `[XCHECK 更正 M2]` **API Key 隔离成立,但 Base URL 运行时经 `x-vozeb-upstream-url` 响应头全量暴露给浏览器,前端主动读取——不是"只存服务端"。**
- 服务端 `sanitizeConfig` 双重校验:客户端提交的 config 里 baseUrl 必须以 `/api/ai/system/` 开头、apiKey 只允许字面量 `"system"`,杜绝注入任意上游; `[XCHECK 更正 M3]` **仅覆盖生成请求;轮询链 `queryPath` 不重绑服务端渠道 + 按 baseUrl 决定带 Session Cookie = SSRF + Cookie 外带,"杜绝注入"不成立。**
- **媒体代理按 origin 决定是否带鉴权**:`includeAuth = 媒体URL.origin === 渠道apiBase.origin`——上游私有媒体带 Key、第三方公网 CDN 裸转发,一行判断防止管理员 Key 泄漏给任意外部主机;
- 公共设置下发时把渠道脱敏为 `hasApiKey` 布尔,密钥永不出后端。

**我方落点**:`apps/core/src/p1/model-supply/` + web 端 `model-settings.tsx`/BYOK 面板。我们已有"服务端渠道 + BYOK"双轨,可补三件事:①客户端 config 的服务端白名单校验(防伪造 baseUrl);②媒体转发的 origin-gated 鉴权注入(我们接 tu-zi/火山后必然要转发生成结果 URL,这是现成的防 Key 泄漏方案);③渠道对前端一律脱敏为占位地址(我们目前 BYOK 面板的密钥掩码逻辑可对齐这个口径)。

### 1.2 异步任务生命周期:"刷新不丢" ★★★(异步任务中心 + 视频链路)

vozeb 做法(`lib/server/image-task-store.ts` + 各工作台页面):

- POST 创建任务即返回 `task.id`,服务端 fire-and-forget 跑任务;任务表挂 `globalThis`(热重载不丢),TTL 1h,**心跳 30s 刷新 + 3min 无心跳判僵尸置错**;
- 任务句柄(`taskId`)随生成记录/画布节点 metadata 一起持久化;**页面挂载时扫描"进行中且有句柄且未在跑"的项,自动重建轮询**(`resumePendingLogs`),`AbortController` Map 统一取消;
- 每用户并发上限**服务端硬校验**(创建入口计数活跃任务,超限 429),前端另有信号量池 + 等待队列,UI 显式展示 `运行 N/上限`;
- 上游先返回 `task_id` 的异步协议:多候选轮询 URL 按序尝试(显式配置 → 约定路径 → `/images/generations/{id}`),支持 `{task_id}`/`:task_id` 模板占位,404/405 换下一个候选。

**我方落点**:`async-task-center.tsx` + apps/core 任务链。我们有 PG,任务持久化天然比它强,但**缺的恰是它有的三样**:心跳/僵尸检测(我们的视频任务如果 worker 挂了,前端会永远转圈)、挂载扫描续跑(刷新后任务中心要能接续展示进行中任务)、服务端并发硬限制(P0 视频成片一旦上线,单用户并发不设防会直接打爆渠道配额)。建议作为任务中心的验收标准写进票:**"刷新页面后,进行中任务自动恢复轮询;kill 掉 worker,3 分钟内任务转为可重试的失败态"**。

### 1.3 视频协议暴力兼容 + 健康检查自动嗅探 ★★★(视频成片 P0 的最大外部输入)

vozeb 做法(`services/api/video.ts` + `api/admin/channel-health/route.ts`):

- 创建路径回退链:`/videos`(OpenAI 官方)→ `/video/generations` → `/videos/generations` → `/videos/videos`(+ Seedance 专属 `/contents/generations/tasks`);
- 每条路径下用 `buildCompatibleVideoPayloadVariants` 生成几十种 body 变体(参考图字段 `image/images/image_url/first_frame_url…` × 时长字段 `duration/seconds…`),按错误信息正则分类(400/422 且含 duration/image/unmarshal → 换变体;404/405/415 → 换路径)逐个试探,`JSON.stringify` 去重;
- 结果提取不依赖固定响应结构:深度递归 6 层遍历容器键挖 URL/base64/task_id/status,且支持管理员配置 `resultField/statusField` 路径 DSL 覆盖;
- **channel-health 端点把上面全部试探跑一遍,成功后回填"推断出的协议配置模板"**(createPath/queryPath/requestTemplate/resultField/durationRange/参考图支持位)——管理员填 baseUrl+Key,系统自动嗅探协议。 `[XCHECK 更正 M5]` **实为"少量变体探测 + 首个 2xx 路径→预定义模板静态映射 + 管理端草稿手动保存",不从响应动态推导、不验证到生成终态、不落库。方向对,机制别当端到端自动发现。**

**我方落点**:apps/core 视频生成链(Seedance/即梦直调)。我们的决策是"直调官方 + 兼容网关兜底",vozeb 等于把兼容网关的字段地狱全部踩过并给出错误分类表。借鉴方式:①不必照搬几十种变体,但**错误分类驱动的"换变体/换路径"两级重试状态机**值得直接采用;②深度递归结果提取器 + 可配置字段路径,能让我们接新渠道不改代码;③**渠道健康检查=自动协议嗅探**应作为 admin 渠道管理的产品功能(见 2.7),这对我们后续混用模型、切换国内渠道(火山/即梦)时的运营成本是数量级的差别。

### 1.4 媒体三层兜底 + SSRF 防御 ★★☆(TOS 存储 + P2 SSRF 积压的现成答案)

vozeb 做法:

- 每个生成资产并存三源:`url`(当前访问)/`remoteUrl`(上游原始)/`serverUrl`(服务器副本),用户端优先级 **本地缓存(IndexedDB Blob)→ 远程 URL → 服务器副本**;渲染层直接打"本地缓存/远程/服务器副本"彩色来源徽标,`<img onError>` 触发丢失标记与一键清理;
- 服务器副本下载有护栏:图 20MB/视频 300MB 上限、15s 超时、`content-length` 预检 + 读后复检;
- **SSRF 防御在三处(媒体代理/副本下载/参考图代理)复用同一实现**:`dns.lookup(all:true)` 要求所有 A/AAAA 记录均为公网 IP(排除全部私网/CGNAT/IPv6 ULA 段)+ `redirect:"manual"` 防跳内网; `[XCHECK 更正 M1 — 硬错,三份裁决独立指认]` **DNS 全记录强校验只有副本下载一处(`isSafeRemoteAssetUrl`);媒体代理是无 DNS、可绕过的弱字符串黑名单(IPv6 `[::1]`/`localhost.` 可穿透)+ `redirect:follow`;"参考图代理"根本不 fetch 远程 URL。借鉴只能以 `isSafeRemoteAssetUrl` 为唯一安全出口。另:图片任务参考图/结果的服务端抓取完全无 SSRF 防护(xcheck A1)。**
- 视频代理保留 `Range/Content-Range/Accept-Ranges`,浏览器分段播放/拖动可用;
- 本地参考图对"只收公网 URL"的上游:落盘为 24h TTL 一次性 token 资源,拼公网地址提交,用完过期清理。

**我方落点**:`canonical-media-gallery.tsx` + apps/core 媒体层 + 未来火山 TOS。①三源模型可简化为两源(TOS 副本 + 上游远程),但"**生成成功先记远程 URL,副本异步落 TOS,展示按可用性降级**"的解耦值得采用——生成链不被存储写入阻塞;②我们 P2 积压里有"SSRF 深度"一项,vozeb 的 DNS 全记录公网校验就是参考实现,可按它的私网段清单直接写我们的测试用例;③Range 透传是视频成片交付页的硬需求,提前写进验收;④参考图临时公网化机制,即梦/Seedance 只收 URL 时我们同样需要。

### 1.5 计费与代理合一:先扣后退 + 幂等结算 ★★★(条数配额口径)

vozeb 做法(代理路由内):

- `classifyPointsRequest` 按"路径+body"判计费类型与倍率(张数×画质倍率、分辨率×时长倍率、模型单价表 + `__default__` 兜底);
- **先扣积分再转发**;失败退款三通道:fetch 异常退、上游非 2xx 退、客户端 abort 监听器退;`pointsSettled` 幂等标志防重复退,上游 2xx 即锁定; `[XCHECK 更正 M4]` **`pointsSettled` 只是请求闭包内局部布尔,无持久化/幂等键/崩溃恢复,`refundUserPoints` 自身可重复加钱——是"单请求内防重复退款",不是"幂等结算"。**
- 消耗/退回都写流水(`balanceAfter` 快照),积分变动经响应头 `x-points-cost/x-points-remaining` 回传,前端每次请求后同步余额,零额外轮询。

**它的坑(反面教材)**:异步视频任务**创建成功即扣费**,后续轮询失败不自动退——因为"上游 2xx"对异步协议只代表任务受理。

**我方落点**:我们的"条数"配额结算。借鉴:①计费集中在核心应用服务一个 seam(我们的 Product Core Application Service 正好是这个位置),不散落各生成入口;②幂等结算标志 + 三通道退款;③**修正它的坑:异步任务的配额结算必须挂在任务终态上**(成功终态才落扣,失败终态自动回滚),这直接写进我们视频链路的验收;④余额随响应头/响应体回传,前端免独立轮询。

### 1.6 生成记录模型:"记录=持久单位,结果=运行时投影" ★★☆(工作台 UX 内核)

vozeb 做法(图片工作台 1815 行单文件,但数据模型很干净):

- 一条记录(`GenerationLog`)持久化 `images/imageTasks/failures` 三数组;运行态由 `resultsFromLog()` 投影成结果网格,`buildLogFromResults()` 反向序列化;
- 同一记录**追加生成**(新结果 slotIndex 从尾部递增)、**失败原槽重试**(复用 result id 不新增槽位)、勾选删除单结果(联动中断 AbortController + 清远端日志 + 删本地 Blob)、记录标题内联重命名;
- 序列化时剥离大二进制:有 storageKey 就清空 dataUrl/缩略图,IndexedDB 里 JSON 与 Blob 不双写。

**我方落点**:ContentPackage 正是"一个聚合多产物"的结构,vozeb 的记录模型给了工作台交互的具体形态:同一个内容包下"再生成 3 条文案/换一版视频"应是**追加**而非新建包;单条产物失败应**原位重试**;这两条可作为工作台后续迭代的交互规范。

### 1.7 Agent 操作富状态 UI 的稳健范式 ★★★(对话式外壳结构化内核的直接印证)

vozeb 做法(画布助手 + 本地 Canvas Agent):

- **op 归一化**:23 个高层语义工具(建节点/连线/生成流程…)在服务端全部展开为单一 `canvas_apply_ops` 的 op 列表,前端只实现一套 op 执行器——工具语义扩展不动前端;
- **写操作人工确认闭环**:`confirmTools` 开启时写类工具挂起为待确认消息,批准/拒绝后继续工具循环;
- **noop 归因**:执行 op 前后对画布做快照签名对比,没变化就返回"没找到要连接的节点/连线已存在"等精准原因——**防止模型假装执行成功**;
- 上下文只送裁剪快照(节点 id/类型/位置 + 内容截断 500 字),不塞 base64; `[XCHECK 更正 M8]` **仅画布结构快照层不含 base64;选中图片引用仍以完整 data URL 送模型。另:拒绝工具即终止(非继续循环);op 归一化在线助手在前端展开(非全在服务端);23 工具中 20 个写类展开为 apply_ops。**
- 工具循环上限 4 步,首轮强制调工具、禁止编造结果。

**我方落点**:这是对我们 ADR"对话式外壳、结构化内核"的第三方印证,且给出三个我们还没有的护栏,建议进 Agent 工作台的设计规范:①**所有 agent 写操作收敛为一个 apply_ops 口**(对我们即"对 ContentPackage 的结构化 patch 指令集"),外壳工具再多,内核只认 patch;②**签名对比 + noop 归因**——agent 说"已为你更新文案"时系统必须能证明状态真的变了,这与我们 D01"真实跑通"的诚实性哲学同源;③写操作确认开关(美业商家场景默认低打扰,但发布类动作必须确认,与我们红线硬停机制互补)。Polotno 画布若做 agent 化,op 归一化就是现成蓝图。

### 1.8 中小型工程韧性件 ★☆☆(择优少量采用)

- **备份导入前自动快照、只留最近 3 份** + **离线管理员密码重置脚本**(强制指定账号、改前备份、`.tmp`+rename 原子写、多匹配即报错)——"后台锁死自救链路"完整。我方是 PG,数据库备份走托管,但**最后管理员保护**(不能删/禁用最后一个 active admin,导入校验也强制)值得抄进我们的 admin 用户管理;
- **种子版本化幂等注入**(`ensureOriginalAuthorPrompts` + `:v3` 标记:读库时发现版本不符→删旧种子→导入新种子→记版本,不碰用户数据)——**这正是我们美业模板库/话术库种子数据的发布机制**,比裸 migration 干净,强烈建议采用;
- mojibake 自动修复(latin1↔utf8 检测 + CJK 打分择优)——采集异构中文源时的实用防御,我们做行业内容采集时留档备用;
- 反代 secure-cookie 判定链(env 强制 → X-Forwarded-Proto → Forwarded → url 协议)——我们 CF 部署 + 未来国内反代迁移时会遇到同样问题,口袋里备着。

## 二、产品化借鉴:功能形态层

### 2.1 提示词库三件套 → 美业模板/话术市场 ★★★

vozeb 形态:公共库(管理员策展 + 远程采集,带标签/分类/封面/Markdown 预览图组)+ 我的提示词(用户私有沉淀)+ 素材库(text/image/video 三类,可从生成结果一键沉淀)。 `[XCHECK 更正 M7]` **"远程采集"实为离线数据准备代码(运行时零调用),线上只消费固化的 874 条种子 JSON——采集与线上运行解耦,这反而是该学的模式。**

**映射到我们**:这就是我们 `template-catalog` + 未来"美业内容资产库"的通用原型,三点具体借鉴:

1. **双 scope 数据模型**(`scope: library|user` + ownerUserId 隔离,同一套 CRUD/检索/标签基建复用)——我们的模板库目前是官方单向供给,加 `user` scope 即获得"商家自有话术沉淀",这是留存钩子(商家积累越多越难走),也呼应我们"本地知识库=护城河"的既有判断;
2. **采集器多源适配器 + 图片可达性过滤**(每源一个 build() 独立容错,封面 HEAD/Range 探测 + 徽章黑名单,只留真正能显示的远程图)——我们做"美业爆款内容结构采集"(小红书/抖音案例参考)时是同样的工程问题;注意我们的合规口径:采集只作内部策展参考,上架内容须有授权或原创;
3. **"从生成结果一键存为素材/模板"**——我们工作台的产物(好的一条文案、一张卡图)应可一键沉淀进商家自己的库,形成"生成→筛选→沉淀→复用"闭环,这是 vozeb 首页 slogan"沉淀每一次好结果"的核心,也应该是我们的。

### 2.2 积分/签到/CDK → 配额与增长玩法 ★★☆

vozeb 形态:积分余额 + 流水(balanceAfter 快照)+ 签到奖励(上海时区判天)+ CDK 兑换码(去易混字符码表、只存 hash、打码预览、批量生成/导出、每人一次、过期/次数控制)。 `[XCHECK 更正 M6]` **CDK 实为明文码 + hash 并存(明文进 auth.json 和备份),管理列表依赖明文展示——是反面教材;我方规格应真·只存 hash、明文仅生成时展示一次。**

**映射到我们**:我们是 399-599 订阅 + 条数配额,不需要积分经济,但两个组件可平移:

1. **CDK 兑换码=线下渠道载体**。美业客群的获客场景高度线下(展会、代理商、异业合作、美博会),CDK 是"渠道商发卡→商家扫码兑换条数/试用期"的最轻实现,vozeb 的码表设计(hash 存储、打码展示、批量导出、兑换明细)可直接作规格参考;
2. **计费配置化**:模型单价表 + `__default__` 兜底 + 画质/时长倍率,管理员可调——我们混用模型(验证期海外模型 + 落地后国内模型)时,"一条视频消耗几个条数"必然要按模型/时长浮动,这套配置结构直接可用;
3. 签到对 B 端商家价值存疑,不建议做;若做活跃钩子,更贴我们场景的是"本周内容日历完成度"类激励(与既有 weekly-operations 呼应)。

### 2.3 公告系统 → 商家端运营位与合规提醒载体 ★★☆

vozeb 形态:公告列表 + 首页弹窗 + 登录后弹窗,时间窗控制,已读只存 localStorage(换设备重弹,缺陷)。

**映射到我们**:我们比它多一个刚性需求——**合规提醒的触达与留痕**(我们的医美轻量版机制=线上纯提醒+红线硬停,17 条自身义务里有留痕要求)。借鉴形态、修正实现:公告/提醒的已读回执必须**服务端落库**(谁、何时、看了哪一版),这样"平台规则变更提醒""红线政策更新"才构成可举证的履责记录。运营位(功能上新、模板上新)与合规提醒共用同一套投放基建,按 severity 区分样式与是否强制确认。

### 2.4 生成日志后台 + 资源对账 → 运营/客服/合规三合一 ★★★

vozeb 形态:全用户生成日志(prompt/入口来源/模型/状态/耗时/结果预览/三源地址,搜索+日期+多维过滤+批量删),资源统计(总量/被引用/未引用/丢失引用)+ 只删未引用文件的安全清理。

**映射到我们**:我们已有 admin-audit,但 vozeb 展示了**生成日志作为产品功能**的完整形态,对我们价值排序:①**客服排障**——美业商家是非技术客群,"我的视频怎么没生成出来"必然是高频工单,后台按用户看到完整链路(哪个渠道、什么错、耗时多少、原始上游地址)是客服效率的分水岭;②**成本审计**——按模型/渠道聚合耗量,直接支撑我们单位经济模型(399-599 定价的毛利监控);③**合规留痕**——生成记录本身就是 AI 生成内容的存证(配合我们的标识烧录义务);④**存储对账清理**——未来 TOS 上"日志引用 vs 实际对象"的对账 + 安全清理,是月度成本治理的现成模式。

### 2.5 首页案例橱窗:内容库自动供给 + 懒加载 ★☆☆

vozeb 形态:首页"沉淀每一次好结果"展示区,random 模式从公共提示词库随机抽 8 条,IntersectionObserver 进视口才加载 + requestIdleCallback 空闲请求,不拖首屏。

**映射到我们**:我们官网/落地页的"案例橱窗"可由**真实模板库/匿名化优秀成片**自动供给,运营零成本、内容常新;懒加载实现直接照做。对美业客群,"看到同行做出来的效果"是最强转化素材。

### 2.6 三层兜底作为产品承诺 ★★☆

vozeb 把"素材永远打得开"做成了可感知的产品能力(来源徽标 + 自动降级 + 丢失清理)。对我们的非技术商家客群,**可靠性即信任**:商家花条数生成的视频,三个月后要二次投放时必须还在。建议把"产物可用性 SLA"(远程失效→TOS 副本兜底)作为 Growth 档以上的显性卖点,而不只是工程内部实现。

### 2.7 渠道接入向导:健康检查产品化 ★★☆

如 1.3 所述,vozeb 的 channel-health 能自动嗅探上游协议并回填配置模板。对我们:admin 加渠道从"读文档手填十个字段"变成"填 baseUrl+Key→点检测→自动识别协议→一键保存",这在我们"验证期海外渠道 + 落地期国内渠道"的多次切换中会反复回本。BYOK 用户侧也可用同一能力做"密钥有效性自检"。

## 三、场景与客群扩展:战略层

### 3.1 无限画布/节点工作流 → 高阶客群(代运营/设计师)的未来容器 ★★☆

vozeb 的中心是画布:节点(图/文/视频/配置)+ 连线组织上下游 + 生成流程节点化。这**不适合**我们的主力客群(非技术美业商家,我们的定案是对话式外壳 + 1 工作台 + 3 资产页),但适合两类延伸客群:

- **美业代运营工作室/连锁品牌内容团队**:一人管 N 家店,需要批量、模板化、可复用的生产流水线——节点画布正是"把一次成功的生产流程固化成可重跑资产"的形态;
- **美业设计师/高阶商家**(Pro 档以上):对生成过程要精细控制(参考图→反推→改提示词→多版对比)。

我们的架构决策(L0-L4 换容器保内核)正好兜住这件事:**画布只是内核(ContentPackage + 结构化 patch)之上的另一个 L 层容器**,不需要现在做,但 vozeb 证明了这个容器的完整形态与工程成本,可作为 Pro/Agency 档的 roadmap 候选,触发条件建议绑"代运营类客户占比"信号而非拍脑袋排期。

### 3.2 本地 Agent + MCP 开放接口 → 生态与高阶自动化 ★☆☆(远期,但架构上便宜)

vozeb 的三段桥(CLI Agent ←MCP stdio→ 本地服务 ←SSE+HTTP→ 浏览器)+ URL 参数自动连接 + Codex 反向注册,让 Claude Code/Codex 直接操作画布。对我们的启发不是照做,而是:

- 如果 1.7 的 **apply_ops 归一化**做到位,"把我们的工作台暴露为 MCP 工具集"是几乎零边际成本的副产品——高阶用户/代运营可以用自己的 agent 批量驱动我们的内容生产;
- 这与我们记忆中既有判断一致(触达=连接桥外接已用工具):MCP 是行业标准连接桥,先把内核 patch 指令集设计干净,开放接口留作 Growth 之后的生态选项。

### 3.3 低配自部署形态 → 私有化部署的可行性证据 ★☆☆

vozeb 用"文件库 + 预构建镜像 + 0.5G 内存"跑通了个人/小团队自部署。我们是多租户 SaaS,主线不变;但它提示了一个远期选项:**连锁美业品牌总部的私有化部署版**(数据不出集团)。vozeb 证明单体架构下这个交付形态的工程成本可以很低——我们的架构 A(Workers 壳 + 单 Node 服务 + 托管 PG)如果保持服务内聚,未来"单租户打包版"不是重写。不建议现在投入,记录为架构约束:**避免引入让单体不可打包的强云绑定**(这与我们"平移便宜"的既有护栏一致)。

### 3.4 竞争定位判断 ★★★

vozeb(及其上游原创项目)代表一个明确信号:**通用 AI 创作工作台正在被开源商品化**——无限画布、图/视频工作台、提示词库、渠道管理、积分后台,一个二开作者就能维护到可用水平,还是 AGPL 免费。推论:

1. 我们**不要**在通用能力上寻求差异化(画布多炫、工作台多全)——这条线的终局是免费开源;
2. 我们的护城河只能在 vozeb 们**做不了**的地方:美业垂直知识(话术框架、品类模板、平台规则)、合规能力(资质准入、标识烧录、留痕)、本地商家工作流(周运营节奏、线索承接)、以及商家自有内容资产的沉淀与复利;
3. vozeb 反而降低了我们的成本:它是一座免费的"工程模式参考库",本报告第一、二部分就是提货清单。

## 四、反面教材(vozeb 的坑,我们要避开)

| 坑 | 后果 | 我们的对策 |
|---|---|---|
| 异步任务"创建即扣费",终态失败不退 | 用户白扣积分 | 配额结算挂任务终态(1.5) |
| 公告已读只存 localStorage | 换设备重弹;无履责留痕 | 已读回执服务端落库(2.3) |
| 视频并发只有客户端软限制 | 绕过前端即可打爆渠道 | 所有并发/配额限制服务端硬校验(1.2) |
| 管理后台 4294 行单文件、图片工作台 1815 行单文件 | 不可维护、不可测 | 我们已按票分模块,保持 |
| 生成记录真源在浏览器 IndexedDB,服务端日志只是镜像 | 换设备/清缓存丢历史;多端不一致要靠复杂去重 | 我们坚持服务端(PG)为唯一真源,客户端只做缓存 |
| "批量删除"实为前端循环单删 | N 次请求、无事务性 | 批量操作走真批量端点 |
| 无数据库文件库 + mutationQueue | 单机可用,多实例即坏 | 我们有 PG,不引入此模式;仅借鉴其 normalize-即-迁移的容错思想 |
